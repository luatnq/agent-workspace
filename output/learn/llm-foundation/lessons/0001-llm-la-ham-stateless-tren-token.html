LLM Foundation · Bài 0001 · 2026-09-20 · ~25 phút · Cheat sheet: Token economics

LLM là một hàm stateless trên token

Mental model đầu tiên, và cũng là cái chi phối cost, latency, và giới hạn của mọi thứ anh sẽ build sau này.

Cái anh mang về sau bài này

Nhìn một tính năng LLM được đề xuất, anh ước lượng được cost và latency từ 4 con số (system prompt, số lượt, độ dài input/output), và chỉ ra được đòn bẩy nào ăn tiền, đòn bẩy nào ăn thời gian — vì hai cái đó không trùng nhau.

1. Model không nhớ gì cả — anh gửi lại toàn bộ lịch sử mỗi lượt

Với dân backend, cách nhanh nhất để hiểu một lệnh gọi LLM là coi nó như một pure function: f(context) → next tokens. Không session, không state phía server. Cái mà chat UI gọi là "cuộc hội thoại" thực ra là client nối tất cả các lượt trước vào request mới rồi gửi lên lại từ đầu.

Doc Anthropic gọi đây là progressive token accumulation: "each user message and assistant response accumulates within the context window, and previous turns are preserved completely." — Context windows

Toàn bộ những gì model "nhìn thấy" trong một lần gọi nằm trong context window. Doc chính thức mô tả nó là "working memory" của model, khác hẳn với corpus khổng lồ nó được train — thứ đó chỉ còn lại dưới dạng trọng số, một kiểu "ký ức mờ". Karpathy dùng đúng cặp hình ảnh này: params = vague recollection, context = working memory. Muốn model biết chắc điều gì, phải đưa vào context, không trông chờ nó "nhớ".

Glossary: Context window — "This is different from the large corpus of data the language model was trained on, and instead represents a 'working memory' for the model."

Hệ quả trực tiếp cho kiến trúc: "memory" là việc của app, không phải của model. Lịch sử hội thoại, hồ sơ user, tài liệu tham chiếu — app quyết định đưa cái gì vào context, và trả tiền cho từng token đưa vào.

2. Mọi thứ đều tính bằng token — và mọi thứ đều nằm trong context

Token là đơn vị đo duy nhất: giá, giới hạn, tốc độ đều tính theo token. Rule of thumb từ doc pricing: 1 token ≈ 4 ký tự ≈ 0.75 từ tiếng Anh; tiếng Việt, code, JSON thường tốn hơn. Một chi tiết nhiều người bỏ qua: tokenizer thay đổi theo thế hệ model — Claude 4.7 trở đi dùng tokenizer mới sinh ra khoảng 30% token nhiều hơn cho cùng một đoạn text, nghĩa là đổi model có thể đổi luôn hóa đơn dù giá/token không đổi.

Pricing FAQ: "1 token is approximately 4 characters or 0.75 words in English." Về tokenizer mới: "This tokenizer produces approximately 30% more tokens for the same text." — Pricing. Muốn thấy tận mắt, dán một đoạn tiếng Việt vào Tiktokenizer.

Cái gì được tính vào context window? Doc trả lời dứt khoát: tất cả.

  • System prompt
  • Mọi message trong messages — kể cả tool results, ảnh, PDF
  • Tool definitions (tên, mô tả, JSON schema của từng tool)
  • Output model sinh ra trong lượt này, kể cả thinking tokens

Cache không thay đổi điều này: "Cached prompt prefixes still occupy the context window: prompt caching changes what you pay for those tokens, not whether they count."

Cả đoạn này lấy từ mục How the context window works và Manage context with compaction của Context windows.

Hai điểm engineering đáng ghim:

  1. Tràn context không phải lỗi mềm. Nếu riêng input đã vượt window → API trả 400 invalid_request_error ("prompt is too long"). Nếu input + max_tokens vượt window, model 4.5+ vẫn chạy nhưng dừng với stop_reason: "model_context_window_exceeded". Code của anh phải xử lý cả hai nhánh.
  2. Nhiều context hơn không tự động tốt hơn. Doc gọi thẳng tên hiện tượng context rot: "As token count grows, accuracy and recall degrade." Window 1M token là trần, không phải mục tiêu.

3. Cost: input rẻ, output đắt, và lịch sử là thứ âm thầm nhân lên

Công thức không có gì bí ẩn:

cost = input_tokens × giá_in + output_tokens × giá_out

Điểm mấu chốt là giá output gấp ~5 lần input trên mọi model Anthropic hiện tại (Opus 5: $5 / $25 per MTok; Sonnet 5: $2 / $10; Haiku 4.5: $1 / $5). Nhưng — và đây là chỗ trực giác hay sai — trong một hội thoại nhiều lượt, input vẫn thường là phần chi phí lớn nhất, vì mục 1: mỗi lượt anh gửi lại cả lịch sử. Lượt thứ n trả tiền cho n−1 lượt trước cộng thêm system prompt.

Bảng giá đầy đủ tại Pricing → Model pricing. Cache write 5 phút = 1.25× giá input, cache read = 0.1×; Batch API giảm 50% cả input lẫn output.

4. Latency: đo bằng output tokens, không phải bằng input

Doc tách hai đại lượng: TTFT (time to first token — thời gian model "đọc xong" prompt và bắt đầu trả lời) và thời gian sinh toàn bộ output. Về mặt cơ chế, model sinh từng token một, tuần tự — nên thời gian sinh tỉ lệ thuận với số output token. Input dài làm TTFT chậm, nhưng phần người dùng cảm nhận rõ nhất là quãng "đang gõ" — và quãng đó do output quyết định.

Reducing latency: "The fewer tokens the model has to process and generate, the faster the response will be." Ba đòn bẩy doc liệt kê: chọn model nhanh hơn, cắt token in/out, streaming.

Ba hệ quả thực dụng:

  • Thinking tokens là output tokens — chúng vừa tính tiền theo giá output, vừa cộng thẳng vào latency. Bật thinking là quyết định có cost/latency rõ ràng, không phải cờ "miễn phí".
  • Streaming không giảm latency thật, nó giảm latency cảm nhận — user thấy chữ hiện ra thay vì chờ. Vẫn là đòn bẩy đáng làm cho chatbot.
  • Đòn bẩy cost và đòn bẩy latency không trùng nhau. Cắt output ngắn lại giảm mạnh latency nhưng giảm ít cost (xem ví dụ dưới). Cache giảm cả cost lẫn TTFT. Đổi model giảm cả hai nhưng đổi chất lượng.

5. Một điểm nhỏ nhưng hay bị hỏi: temperature 0 không đồng nghĩa deterministic

Glossary nói thẳng: "Even with temperature set to 0, the results will not be fully deterministic and identical inputs may produce different outputs across API calls." Nếu ai đó trong team thiết kế test dựa trên "cùng prompt → cùng output", đó là giả định sai từ gốc. Test LLM cần eval theo tiêu chí, không phải string equality — chủ đề của một bài sau.

Glossary: Temperature.

Ví dụ có số: chatbot hỗ trợ khách hàng

Team đề xuất chatbot CSKH. Anh có 4 con số:

  • System prompt gồm tài liệu chính sách + hướng dẫn: 15,000 token
  • Mỗi cuộc hội thoại trung bình 8 lượt; user gõ ~100 token, bot trả ~300 token
  • 500 hội thoại/ngày, dùng Opus 5 ($5 in / $25 out)

Thử tự tính trước khi mở đáp án: một hội thoại tốn bao nhiêu input token tổng cộng? (Gợi ý: lượt k gửi lại system prompt + toàn bộ k−1 lượt trước + câu hỏi mới.)

Đáp án và phân tích

Lượt k input = 15,000 + 400×(k−1) + 100. Cộng 8 lượt: 8×15,100 + 400×(0+1+…+7) = 120,800 + 11,200 = 132,000 input token. Output = 8×300 = 2,400 token.

Phương án$/hội thoại$/ngàyTiết kiệm
Opus 5, không cache0.72360—
Opus 5, cache system prompt (write lượt 1, read 7 lượt sau)0.2713363%
Sonnet 5, không cache0.2914460%

Opus 5, rút reply 300 → 150 token0.673357%

Ba điều đáng thấy:

  1. System prompt gửi lại 8 lần = 120,000 trong 132,000 input token — 83% hóa đơn là một tài liệu không đổi. Đó là lý do cache ăn tiền nhất.
  2. Output chỉ chiếm $0.06/$0.72. Rút reply ngắn một nửa gần như không đổi cost — nhưng giảm một nửa thời gian sinh mỗi lượt. Đòn bẩy latency ≠ đòn bẩy cost.
  3. Batch API không áp dụng: chatbot cần trả lời ngay.

Cách tính cache: write 15,000×$6.25/M = $0.094; read 7×15,000×$0.50/M = $0.053; input còn lại 12,000×$5/M = $0.06; output $0.06. Cộng ≈ $0.27.

Kiểm tra nhanh

Trong một hội thoại 8 lượt, vì sao lượt 8 tốn nhiều input token hơn lượt 1?

  • Cả lịch sử được gửi lại
  • Server giữ state nên tính thêm
  • Output các lượt sau dài hơn
  • Giá mỗi token tăng theo lượt

Model stateless; client gửi lại system prompt + tất cả lượt trước trong mỗi request. Giá/token không đổi theo lượt, và server không giữ state.

Thứ nào dưới đây KHÔNG chiếm chỗ trong context window?

  • Tool definitions của request
  • Thinking tokens lượt này
  • Dữ liệu pretraining model
  • Tool results trả về

Corpus pretraining chỉ còn trong trọng số ("vague recollection"). Tool definitions, tool results và thinking của lượt hiện tại đều tính vào context.

Muốn giảm thời gian sinh output thật sự (không phải cảm nhận) mà không đổi model, đòn bẩy trực tiếp nhất là gì?

  • Rút ngắn output lại
  • Bật prompt caching lên
  • Tăng max_tokens lên cao
  • Đặt temperature về 0

Model sinh từng token tuần tự; thời gian sinh tỉ lệ với số output token. Cache giúp TTFT và cost, không giúp thời gian sinh. max_tokens là trần, không phải tốc độ.

Cùng một prompt, temperature = 0, gọi hai lần. Output có giống hệt nhau không?

  • Vẫn có thể khác nhau
  • Luôn giống hệt như nhau
  • Giống nếu cùng một model
  • Khác chỉ khi prompt dài

Glossary Anthropic nói rõ: ngay cả temperature 0 cũng không hoàn toàn deterministic giữa các lần gọi API. Đừng test LLM bằng string equality.

System prompt 20,000 token, gọi đúng 1 lần mỗi 10 phút, bật cache 5 phút. So với không cache, chi phí phần system prompt ra sao?

  • Đắt hơn là không cache
  • Rẻ hơn là không cache
  • Bằng hệt như không cache
  • Rẻ hơn nếu dùng batch

Cache 5 phút hết hạn trước lần gọi kế tiếp, nên lần nào cũng là cache write (1.25× giá input) và không bao giờ có hit (0.1×). Cache chỉ có lãi khi có ít nhất một lần read trong TTL.
