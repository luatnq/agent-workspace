Tool-use loop: model không gọi gì cả — app của anh gọi

Bài 2 nói "giao cho tool" rất thoải mái. Bài này mở cái hộp đó ra: tool use là một vòng while mà anh sở hữu, model chỉ sinh ra yêu cầu dưới dạng JSON. Hiểu đúng ranh giới này, anh sẽ biết lỗi nằm ở phía nào khi agent "làm sai".

Cái anh mang về sau bài này

Vẽ được vòng lặp tool use bằng 5 bước, chỉ ra 4 chỗ hay hỏng khi đọc một transcript, và thiết kế được một tool definition theo chuẩn Anthropic (gộp thay vì wrap API, mô tả như cho new hire, error message có hướng dẫn) — thứ quyết định agent có gọi đúng tool hay không.

1. Vòng lặp: model là planner, app là executor

Với dân backend, đây là mô hình quen: model không có quyền thực thi gì. Nó nhận danh sách tools (tên + mô tả + JSON schema), và khi thấy cần, nó dừng với stop_reason: "tool_use" kèm một block JSON: {id, name, input}. Phần còn lại là việc của anh.

Tool use overview: "Claude responds with stop_reason: "tool_use" and one or more tool_use blocks. Your code executes the operation and sends back a tool_result."
messages = [user: "Đơn #A123 của tôi tới đâu rồi?"]

loop:
    resp = call(model, tools, messages)          # bài 1: gửi lại tất cả
    messages += assistant(resp.content)

    if resp.stop_reason != "tool_use": break     # end_turn → xong

    results = []
    for block in resp.tool_use_blocks:           # có thể > 1 block
        out = run(block.name, block.input)       # ← CODE CỦA ANH
        results += tool_result(block.id, out)

    messages += user(results)                    # MỘT message duy nhất

Năm điều đáng ghim ngay từ hình này:

  1. Không có role tool. Claude API nhét tool_use vào message của assistant và tool_result vào message của user. Nghĩa là về mặt model, kết quả tool là "người dùng nói cho tôi biết" — quan trọng khi nghĩ về prompt injection (mục 4).
  2. Mỗi vòng là một request đầy đủ — bài 1 áp dụng nguyên xi: toàn bộ lịch sử, tool definitions, và mọi tool result trước đó được gửi lại. Agent 10 vòng = 10 request, request sau to hơn request trước.
  3. Client tool vs server tool. Tool anh định nghĩa chạy ở app anh. web_search, web_fetch, code_execution chạy trên hạ tầng Anthropic, kết quả về thẳng trong cùng response — không có vòng lặp phía anh.
  4. SDK có Tool Runner lo vòng lặp này hộ, nhưng cơ chế bên dưới y hệt. Hiểu vòng lặp thủ công để đọc log khi Tool Runner hành xử lạ.
  5. Loop cần guard. Doc không tự chặn; anh phải đặt số vòng tối đa, ngân sách token, và kiểm tra stop_reason == "max_tokens" trước khi chạy tool (block có thể bị cụt JSON).
Handle tool calls: "Unlike APIs that separate tool use or use special roles like tool or function, the Claude API integrates tools directly into the user and assistant message structure."

2. Model chọn tool bằng cách đọc description — không có gì khác

Với tool_choice: auto (mặc định), doc mô tả tiêu chí rất gọn: model gọi tool "when the request maps to that tool's described capability and the answer isn't already in context." Không có routing table, không có intent classifier riêng — chỉ có văn bản mô tả nằm trong context và cơ chế next-token của bài 1–2. Hệ quả: tool description là prompt engineering, và là chỗ đầu tiên phải sửa khi model gọi sai/không gọi.

Overview → When Claude uses tools. Cùng trang: nếu model không gọi tool như kỳ vọng, một câu trong system prompt như "Use the tools to investigate before responding." đẩy tần suất gọi lên.

Kèm theo: strict: true trên tool definition đảm bảo input luôn khớp schema — loại bỏ hẳn lớp lỗi "thiếu param, sai kiểu". 3. Tool là thứ ngốn context nhanh nhất

Ghép với bài 1, mỗi request trong loop trả tiền cho:

  • Tool definitions — gửi lại mọi request. 20 tool với schema dài là vài nghìn token cố định mỗi vòng.
  • System prompt tool use — API tự chèn, ~286 token trên Opus 5 với auto.
  • tool_use blocks — output token (đắt gấp 5).
  • tool_result blocks — và đây là con quái vật. Một query trả 500 dòng JSON, một trang web 25k token, một stack trace 200 dòng — tất cả nằm trong context cho đến hết cuộc hội thoại.
Bảng token system prompt tool use theo model: Pricing → Tool use. Anthropic "restrict tool responses to 25,000 tokens by default" trong Claude Code — Writing effective tools for agents.

Anthropic tự đặt trần 25k token cho mỗi tool response trong Claude Code, và khuyến nghị tool phải có "pagination, range selection, filtering, and/or truncation with sensible default parameter values". Khi cắt bớt, thông báo cắt phải kèm hướng dẫn: "making many small and targeted searches instead of a single, broad search". Đây là context rot (bài 1) ở dạng thực dụng nhất — và là lý do doc context windows có riêng cơ chế tool result clearing.

4. Bốn chỗ hay hỏng khi đọc transcript

a. Sai thứ tự block → 400

Hai luật cứng: tool_result phải nằm ngay message sau tool_use (không được chen message khác), và trong user message đó, các tool_result phải đứng trước mọi text. Lỗi "tool_use ids were found without tool_result blocks immediately after" gần như luôn là chỗ này.

Handle tool calls → Important formatting requirements.

b. Parallel tool use bị trả rời rạc

Một response có thể chứa nhiều tool_use. Chạy chúng đồng thời, rồi trả tất cả result trong một user message. Tách thành nhiều message không lỗi ngay — nhưng hội thoại đó trở thành ví dụ dạy model "gọi từng cái một", và model sẽ dần ngừng gọi song song. Lỗi im lặng, khó thấy trên log, chỉ thấy khi agent chậm dần.

Parallel tool use. Muốn tắt hẳn: tool_choice: {type: "auto", disable_parallel_tool_use: true}.

c. Tool lỗi → exception làm vỡ loop

Tool gọi API bị 500 không phải lý do để dừng agent. Trả tool_result với is_error: true và nội dung có hướng dẫn: doc lấy ví dụ "Rate limit exceeded. Retry after 60 seconds." thay vì "failed". Model sẽ tự thử lại 2–3 lần với tham số sửa, hoặc giải thích cho user. Nguyên tắc chung: mọi tool_use phải có tool_result, kể cả khi thất bại — drop nó là vi phạm luật (a).

Handle tool calls → is_error: "Write instructive error messages. Instead of generic errors like "failed", include what went wrong and what Claude should try next."

d. Tool result là input không tin cậy

Nhớ điều 1 ở mục 1: tool result đi vào message của user. Nội dung trang web, email inbound, file upload, response của API bên thứ ba — tất cả có thể chứa câu lệnh nhắm vào model (indirect prompt injection). Doc yêu cầu giữ nội dung đó bên trong tool_result block, không bao giờ đưa vào system hay text block thường. Về kiến trúc: quyền thực thi nằm ở app anh, nên hàng rào cuối cùng (confirm trước hành động không hoàn tác, allowlist, sandbox) cũng phải nằm ở app anh, không nằm ở prompt.

Handle tool calls, hộp Warning về untrusted content và Mitigate jailbreaks and prompt injections.

5. Thiết kế tool: wrap API là sai mặc định

Bài viết "Writing effective tools for agents" của Anthropic là primary source cho mục này. Điểm xuất phát của họ: "More tools don't always lead to better outcomes" — đừng wrap từng endpoint REST thành một tool. Agent có context hữu hạn và không có tri thức ngầm của người dùng API.

Bài tập phán đoán

A. Đọc transcript — tìm lỗi. Agent CSKH: user hỏi "đơn A123 và A124 tới đâu rồi?", model trả về 2 block tool_use (get_order A123, get_order A124). App gửi: user[tool_result A123] → gọi model → user[tool_result A124] → gọi model.

Hai lỗi. (1) Request thứ hai thiếu tool_result cho A124 ngay sau tool_use → API trả 400 "tool_use ids were found without tool_result blocks immediately after". (2) Kể cả nếu format lách được, việc trả từng result một là dạy model bỏ parallel (mục 4b). Sửa: chạy hai get_order đồng thời, trả một user message chứa cả hai tool_result, rồi mới gọi model.

B. Thiết kế lại bộ tool. Team wrap 3 endpoint: list_orders() (trả mọi đơn của khách, JSON đầy đủ), get_order(order_uuid), cancel_order(order_uuid). Agent hay gọi list_orders rồi "quên" mất đơn user nói, và đôi lúc hủy nhầm.

Ba vấn đề đối chiếu mục 5: unbounded list làm phình context (search thay list); UUID không có nghĩa nên model dễ lẫn giữa các đơn (trả mã đơn người đọc được + tóm tắt); cancel_order không có rào chắn ở app.

TrướcSau

Error message mẫu cho orders_cancel: "Đơn A123 đã giao ngày 18/09, không hủy được. Nếu khách muốn trả hàng, dùng returns_create." — model có đường đi tiếp thay vì đoán.

C. Agent chạy 40 vòng rồi mới trả lời, hóa đơn cao gấp 8 lần dự kiến. Nhìn vào đâu trước?

Theo thứ tự: (1) kích thước tool_result — một result 20k token được gửi lại 39 lần là ~800k input token; (2) số tool definitions gửi mỗi vòng; (3) có guard số vòng / ngân sách chưa; (4) model có gọi lặp cùng tool cùng input không — dấu hiệu description mơ hồ hoặc error message không hướng dẫn. Cache prefix (bài 1) giảm giá tiền nhưng không giảm context rot — cắt result mới là gốc.

Kiểm tra nhanh

Model trả về stop_reason: "tool_use" với block get_order. Ai thực thi hàm đó?

  • App của anh chạy
  • Model chạy phía server
  • API Anthropic chạy hộ
  • Sandbox của Anthropic chạy

Client tool chạy trong app của anh; model chỉ sinh JSON yêu cầu. Chỉ server tools (web_search, code_execution…) mới chạy trên hạ tầng Anthropic.

Model gọi ba tool song song trong một response. Cách trả kết quả đúng?

  • Cả ba trong một message
  • Mỗi result một message riêng
  • Chỉ trả result đầu tiên
  • Gộp thành một text block

Tất cả tool_result cho cùng một lượt phải nằm trong một user message. Tách ra vừa dễ 400 vừa dạy model bỏ parallel; gộp thành text mất tool_use_id.

Tool gọi API nội bộ bị HTTP 500. App nên làm gì?

  • Trả is_error kèm hướng dẫn
  • Ném exception dừng vòng lặp
  • Bỏ qua, không trả gì
  • Trả result rỗng im lặng

Mọi tool_use phải có tool_result. is_error: true + message nói cái gì sai và nên thử gì cho phép model retry hoặc giải thích cho user.

Thành phần nào Anthropic phải đặt trần 25k token trong Claude Code vì dễ phình context nhất?

  • Tool results trả về
  • Tool definitions ban đầu
  • System prompt tool use
  • Thinking của mỗi lượt

Tool result (trang web, query lớn, log) nằm trong context tới hết hội thoại và được gửi lại mỗi vòng. Definitions và system prompt tool use cố định; thinking là output token nhưng không phải thứ bị đặt trần này.

Theo Anthropic, thay vì ba tool list_users, list_events, create_event, nên thiết kế thế nào?

  • Một tool schedule_event gộp
  • Ba tool có namespace
  • Một tool list_all chung
  • Bốn tool chi tiết

Gộp theo workflow: schedule_event tự tìm slot và đặt lịch. Namespace là nguyên tắc khác (phân biệt hệ thống), không thay thế việc gộp; list_all là unbounded result.

Hỏi tôi

Có bộ tool thật của team muốn tôi review theo bảng mục 5, hay muốn bàn "guard ở app vs guard ở prompt" cho hành động không hoàn tác — hỏi trong phiên /teach. Bài tiếp theo dự kiến: workflow vs agent — khi nào một vòng lặp tự do như bài này là đúng, khi nào một pipeline cố định rẻ hơn và tin cậy hơn.
