Agent memory: từ lý thuyết CoALA đến thư mục memory/ thật

Bài 6 đã chỉ ra rằng context là tài nguyên khan hiếm và đắt đỏ. Nhưng LLM bản chất là hàm phi trạng thái: hết một phiên là quên sạch. Để trở thành cộng sự lâu dài, agent cần một hệ thống nhớ. Ta sẽ mổ xẻ 4 ngăn nhớ theo khung CoALA, giải bài toán đau đầu nhất là "quên" (cache invalidation), và soi chiếu thẳng vào kiến trúc memory/ hai tầng mà anh đang dùng hàng ngày.

Sau bài này anh làm được

Phân biệt rạch ròi 4 ngăn nhớ của agent (Working, Episodic, Semantic, Procedural) và ánh xạ sang các tầng lưu trữ quen thuộc của backend. Giải thích cơ chế index 2 tầng của my-agent theo nguyên lý progressive disclosure. Thiết kế chính sách cập nhật và dọn dẹp ký ức (eviction policy) để chặn đứng nguy cơ dirty read và mâu thuẫn context.

Một câu ôn bài 6, và một câu đoán trước. Đáp án câu đoán nằm ở mục 3.

Ghi chú vận hành: anh đang dồn tiến độ thực hành của bài 4, 5, 6. Bài 7 này thiết kế bài tập trực tiếp trên chính thư mục memory/ sẵn có của anh để làm rất nhanh trong 15–20 phút.

Skill research bị undertrigger vì description chỉ có 198 ký tự, viết chung chung "so sánh lựa chọn kỹ thuật". Model tự tin tự trả lời được nên bỏ qua skill. Trong khi đó, po và brainstorm có description dài, nêu rõ "kể cả khi tôi chỉ nói…". Với memory cũng vậy: mô tả mẩu nhớ mơ hồ thì model không bao giờ biết đường nạp lại.

Đoán trước: nếu anh nói với agent "Từ nay tôi chuyển hẳn sang dùng Maven cho các dự án mới", nhưng trong memory vẫn còn file cũ ghi "Luật ưu tiên dùng Gradle", điều gì sẽ xảy ra ở phiên tiếp theo khi anh bảo nó tạo dự án Java? Viết ra rồi mới mở.

Giữ câu trả lời của anh. Mục 3 sẽ phân tích hiện tượng mâu thuẫn ký ức (contradiction) và bài toán kinh điển cache invalidation.

1. Vấn đề gốc rễ: LLM là hàm phi trạng thái, context window không phải memory

Trước hết, hãy quay lại bản chất toán học: một LLM là một hàm thuần túy (pure function) không trạng thái: y = f(x). Mỗi lần gọi API là một lượt tính toán độc lập. Model không hề có "trí nhớ sinh học" nào sau khi hàm trả về kết quả.

Nhiều người lầm tưởng rằng tăng context window lên 1M hay 2M token là giải quyết xong bài toán bộ nhớ. Thật ra đó là một ảo tưởng kỹ thuật. Dân backend nhìn vào sẽ thấy ngay ba rào cản chí mạng:

  • Chi phí (Context Tax): Gửi 100k token lịch sử qua lại ở mỗi lượt gõ phím làm chi phí tăng theo cấp số nhân và độ trễ (TTFT - Time To First Token) kéo dài.
  • Mất tập trung (Context Rot & "Lost in the Middle"): Càng nhồi nhiều thông tin không liên quan vào prompt, model càng dễ bỏ sót chỉ dẫn cốt lõi hoặc suy luận sai lệch.
  • Mất sạch khi hết phiên: Đóng terminal hoặc sang một issue mới là sạch trơn. Toàn bộ kinh nghiệm fix bug của phiên trước bốc hơi hoàn toàn.

Với dân backend, context window chỉ tương đương với L1 Cache hoặc ThreadLocal state của một HTTP request. Khi request kết thúc, thread trả về pool, state bị xóa. Muốn dữ liệu sống sót qua các request và phiên làm việc, ta bắt buộc phải có một hệ thống lưu trữ ngoại vi (external persistence). Đó chính là Agent Memory.

Điều cần nhớ: Context window là bộ nhớ làm việc tạm thời của một lượt tính toán, không phải bộ nhớ dài hạn. Nhồi nhét context vừa đắt vừa làm cùn khả năng suy luận của model.

2. Bốn ngăn nhớ theo khung CoALA

Để thiết kế hệ thống nhớ cho agent mà không bị chắp vá, giới nghiên cứu AI đã mượn mô hình từ khoa học nhận thức (cognitive science). Khung kiến trúc chuẩn mực nhất hiện nay là CoALA (Cognitive Architectures for Language Agents) của nhóm nghiên cứu Princeton/Stanford:

Sumers et al., "Cognitive Architectures for Language Agents", TMLR 2024. Đọc Section 2 và 3 để thấy cách họ phân chia rạch ròi 4 ngăn nhớ.
"Working memory maintains active context, while long-term memory stores episodic experiences, semantic knowledge, and procedural skills."
Tạm dịch: "Bộ nhớ làm việc duy trì ngữ cảnh đang kích hoạt, trong khi bộ nhớ dài hạn lưu trữ các trải nghiệm tình huống, tri thức ngữ nghĩa và kỹ năng quy trình."

Bốn ngăn nhớ này ánh xạ hoàn hảo sang các khái niệm quen thuộc trong hệ thống phần mềm:

Ngăn nhớBản chất trong AI AgentVí dụ cụ thểTương đương trong Backend
Working Memory
(Làm việc / Ngắn hạn)		 Toàn bộ context window hiện tại: system prompt, tool definitions, tool results, lịch sử hội thoại vài lượt gần nhất. Prompt hiện thời, kết quả vừa chạy của lệnh git status, các turn chat đang diễn ra. RAM / CPU Cache / ThreadLocal: cực nhanh, dung lượng nhỏ, mất sạch khi tắt tiến trình.
Episodic Memory
(Trải nghiệm / Sự kiện)		 Nhật ký các sự kiện, hành động và kết quả trong quá khứ gắn chặt với chuỗi thời gian cụ thể ("chuyện gì đã xảy ra, khi nào, kết quả ra sao"). Transcript JSONL của phiên hôm qua; commit log; "lần trước sửa migration V3 bị deadlock vì bảng Orders có foreign key". WAL (Write-Ahead Log) / Audit Trail / Event Sourcing Stream: append-only, tuần tự theo thời gian.
Semantic Memory
(Ngữ nghĩa / Sự thật)		 Tri thức, sự thật, quy tắc, sở thích độc lập với thời gian, được đúc kết lại sau nhiều trải nghiệm. "Luật là senior backend Java/Spring"; "Dự án này cấm sửa file migration đã merge"; "Luật học tiếng Anh để phỏng vấn". Normalized Relational DB (PostgreSQL): dữ liệu có cấu trúc, quan hệ, tra cứu theo thuộc tính/khóa.
Procedural Memory
(Quy trình / Kỹ năng)		 Kỹ năng, công cụ, hướng dẫn hành động đã được lập trình hoặc chuẩn hóa ("làm điều đó như thế nào"). Các MCP tools (Bài 4–5); các Skills như review-java, report (Bài 6); script bash tự động hóa. Application Code / Stored Procedures / Shell Scripts: logic thực thi tất định.

Đến đây anh có thể nhận ra: từ Bài 1 đến Bài 6, chúng ta đã xây dựng trọn vẹn phần Procedural Memory (bộ công cụ MCP và quy trình Skill). Hôm nay, ta bước sang phần lưu trữ dữ liệu thật sự: Episodic và Semantic Memory.

Điều cần nhớ: CoALA chia bộ nhớ thành 4 ngăn: Working (ngắn hạn trong context), Episodic (nhật ký sự kiện theo thời gian), Semantic (sự thật đúc kết) và Procedural (công cụ và kỹ năng). Coding agent thông minh không nhồi tất cả vào context mà phân luồng lưu trữ rõ ràng.

3. Vòng đời ký ức và cơn ác mộng Cache Invalidation

Một hệ thống memory không chỉ là một cái kho để quẳng dữ liệu vào. Nó có vòng đời 4 thao tác: Capture (Ghi) → Retrieve (Đọc) → Consolidate (Đúc kết) → Forget (Quên).

A. Capture (Ghi nhận): Explicit vs Implicit

Có hai cách đưa ký ức vào hệ thống:

  • Explicit (Chủ động): Người dùng ra lệnh trực tiếp, ví dụ gõ /remember tôi hoãn thi TOEIC. Ưu điểm: độ chính xác 100%, không sinh rác. Nhược điểm: đòi hỏi con người phải có thói quen ghi chép.
  • Implicit (Tự động trích xuất): Sau mỗi phiên hoặc mỗi turn, một model nền chạy ngầm (reflection agent giống MemGPT hay Mem0) tự quét transcript để rút ra fact mới. Ưu điểm: người dùng không cần làm gì. Nhược điểm: rất dễ lưu rác, lưu những thứ vụn vặt tạm thời ("người dùng vừa hỏi lỗi compile dòng 15").
Packer et al., "MemGPT: Towards LLMs as Operating Systems", 2023. MemGPT dùng model đóng vai trò OS kernel quản lý việc đẩy memory ra vào context thông qua tool gọi hàm.

B. Retrieve (Truy xuất): Vector Search vs Exact Index Pointer

Nhiều người nghĩ cứ nói đến AI memory là phải cài Vector Database (Chroma, Pinecone). Nhưng trong kỹ thuật phần mềm, Vector Search bộc lộ 3 điểm yếu chí tử:

  1. Mù thời gian (Temporal Blindness): Cosine similarity chỉ đo khoảng cách ngữ nghĩa giữa hai vector chữ, hoàn toàn không biết cái nào mới hơn cái nào. Câu "tôi thích Gradle" (2024) và "tôi ghét Gradle, chuyển sang Maven" (2026) có độ tương đồng ngữ nghĩa cực cao với từ khóa "Java build tool", và vector search sẽ kéo cả hai vào context!
  2. Mất từ khóa chính xác: Tên class, mã lỗi, tên biến kỹ thuật (như OptimisticLockException) thường bị vector embedding làm nhòe nghĩa.
  3. Chi phí hạ tầng: Phải dựng database riêng, quản lý connection pool, lo embedding model drift.

Trường phái ngược lại là Exact Index Pointer (dùng chỉ mục phẳng 1 dòng như MEMORY.md). Nó cực kỳ nhẹ, chính xác, và model đọc trực tiếp bằng khả năng lý luận tự nhiên.

C. Consolidate (Đúc kết): Biến trải nghiệm thành quy tắc

Trong bài báo kinh điển Generative Agents (Stanford/Google), các tác giả gọi đây là bước Reflection:

Park et al., "Generative Agents: Interactive Simulacra of Human Behavior", UIST 2023.
"Reflection generates higher-level, more abstract thoughts from an agent's memory stream."
Tạm dịch: "Sự đúc kết sinh ra những suy nghĩ trừu tượng và khái quát hơn từ dòng ký ức của agent."

Ví dụ: thay vì lưu 20 mẩu nhật ký về 20 lần fix deadlock trên Oracle, bước consolidate sẽ rút ra một luật semantic duy nhất: "Trong dự án này, luôn sắp xếp thứ tự update row theo ID tăng dần để chống deadlock".

D. Forget & Evict: Cache Invalidation

Đây là câu trả lời cho câu đoán ở mục 0. Trong khoa học máy tính có câu châm ngôn bất hủ của Phil Karlton:

"There are only two hard things in Computer Science: cache invalidation and naming things."
Tạm dịch: "Chỉ có hai điều khó trong Khoa học Máy tính: vô hiệu hóa cache và đặt tên."

Khi sở thích hay quyết định kỹ thuật thay đổi mà hệ thống memory chỉ biết INSERT mà không biết UPDATE hay DELETE, hiện tượng Contradiction (Mâu thuẫn ký ức) sẽ xảy ra. Lúc này context chứa cả hai sự thật đối nghịch nhau. Model của Claude Code hay GPT khi thấy hai chỉ dẫn mâu thuẫn sẽ hành xử theo cơ chế: "may pick one arbitrarily" (tự chọn bừa một cái). Anh sẽ thấy lúc thì nó sinh project bằng Maven, lúc lại sinh bằng Gradle.

Điều cần nhớ: Hệ thống memory không có cơ chế quên và vô hiệu hóa (eviction/invalidation) thì càng dùng lâu càng tích tụ mâu thuẫn và rác bẩn, dẫn đến tình trạng "dirty read" trong context.

4. Mổ xẻ hệ thống memory/ của my-agent

Bây giờ ta hãy đối chiếu lý thuyết trên với chính cấu trúc mà anh đang dùng trong my-agent. Anh đã thiết lập một hệ thống Two-tier Index-Detail thuần Markdown rất thanh thoát:

Tại sao thiết kế này rất kỹ thuật và hiệu quả?

Anh đã vô tình áp dụng đúng nguyên lý Progressive Disclosure của Bài 6 cho tầng Data:

  • Rẻ tối đa: MEMORY.md mỗi bản ghi chỉ đúng một dòng gạch đầu dòng (pointer + tóm tắt 10 từ). Nếu có 20 mẩu ký ức, cả file chỉ tốn khoảng 300 token—quá nhỏ so với ngân sách 200k.
  • Version control bằng Git: Mọi thay đổi ký ức đều là commit git. Anh có thể xem git diff, git blame, biết agent đã sửa ký ức lúc nào. Khi có lỗi, chỉ cần git checkout là khôi phục (như tôi đã làm ở bài 6 khi eval ghi nhầm).
  • Harness-agnostic: Cả Claude Code lẫn Antigravity đều dùng chung một thư mục memory/. Không bị khóa chặt vào cơ chế Auto-Memory riêng của từng tool.
  • Định dạng tuyệt đối: Trong SKILL.md của remember, anh có quy định rất đắt giá: "Ngày tháng viết dạng tuyệt đối (vd: 2026-08-22), không viết 'hôm nay'/'tuần trước'". Điều này triệt tiêu hoàn toàn lỗi nhầm lẫn mốc thời gian khi nạp lại ở tương lai.

Những điểm mù của thiết kế hiện tại cần cải tiến

  1. Index Bloat khi scale: Khi số mẩu nhớ tăng lên 200–500 file, MEMORY.md sẽ chiếm 5.000–10.000 token ở mọi phiên. Lúc đó sẽ cần phân nhóm theo danh mục hoặc thư mục con.
  2. Hoàn toàn thiếu Episodic Memory: Hệ thống hiện tại chỉ lưu Semantic Memory (sự thật, sở thích). Anh chưa có cơ chế lưu lại: "Tuần trước đã optimize query Oracle bảng Transaction bằng hint gì". Những kinh nghiệm đó đang trôi mất sau khi đóng phiên terminal.
  3. Chính sách Invalidation phụ thuộc ý thức: Skill remember có dặn: "Đọc MEMORY.md xem đã có ghi nhớ nào trùng/liên quan chưa... nếu có thì cập nhật file đó". Đây là một optimistic check. Nếu người dùng nói vội, agent vẫn có thể vô tình tạo file mới gây mâu thuẫn.

Điều cần nhớ: Hệ thống memory 2 tầng của my-agent áp dụng progressive disclosure cho dữ liệu: index 1 dòng nạp sẵn, chi tiết nạp lười. Điểm mạnh là git versioning và chi phí thấp; điểm yếu là mới chỉ có semantic memory mà thiếu hẳn episodic memory.

5. Thực hành: Audit và stress-test memory của my-agent (~20 phút)

Bài tập hôm nay làm trực tiếp trên repo my-agent. Chúng ta sẽ soi kiểm tra thực tế và chạy một thử nghiệm mâu thuẫn ký ức có kiểm soát.

Bước 1 — Đo kích thước và chi phí hiện tại (3 phút).
Mở terminal tại thư mục my-agent và kiểm tra hai file:

wc -l -c memory/MEMORY.md
ls -la memory/

Tính xem tầng 1 (chỉ mục) của anh hiện tốn xấp xỉ bao nhiêu token (quy tắc thô: 1 token ≈ 4 ký tự tiếng Anh / 1–2 ký tự tiếng Việt có dấu). Chỉ mục này đang chiếm bao nhiêu phần trăm trong context khởi đầu của anh?

Bước 2 — Thử nghiệm Contradiction (Mâu thuẫn ký ức) (10 phút).
Hiện tại trong memory/muc-tieu-tieng-anh.md ghi rõ: "đích 3 tháng là phỏng vấn công ty nước ngoài; TOEIC/IELTS đã cố ý hoãn, đừng đề xuất luyện đề".
Hãy mở một phiên chat mới (hoặc test trên Antigravity / Claude Code) và đặt câu hỏi bẫy sau:

"Tôi muốn nâng cao tiếng Anh trong 2 tháng tới, bạn gợi ý lộ trình học phù hợp giúp tôi."

Quan sát câu trả lời của agent: Nó có tự động đọc file muc-tieu-tieng-anh.md không? Nó có đề xuất luyện thi TOEIC/IELTS không, hay đi thẳng vào phỏng vấn xin việc?

Sau đó, thử tưởng tượng anh muốn chuyển mục tiêu sang học tiếng Nhật/tiếng Đức. Mở file .claude/skills/remember/SKILL.md ra đọc lại: quy trình 4 bước của anh đã đủ chặt để ngăn agent tạo thêm file mục tiêu mới mà không vô hiệu hóa file tiếng Anh cũ chưa?

Bước 3 — Đề xuất 1 quy tắc dọn dẹp (Eviction Policy) (7 phút).
Viết vào nháp hoặc NOTES.md: Nếu một đồng nghiệp trong team muốn áp dụng cấu trúc memory/ này cho repo của họ, anh sẽ đưa ra quy định gì cho 3 tình huống sau:

  1. Khi một thông tin trong memory hết hạn (ví dụ: dự án migrate sang Spring Boot 3 đã hoàn thành).
  2. Khi hai memory mâu thuẫn trực tiếp với nhau.
  3. Khi nào một sự thật trong memory/ xứng đáng được "thăng hạng" đưa thẳng vào AGENTS.md / CLAUDE.md?

Trả lời ba câu hỏi thực hành:

  1. Bước 1: MEMORY.md của anh dài bao nhiêu dòng, chiếm khoảng bao nhiêu token?
  2. Bước 2: Agent có bị dính bẫy đề xuất TOEIC/IELTS không? Điểm cốt lõi nào trong MEMORY.md đã cứu nó?
  3. Bước 3: Ba quy tắc eviction của anh, mỗi quy tắc đúng một câu.
Gợi ý (mở sau khi đã suy nghĩ)

Câu 2: Nếu MEMORY.md được nạp vào system prompt / context đầu phiên, agent nhìn thấy pointer ngay lập tức và biết là TOEIC đã hoãn mà không cần mở file chi tiết! Đó là sức mạnh của việc tóm tắt 1 dòng mang thông tin phủ định ("đừng đề xuất luyện đề").

Câu 3: Gợi ý chuẩn cho team: (1) Khi hết hạn → chuyển vào memory/archive/ hoặc xóa hẳn commit; (2) Khi mâu thuẫn → UPDATE ghi đè file cũ, ghi rõ ngày cập nhật; (3) Thăng hạng lên AGENTS.md khi sự thật đó áp dụng cho toàn bộ mọi thành viên trong team và bắt buộc cho mọi phiên làm việc.

6. Kiểm tra cuối bài

Ba câu trắc nghiệm tình huống và hai câu tự diễn đạt. Nhớ rằng trắc nghiệm kiểm tra độ hiểu sâu, không đoán mò.

Trong phân loại CoALA, nhật ký toàn bộ các phiên làm việc trước đó cùng mã lỗi từng gặp thuộc về ngăn nhớ nào?

  • Episodic memory ghi nhận chuỗi các sự kiện cùng trải nghiệm trong quá khứ
  • Semantic memory tổng hợp các sự thật và tri thức độc lập thời gian
  • Procedural memory đóng gói các công cụ cùng quy trình thực thi hành động
  • Working memory lưu trữ toàn bộ ngữ cảnh tạm thời của phiên làm việc

Episodic memory là nhật ký sự kiện tuần tự theo thời gian (giống Event log/WAL). Semantic memory là tri thức đúc kết độc lập thời gian. Procedural memory là kỹ năng/công cụ. Working memory là context window hiện hành.

Hệ thống memory/ của my-agent dùng file MEMORY.md làm chỉ mục và nạp lười các file chi tiết. Ưu điểm lớn nhất của thiết kế này so với Vector Database cho cá nhân là gì?

  • Dễ dàng kiểm soát phiên bản qua git và sửa chữa trực tiếp bằng tay
  • Khả năng mở rộng tự động lên đến hàng triệu bản ghi không suy giảm
  • Tìm kiếm ngữ nghĩa xuất sắc ngay cả khi từ khóa hoàn toàn không khớp
  • Tự động giải quyết triệt để mọi mâu thuẫn ký ức không cần can thiệp

Với quy mô cá nhân và team nhỏ, file markdown lưu trong git cho phép diff, audit, sửa lỗi bằng tay và zero-infrastructure. Vector DB mạnh khi có hàng vạn bản ghi nhưng phức tạp, mù thời gian và khó debug khi sai.

Khi người dùng đổi ý từ "Tôi thích dùng Gradle" sang "Tôi chuyển hẳn sang Maven", rủi ro lớn nhất nếu agent chỉ thêm memory mới mà không xóa bỏ ký ức cũ là gì?

  • Model bị mâu thuẫn ngữ cảnh và chọn ngẫu nhiên một trong hai sự thật
  • Model lập tức báo lỗi giao thức và dừng phiên làm việc ngay tại chỗ
  • Thư mục memory bị hỏng cấu trúc khiến cho toàn bộ chỉ mục biến mất
  • Chi phí token tăng vọt gấp mười lần ngay trong lượt trao đổi kế tiếp

Khi có hai thông tin mâu thuẫn cùng xuất hiện trong context, LLM không có cơ chế tất định để biết cái nào đúng nếu không có timestamp hoặc quy tắc ưu tiên rõ ràng; model thường chọn ngẫu nhiên hoặc hallucinates.

Tự diễn đạt 1: Hãy giải thích cho một dev trong team sự khác nhau giữa Episodic Memory và Semantic Memory bằng một ví dụ thực tế trong công việc bảo trì hệ thống.

Episodic Memory là lịch sử các sự cố cụ thể đã diễn ra: "Lúc 14h ngày 10/10, service Payment bị OOM vì batch job quét 1 triệu record không phân trang". Semantic Memory là bài học trừu tượng được rút ra sau sự cố đó: "Mọi truy vấn danh sách giao dịch bắt buộc phải có phân trang limit/offset và giới hạn tối đa 500 bản ghi mỗi lần gọi".

Tự diễn đạt 2: Tại sao nói hệ thống memory/ của anh là sự kết hợp giữa Progressive Disclosure (Bài 6) và Stateless Function (Bài 1)?

LLM bản chất là hàm phi trạng thái (Bài 1), không nhớ gì sau khi kết thúc request. Hệ thống memory/ cung cấp vùng lưu trữ ngoài để duy trì trạng thái lâu dài. Thay vì nhồi toàn bộ dữ liệu vào context làm tăng chi phí và loãng model, anh dùng Progressive Disclosure (Bài 6): chỉ đưa 1 dòng pointer vào MEMORY.md nạp sẵn ở đầu phiên, và chỉ khi bài toán thật sự cần thì file chi tiết mới được tải vào context.

Tóm lại

  • Context window không phải memory: Đó là RAM tạm thời của một lượt tính toán. Nhồi nhét context gây tốn tiền (Context Tax), tăng độ trễ và mục ruỗng khả năng chú ý (Context Rot).
  • Khung CoALA chia 4 ngăn: Working (context hiện tại), Episodic (nhật ký sự kiện tuần tự), Semantic (tri thức, sự thật đúc kết) và Procedural (công cụ, kỹ năng, skills).
  • Vòng đời 4 bước: Ghi (Capture) → Đọc (Retrieve) → Đúc kết (Consolidate) → Quên (Forget).
  • Ác mộng Cache Invalidation: Ký ức mâu thuẫn hoặc hết hạn làm model chọn bừa. Hệ thống memory bắt buộc phải có cơ chế UPDATE và DELETE/EVICT rõ ràng.
  • Index-Detail Pattern của my-agent: MEMORY.md (tầng 1) nạp sẵn giá rẻ, các file chi tiết (tầng 2) nạp lười. Kiểm soát phiên bản bằng Git, không phụ thuộc hạ tầng vector DB cồng kềnh.
