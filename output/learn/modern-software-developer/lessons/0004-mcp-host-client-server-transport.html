MCP: host, client, server, transport

Ở bài 1, bộ tool của agent là thứ harness viết sẵn: Read, Edit, Bash. Muốn agent đọc Jira, query database dev hay gọi API nội bộ thì sao? Viết lại tool cho từng harness là cách cũ. MCP là cách mới: viết một lần, cắm vào harness nào cũng chạy. Hôm nay anh viết server đầu tiên và nhìn tận dây xem nó nói chuyện với Claude Code thế nào.

Sau bài này anh làm được

Viết một MCP server stdio khoảng 40 dòng, cắm vào Claude Code bằng claude mcp add, và đọc được chính xác các message JSON-RPC đi qua lại. Khi một tool MCP hỏng, anh biết lỗi nằm ở tầng nào: transport, protocol, hay trong code của tool.

0. Khởi động

Một câu ôn bài 1, và một câu đoán trước. Câu đoán sẽ có đáp án ở mục 4.

Câu 1 ôn "ai thực thi tool" (bài 1, và lỗ cũ ở LR-0004 của llm-foundation), lần này trong bối cảnh MCP. Câu đoán ôn lỗ "đường đi của lỗi trong harness" ở LR-0001.

Claude Code gọi tool mcp__learn__learning_progress. Đoạn code Python của tool đó thực sự chạy ở đâu?

  • Trong process server mà host khởi chạy
  • Trong model, ngay lúc sinh ra tool_use
  • Trên hạ tầng của Anthropic, cạnh model
  • Trong chính process Claude Code đang chạy

Vẫn là bài học của bài 1: model chỉ sinh ra yêu cầu tool_use, không chạy gì cả. Với MCP còn thêm một tầng: harness (Claude Code) không tự chạy code của tool mà chuyển yêu cầu sang một process riêng, chính là MCP server. Với transport stdio, process đó do Claude Code khởi chạy trên máy anh.

Đoán trước: tool trong server raise ValueError("Không có chủ đề 'x'. Các chủ đề hiện có: a, b, c"). Model nhận được gì? Viết câu trả lời của anh ra, rồi mới mở.

Chưa có đáp án ở đây. Giữ câu trả lời của anh, mục 4 sẽ cho thấy kết quả thật khi chạy trên máy.

1. MCP giải quyết vấn đề gì

Trước hết, thử nhớ lại thời trước JDBC. Mỗi ứng dụng muốn nói chuyện với Oracle, MySQL, PostgreSQL phải viết code riêng cho từng database. Có N ứng dụng và M database thì cần N×M bộ tích hợp. JDBC cắt bài toán đó: ứng dụng chỉ viết theo một API, còn mỗi vendor cung cấp một driver. N×M thành N+M.

Agent năm 2024 đúng ở tình trạng "trước JDBC". Claude Code, Cursor, Codex, agent tự viết: mỗi bên định nghĩa tool một kiểu. Muốn agent đọc Jira thì mỗi harness lại viết một tích hợp riêng. MCP (Model Context Protocol) là "JDBC cho context của agent": harness nói một giao thức, mỗi hệ thống bên ngoài cung cấp một server theo giao thức đó.

Anthropic công bố MCP cuối 2024. Ngày 2025-12-09, Anthropic tặng MCP cho Agentic AI Foundation thuộc Linux Foundation, đồng sáng lập với Block và OpenAI. Tức là giao thức không còn thuộc riêng một vendor nào.

Phép so sánh này hỏng ở hai chỗ, và cả hai đều quan trọng:

  • Server là một process riêng, không phải thư viện nạp vào cùng JVM như JDBC driver. Hai bên nói chuyện qua stdin/stdout hoặc HTTP. Vì thế server viết bằng Python vẫn cắm được vào harness viết bằng TypeScript.
  • Người dùng cuối của API là model, không phải lập trình viên. Description, tên tham số, message lỗi đều là thứ model đọc để quyết định bước tiếp theo. Bài 5 sẽ đi sâu vào điểm này.

Điều cần nhớ: MCP chuẩn hóa cách harness lấy tool và context từ bên ngoài, biến N×M tích hợp thành N+M. Khác JDBC ở chỗ server là process riêng và người đọc API là model.

2. Ba vai: host, client, server

Spec chia hệ thống thành ba vai. Đọc định nghĩa gốc:

MCP — Architecture overview.

MCP Host: The AI application that coordinates and manages one or multiple MCP clients.
MCP Client: A component that maintains a connection to an MCP server and obtains context from an MCP server for the MCP host to use.
MCP Server: A program that provides context to MCP clients.

Tạm dịch: Host là ứng dụng AI, điều phối và quản lý một hoặc nhiều client. Client là một thành phần giữ kết nối tới một server và lấy context từ server đó cho host dùng. Server là chương trình cung cấp context cho client.

Điểm dễ nhầm nhất là quan hệ giữa client và server. Nhiều người nghĩ "Claude Code là một client, nối tới nhiều server". Thật ra spec nói: "The MCP host accomplishes this by creating one MCP client for each MCP server" (tạm dịch: "host làm việc này bằng cách tạo một client cho mỗi server"). Mỗi client giữ một kết nối riêng tới đúng một server.

Vì sao lại một client cho mỗi server? Giống connection pool tách riêng cho từng datasource trong Spring: lỗi hay chậm ở một nguồn không kéo theo các nguồn khác. Mỗi kết nối có version và capability riêng (mục 4). Host cũng giữ quyền quyết định: server nào được tin, tool nào cần hỏi người dùng trước khi chạy.

Spec cũng chia giao thức thành hai tầng, giống cách anh tách HTTP khỏi TCP:

  • Data layer: nội dung message, dạng JSON-RPC 2.0. Gồm việc trao đổi version, capability, và các primitive ở mục 3.
  • Transport layer: message đi bằng đường nào (stdio hay HTTP), đóng khung ra sao, xác thực thế nào. Mục 5.

Điều cần nhớ: host là ứng dụng (Claude Code), client là kết nối bên trong host, server là chương trình cung cấp tool. Một client ứng với đúng một server. Giao thức có hai tầng: data (JSON-RPC) và transport.

3. Server cung cấp gì: ba primitive, ba người điều khiển

Server không chỉ cung cấp tool. Spec định nghĩa ba loại "primitive", và cái hay là mỗi loại do một bên khác nhau quyết định khi nào dùng:

PrimitiveLà gìAi quyết định dùngMethod
ToolsHàm có tác dụng: query, gọi API, ghi dữ liệuModel: "model-controlled" (tạm dịch: "do model điều khiển")tools/list, tools/call
ResourcesDữ liệu chỉ đọc có URI: file, schema DB, tài liệuỨng dụng: "application-driven" (tạm dịch: "do ứng dụng chủ động đưa vào")resources/list, resources/read
PromptsMẫu prompt có tham số, kiểu một slash commandNgười dùng: "user-controlled" (tạm dịch: "do người dùng chủ động chọn")prompts/list, prompts/get

Nguồn: spec 2026-07-28, các trang tools, resources, prompts.

Đến đây anh có thể tự hỏi: vậy schema của database dev nên là tool hay resource? Câu trả lời phụ thuộc vào việc ai nên quyết định đưa nó vào context. Nếu muốn model tự tra khi cần, dùng tool describe_table. Nếu anh muốn chủ động gắn schema vào cuộc hội thoại, dùng resource. Trên thực tế, đa số server hiện nay chỉ dùng tools, vì đó là thứ mọi host đều hỗ trợ tốt.

Chiều ngược lại cũng có: server có thể nhờ client làm việc. Đáng nhớ nhất là elicitation, khi server hỏi thêm thông tin từ người dùng qua client (ví dụ xác nhận "xóa 120 record, chắc chưa?"). Spec cấm dùng form elicitation để xin mật khẩu hay API key. Hai tính năng cũ là sampling (server nhờ client gọi LLM) và roots (giới hạn thư mục server được làm việc) đã bị đánh dấu deprecated ở bản 2026-07-28.

Elicitation; changelog 2026-07-28: "Deprecate the Roots, Sampling, and Logging features" (tạm dịch: "đánh dấu deprecated các tính năng Roots, Sampling và Logging").

Một chi tiết an toàn cần biết ngay: tool có thể kèm annotations như readOnlyHint hay destructiveHint. Đúng như tên gọi, đó chỉ là gợi ý. Spec nói thẳng: "clients MUST consider tool annotations to be untrusted unless they come from trusted servers" (tạm dịch: "client PHẢI coi annotations là không đáng tin, trừ khi đến từ server tin cậy"). Server của bên thứ ba tự khai readOnlyHint: true thì không có nghĩa nó chỉ đọc.

Điều cần nhớ: tools do model gọi, resources do ứng dụng đưa vào, prompts do người dùng chọn. Annotations chỉ là lời tự khai của server, không phải bảo đảm.

4. Nhìn tận dây: một phiên thật giữa Claude Code và server

Phần này không lấy từ tài liệu mà từ máy anh. Hôm nay tôi chạy server learn của mục 7 trong Claude Code 2.1.292, chèn tee vào stdin/stdout để ghi lại mọi message. Đây là thứ thật sự đi trên dây:

(1) Không còn handshake

Nếu anh đọc tutorial MCP trên mạng, gần như bài nào cũng bắt đầu bằng initialize → notifications/initialized, giống bắt tay TCP. Từ bản spec 2026-07-28 (bản hiện hành), bước đó bị bỏ: "Make MCP stateless: remove the initialize/notifications/initialized handshake. Every request now carries its protocol version and client capabilities in _meta" (tạm dịch: "làm MCP thành stateless: bỏ handshake initialize. Mỗi request tự mang version và capability của client trong trường _meta"). Một tools/call thật trông thế này:

Changelog 2026-07-28. Bản này cũng bỏ header Mcp-Session-Id của HTTP. Server viết cho bản cũ vẫn chạy: client hiện đại hỏi server/discover trước, không được thì lùi về initialize.
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{
  "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
           "io.modelcontextprotocol/clientCapabilities":{}},
  "name":"learning_progress","arguments":{"topic":"modern-software-developer"}}}

Với dân backend, đây là quyết định quen thuộc: bỏ sticky session để scale ngang. Mỗi request tự đủ thông tin, nên server HTTP chạy sau load balancer với 5 replica trên K8s không cần chia sẻ session. Cái giá phải trả: tool nào cần trạng thái (ví dụ một transaction nhiều bước) phải truyền handle tường minh trong tham số.

(2) Tool MCP được nạp trễ

Trong trace, model gọi ToolSearch trước rồi mới gọi được tool MCP. Đó là cơ chế tool search của Claude Code: "Only tool names and server instructions load at session start" (tạm dịch: "lúc bắt đầu phiên chỉ nạp tên tool và chỉ dẫn của server"). Lý do là chi phí context, đúng mạch bài 7 của llm-foundation. Anthropic ghi nhận agent nối tới hàng nghìn tool "need to process hundreds of thousands of tokens before reading a request" (tạm dịch: "phải xử lý hàng trăm nghìn token trước khi đọc tới yêu cầu").

Claude Code — MCP; Anthropic — Code execution with MCP (11/2025).

(3) Đáp án câu đoán: lỗi đi về đâu

Giờ quay lại câu đoán ở mục 0. Tôi chạy đúng tình huống đó với Python SDK 2.3.0:

Code trong toolModel nhận được
raise ValueError("Không có chủ đề 'x'. …")Error executing tool learning_progress: mất hết thông báo
raise ToolError("Không có chủ đề 'x'. …")Error executing tool learning_progress: Không có chủ đề 'x'. Các chủ đề hiện có: llm-foundation, …

SDK coi mọi exception không phải ToolError là crash, và giấu nội dung đi (có thể chứa stack trace hay dữ liệu nội bộ). Chỉ ToolError mới được coi là "lỗi anh đã lường trước" và đi tới model nguyên văn. Với bản có ToolError, trong trace Claude Code ở trên, model đọc danh sách chủ đề trong message lỗi rồi tự gọi lại với một chủ đề có thật. Đó chính là vòng tự sửa.

Câu đoán của anh có đúng không? Nếu anh đoán "model thấy nguyên message" thì sai cũng là bình thường, và đó chính là chỗ đáng học. Đây là lỗ ở bài 1 (except: continue nuốt lỗi), giờ xuất hiện ở tầng SDK.

Spec phân biệt hai loại lỗi, và anh cần giữ ranh giới này khi viết server:

MCP spec — Tools, mục Error Handling.
LoạiVí dụAi sửa được
Protocol error (JSON-RPC error)Thiếu clientCapabilities trong _meta → -32602Người viết client. "models are less likely to be able to fix" (tạm dịch: "model khó tự sửa")
Tool execution error (result có isError: true)Chủ đề không tồn tại, query sai cột, API trả 404Model. "actionable feedback that language models can use to self-correct" (tạm dịch: "phản hồi đủ cụ thể để model tự sửa và thử lại")

Điều cần nhớ: spec 2026-07-28 là stateless, mỗi request tự mang version. Tool MCP trong Claude Code được nạp trễ qua ToolSearch. Lỗi nghiệp vụ phải đi ra bằng tool execution error có message chỉ cách sửa; trong Python SDK 2.x, điều đó nghĩa là raise ToolError.

5. Transport: stdio hay Streamable HTTP

Spec hiện có hai transport. Hãy nhìn chúng như hai cách deploy một service:

stdioStreamable HTTP
Chạy ở đâuProcess con do host khởi chạy, trên máy người dùngService độc lập, một endpoint duy nhất nhận POST
Ai dùngMột người, một hostCả team, nhiều host cùng lúc
CredentialLấy từ biến môi trường. Spec: stdio "SHOULD NOT" (tạm dịch: "không nên") dùng phần authorizationOAuth 2.1, server đóng vai resource server
Giống vớiMột CLI tool anh tự chạyMột microservice trên K8s
Rủi ro hay gặpGhi rác ra stdoutQuên kiểm tra Origin, bind ra 0.0.0.0 khi chạy local

Nguồn: spec 2026-07-28, stdio, Streamable HTTP, Authorization. Transport cũ "HTTP+SSE" đã deprecated từ 2025-03-26; gặp tutorial dùng nó thì bỏ qua.

Với stdio, có một luật mà ai mới viết server cũng vấp: "The server MUST NOT write anything to its stdout that is not a valid MCP message" (tạm dịch: "server KHÔNG ĐƯỢC ghi ra stdout bất cứ thứ gì không phải message MCP hợp lệ"). Lý do: stdout chính là đường truyền. Một dòng print("debug") chen vào giữa luồng JSON-RPC thì client đọc phải rác. Log phải ghi ra stderr. Bên Java cũng vậy: tutorial Java chính thức dặn tắt console log của Spring Boot (logging.pattern.console=) khi chạy server stdio.

Điều cần nhớ: tool cá nhân dùng stdio, credential lấy từ env. Tool dùng chung cho team dùng Streamable HTTP, có OAuth, deploy như một service. Với stdio, stdout là của giao thức; log đi stderr.

6. MCP trong Claude Code: bốn điều cần biết

  1. Thêm server: claude mcp add <tên> -- <lệnh> [args…] cho stdio, claude mcp add --transport http <tên> <url> cho HTTP. Mọi thứ sau -- được chuyển nguyên cho server.
  2. Scope: local (mặc định, chỉ anh, chỉ project này), user (chỉ anh, mọi project), project (ghi vào .mcp.json ở root, commit lên git cho cả team; Claude Code hỏi xác nhận trước khi dùng server từ file này).
  3. Tên tool: mcp__<server>__<tool>. Đây cũng là tên anh dùng trong permission rule và matcher của hook (bài 9).
  4. Giới hạn output: cảnh báo khi một tool trả quá 10.000 token, cắt ở 25.000 token (chỉnh bằng MAX_MCP_OUTPUT_TOKENS). Tool trả nguyên một bảng 50.000 dòng là tool thiết kế sai, chuyện của bài 5.

Nguồn: Claude Code — MCP. Lệnh /mcp trong phiên cho xem trạng thái, bật/tắt và kết nối lại server.

Cuối cùng là cảnh báo của chính tài liệu Claude Code: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." (tạm dịch: "hãy chắc rằng anh tin server trước khi kết nối. Server lấy nội dung từ bên ngoài có thể mở đường cho prompt injection.") Một MCP server là code chạy với quyền của anh, và output của nó đi thẳng vào context của model. Bài 15 sẽ lập threat model cho chuyện này. Hôm nay chỉ cần nhớ: cài MCP server cũng cẩn thận như thêm một dependency vào pom.xml.

Điều cần nhớ: claude mcp add, ba scope, tên mcp__server__tool, giới hạn 25k token. MCP server là code có quyền của anh; chọn server như chọn dependency.

7. Thực hành: server learn (~20 phút)

Hôm nay anh hỏi tôi "đang học đến chương nào". Để trả lời, tôi phải chạy ba lệnh shell đọc thư mục output/learn/. Ta biến việc đó thành một tool. Nhỏ, nhưng là việc thật, và anh sẽ dùng nó.

Muốn làm cho việc ở công ty thay vì? Chọn một việc anh hay copy-paste vào agent: tra schema DB dev (chỉ đọc), gọi một API nội bộ, đọc trạng thái pipeline. Làm theo đúng các bước dưới đây. Không cần gửi code, chỉ cần trả lời các câu hỏi ở cuối.

Bước 1 — Viết server. Lưu ở đâu tùy anh, ví dụ ~/mcp/learn_server.py. Khối comment đầu file cho uv tự cài dependency.

# /// script
# requires-python = ">=3.10"
# dependencies = ["mcp>=2,<3"]
# ///
import re
import sys
from pathlib import Path

from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

LEARN_DIR = Path(sys.argv[1]).resolve()
mcp = MCPServer("learn")


@mcp.tool()
def learning_progress(topic: str) -> str:
    """Tiến độ của một chủ đề học: bài mới nhất đã giao và learning record mới nhất.

    topic: tên thư mục trong output/learn/, ví dụ "modern-software-developer".
    """
    ws = LEARN_DIR / topic
    if not ws.is_dir():
        topics = ", ".join(sorted(p.name for p in LEARN_DIR.iterdir()
                                  if p.is_dir() and not p.name.startswith(".")))
        raise ToolError(f"Không có chủ đề '{topic}'. Các chủ đề hiện có: {topics}")
    lessons = sorted((ws / "lessons").glob("*.html"))
    records = sorted((ws / "learning-records").glob("*.md"))
    last = records[-1].read_text(encoding="utf-8") if records else ""
    title = re.search(r"^#\s+(.+)$", last, re.M)
    return (f"Số bài đã giao: {len(lessons)}; bài mới nhất: {lessons[-1].name if lessons else '-'}\n"
            f"Learning record mới nhất: {records[-1].name if records else '-'}\n"
            f"Tóm tắt: {title.group(1) if title else '-'}")


if __name__ == "__main__":
    mcp.run()  # mặc định: stdio

Cảnh báo: Python SDK lên 2.0 ngày 2026-07-28 và đổi FastMCP thành MCPServer. Gần như mọi tutorial trên mạng (kể cả nhiều bài trên trang chính thức) vẫn dùng from mcp.server.fastmcp import FastMCP; với bản 2.x, dòng đó báo ModuleNotFoundError. Xem migration guide.

M='"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}'
{ echo '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{'"$M"'}}'
  echo '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{'"$M"',"name":"learning_progress","arguments":{"topic":"x"}}}'
  sleep 3; } | uv run -q ~/mcp/learn_server.py ~/workspace/my-agent/output/learn | jq -c .

Cách khác: MCP Inspector (npx @modelcontextprotocol/inspector uv run …) có giao diện web, nhưng cần Node ≥ 22.19; máy anh đang có Node 22.12.

Bước 3 — Cắm vào Claude Code (scope local, không ảnh hưởng ai):

cd ~/workspace/my-agent
claude mcp add learn -- uv run -q $HOME/mcp/learn_server.py $HOME/workspace/my-agent/output/learn
claude mcp list

Bước 4 — Dùng và đọc trace. Mở phiên mới, hỏi: "tôi đang học tới đâu ở chủ đề mcp?" (cố ý dùng tên sai). Sau đó lấy lại kỹ năng đọc trace của bài 1:

F=$(ls -t ~/.claude/projects/-Users-luatnq-workspace-my-agent/*.jsonl | head -1)
jq -c '.message.content[]? | select(.type=="tool_use") | {name, input}' "$F"

Bước 5 — Thí nghiệm. Đổi raise ToolError thành raise ValueError, gõ /mcp để kết nối lại server, rồi hỏi lại câu cũ trong một phiên mới. Đếm số lần model gọi tool trước khi trả lời, và xem câu trả lời cuối khác gì.

Trả lời bốn câu:

  1. Trong trace, trước lần gọi mcp__learn__learning_progress có lần gọi ToolSearch không? Vì sao?
  2. Bước 5: với ValueError, model gọi tool mấy lần, và có tìm ra chủ đề đúng không? Với ToolError thì sao?
  3. Khi tôi thử với tên sai "mcp-co-ban", model chọn llm-foundation là "gần nhất", dù bài MCP nằm ở modern-software-developer. Lỗi đó do model hay do thiết kế tool? Anh sẽ sửa gì trong tool? (Bài 5 sẽ dùng câu trả lời này.)
  4. Nếu muốn cả team dùng một server kiểu này cho dữ liệu chung (ví dụ tiến độ sprint), anh chọn transport nào, và credential đi đường nào?
Gợi ý (mở sau khi đã làm)

Câu 1. Có, vì tool search mặc định bật: lúc đầu model chỉ biết tên tool, chưa biết schema. Đó là cách giữ context nhỏ khi có nhiều server.

Câu 2. Tôi đã chạy thử mỗi bản 2 lần, cùng câu hỏi "chủ đề mcp". Bản ValueError: cả hai lần đều gọi tool 3 lần, xen giữa là một lần model bỏ tool, tự chạy ls bằng Bash để xem thư mục. Bản ToolError: một lần gọi 2 lần (lần 2 đúng), một lần gọi 1 lần rồi hỏi lại người dùng, và không lần nào phải dùng Bash. Mẫu nhỏ (n=2) nên chỉ coi là minh họa. Nhưng hãy để ý: agent production thường không có Bash, nên khi message lỗi bị nuốt, model chỉ còn cách đoán. Message lỗi là một phần của API mà model đọc.

Câu 3. Chủ yếu do tool. Description không nói mỗi chủ đề chứa gì, nên model chỉ đoán theo tên thư mục. Hướng sửa: thêm tool list_topics trả cả tên lẫn mô tả (lấy dòng đầu của MISSION.md), hoặc đưa mô tả vào chính message lỗi.

Câu 4. Streamable HTTP, deploy như một service, có OAuth hoặc ít nhất đứng sau gateway xác thực của công ty. Credential của nguồn dữ liệu nằm ở phía server, không nằm trên máy từng dev. Bài 20 (MCP portal) sẽ quay lại chuyện này ở quy mô team.

Muốn thử bản Java? Có Java SDK chính thức (io.modelcontextprotocol.sdk:mcp, Java 17+) và Spring AI MCP server starter với annotation @McpTool. Lưu ý: đến 2026-10-07 tôi chưa thấy bằng chứng Java SDK hỗ trợ spec 2026-07-28. Nó vẫn chạy được với Claude Code nhờ cơ chế lùi về initialize. Tôi chưa chạy thử bản Java trên máy anh.

8. Kiểm tra cuối bài

Bốn câu tình huống, và một câu tự diễn đạt. Câu tự diễn đạt quan trọng hơn: nó đo anh nhớ được, không chỉ nhận ra được.

Server stdio của anh chạy đúng khi test riêng từng hàm. Cắm vào Claude Code thì kết nối lỗi ngay. Anh vừa thêm vài dòng print() để debug. Nguyên nhân là gì?

  • Lệnh print ghi vào stdout, làm hỏng luồng JSON-RPC
  • Lệnh print làm server chậm, client hết thời gian
  • Claude Code chặn mọi server ghi log ra terminal
  • Lệnh print đổi encoding của stdin sang kiểu khác

Với stdio, stdout chính là đường truyền: spec cấm ghi ra stdout bất cứ thứ gì không phải message MCP. Log phải đi stderr. Server Spring Boot cũng gặp đúng chuyện này với console log.

Team 30 người muốn agent của mọi người cùng tra Jira nội bộ. Token Jira không được nằm trên máy từng dev. Chọn thiết kế nào?

  • Một server Streamable HTTP dùng chung, xác thực bằng OAuth
  • Mỗi dev tự chạy server stdio, token để trong env
  • Commit cả server stdio lẫn token chung vào file .mcp.json
  • Bỏ MCP, để agent gọi Jira bằng curl trong Bash

Stdio lấy credential từ môi trường của từng máy, nên token sẽ rải khắp team. Server HTTP dùng chung giữ credential ở phía server, và mỗi dev xác thực bằng danh tính của mình qua OAuth 2.1. Cách này cũng cho anh audit log tập trung, điều mà một team làm ngân hàng cần.

Một MCP server của bên thứ ba khai tool sync_data với readOnlyHint: true. Anh nên hiểu thế nào?

  • Chỉ là lời server tự khai, chưa đủ để tin
  • Claude Code đã kiểm chứng, tool chắc chắn chỉ đọc
  • Spec bắt server phải khai đúng, sai sẽ bị gỡ
  • Tool chạy trong sandbox, có ghi dữ liệu cũng ổn

Annotations là "hints". Spec yêu cầu client coi chúng là không đáng tin, trừ khi server đáng tin. Không ai kiểm chứng lời khai đó. Muốn chặn ghi thật sự thì dùng permission rule hoặc hook ở phía host (bài 9), hoặc chỉ cấp cho server một credential read-only.

Theo spec 2026-07-28, client mới kết nối tới server qua HTTP. Request tools/call đầu tiên cần gì đi trước?

  • Không cần gì, version nằm sẵn trong _meta của request
  • Gọi initialize một lần để server cấp Mcp-Session-Id cho client
  • Một lần tools/list để server biết client đã đọc schema
  • Mở sẵn kết nối GET SSE để nhận kết quả

Bản 2026-07-28 bỏ handshake initialize, bỏ Mcp-Session-Id và bỏ GET stream. Mỗi request tự mang version và capability trong _meta, nên request nào cũng có thể là request đầu tiên. server/discover có sẵn nếu client muốn hỏi trước, nhưng không bắt buộc. Các đáp án còn lại mô tả spec bản cũ.

Tự diễn đạt: giải thích cho một dev trong team, trong 3 câu, khác nhau giữa protocol error và tool execution error, và vì sao khác biệt đó quan trọng với agent. Viết ra trước, rồi mới mở.

Protocol error là lỗi ở tầng JSON-RPC: request sai cấu trúc, method không tồn tại, thiếu trường bắt buộc. Lỗi này dành cho người viết client sửa. Tool execution error là lỗi khi chạy tool (tham số nghiệp vụ sai, dữ liệu không có), trả về trong result với isError: true, và model đọc được. Nó quan trọng vì chỉ loại thứ hai mới đi vào vòng ReAct: message lỗi càng chỉ rõ cách sửa thì model càng tự sửa được ngay ở lần gọi sau.

So với câu của anh: có đủ ba ý "ai sửa", "nằm ở đâu trong message", và "vì sao message phải chỉ cách sửa" không?

Tóm lại

  • MCP là "JDBC cho context của agent": N×M tích hợp thành N+M. Khác JDBC ở chỗ server là process riêng, và người đọc API là model.
  • Host / client / server: host là ứng dụng, mỗi server có một client riêng bên trong host.
  • Ba primitive: tools (model gọi), resources (ứng dụng đưa vào), prompts (người dùng chọn). Annotations chỉ là lời tự khai.
  • Spec 2026-07-28 là stateless: không còn initialize, không còn session; mỗi request mang version trong _meta.
  • Transport: stdio cho tool cá nhân (stdout là của giao thức), Streamable HTTP + OAuth cho tool dùng chung.
  • Lỗi nghiệp vụ phải tới được model: tool execution error có message chỉ cách sửa. Trong Python SDK 2.x là ToolError.

Bài 5 sẽ dùng lại chính server này. Ta sẽ review bộ tool của nó dưới góc "người dùng là model": đặt tên, description, kích thước output, message lỗi, và cách viết test cho tool.
