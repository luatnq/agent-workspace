Hooks: lint gate, test gate, guardrail

Ở Bài 8, ta đã biết AGENTS.md là hợp đồng chung cho cả team. Nhưng instruction file bản chất vẫn chỉ là lời dặn bằng văn bản: model có thể quên, có thể bỏ sót khi ngữ cảnh quá dài. Muốn biến quy ước thành luật sắt bất khả xâm phạm và tạo vòng lặp tự sửa lỗi (tight feedback loop), ta cần Hooks. Hôm nay ta sẽ gắn linter, test gate và chốt chặn an toàn trực tiếp vào vòng lặp thực thi của agent.

Sau bài này anh làm được

Phân biệt rạch ròi giữa hướng dẫn mềm (instruction) và cưỡng chế cứng (hook). Cấu hình các điểm neo vòng lặp (PreToolUse, PostToolUse) để chặn đứng hành vi nguy hiểm và tự động chạy test/linter sau mỗi lần sửa code. Thiết kế kịch bản hook đa nền tảng chạy được trên cả Claude Code lẫn Antigravity.

  • Làm cho hệ thống git bị xung đột mã nguồn liên tục khi merge nhánh

Tương tự, nếu anh viết vào AGENTS.md "nhớ chạy linter sau khi sửa code", model vẫn có thể quên. Thay vì viết văn xuôi, ta dùng Hook.

Giữ câu trả lời của anh. Mục 2 và 3 sẽ giải phẫu chi tiết cơ chế chặn đứng (abort) của PreToolUse.

1. Bản chất: Lời dặn bằng chữ vs Luật sắt bằng code

Trước hết, hãy so sánh hai cách tiếp cận quản trị kỹ thuật:

  • Instruction (AGENTS.md / CLAUDE.md): Là hướng dẫn mềm (soft guidelines). Harness nạp nó vào context như một đoạn text. Model cố gắng đọc hiểu và làm theo. Nhưng model là mạng xác suất: khi task phức tạp, context dài hoặc có xung đột, model hoàn toàn có thể "bỏ quên" luật.
  • Hook: Là rào chắn cứng (hard guardrail). Đây là code shell script hoặc binary thật do chính harness thực thi tại các thời điểm vòng lặp (lifecycle events). Model không hề biết trước hook sẽ chạy gì, và model không thể vượt rào (bypass) được hook.

Với dân backend, có một phép so sánh kinh điển:

Instruction giống như comment trong code: // Chú ý: bảng này không được phép xoá row. Developer đọc có thể làm theo, nhưng không gì ngăn cản một câu lệnh DELETE chạy thẳng vào DB.
Hook giống như Database Constraint (Foreign Key / NOT NULL / Trigger) hoặc Servlet Filter / Spring Interceptor: nếu vi phạm, harness quăng exception và chặn đứng request ngay tại cửa!

Tài liệu chính thức của Anthropic đúc kết nguyên tắc chuyển đổi này bằng một câu rất đắt giá:

Claude Code — Best practices, mục "Enforcing invariants".
"If you find yourself repeatedly reminding Claude about the same rule, consider moving it into a hook."
Tạm dịch: "Nếu anh thấy mình phải liên tục nhắc nhở Claude về cùng một quy tắc, hãy cân nhắc chuyển quy tắc đó sang hook."

Điều cần nhớ: Instruction file dựa vào trí nhớ và sự tập trung của model; Hook dựa vào cơ chế thực thi tất định của hệ điều hành. Luật nào bắt buộc 100% phải đúng thì đưa vào Hook.

2. Các điểm neo vòng lặp (Lifecycle Events)

Cả Claude Code và Antigravity đều cung cấp các điểm neo (lifecycle hooks) để xen code của anh vào giữa các bước thực thi của agent:

Claude Code Hooks và Antigravity Lifecycle Hooks. Hai hệ thống có cấu trúc matcher và lifecycle rất tương đồng.

A. PreToolUse: Chốt chặn an toàn (Guardrail Gate)

Chạy ngay trước khi tool thật sự được thực thi trên máy tính của anh.

  • Dữ liệu đầu vào: Harness truyền toàn bộ tham số mà model định gọi (tên file, nội dung chuẩn bị ghi, câu lệnh bash định chạy).
  • Quyền lực: Hook có quyền hủy bỏ (abort) lệnh gọi tool đó trước khi nó kịp chạm vào hệ điều hành.
  • Ứng dụng tiêu biểu:
    • Chặn sửa các file migration database đã commit (src/main/resources/db/migration/*.sql).
    • Chặn các lệnh bash nguy hiểm (rm -rf, git push --force, DROP TABLE).
    • Chặn sửa file cấu hình hạ tầng K8s production khi đang ở môi trường local.

B. PostToolUse: Vòng lặp phản hồi tự động (Verification Gate)

Chạy ngay sau khi tool thực thi xong trên đĩa.

  • Quyền lực: Hook chạy một lệnh kiểm tra (linter, unit test, format code). Nếu kiểm tra thất bại, hook trả về lỗi. Harness sẽ tự động lấy toàn bộ thông báo lỗi đó nhồi vào context của lượt chat tiếp theo.
  • Ứng dụng tiêu biểu:
    • Lint Gate: Sau khi agent sửa file Java, tự động chạy ./gradlew spotlessApply. Nếu code sai convention, spotless tự format lại hoặc báo lỗi.
    • Test Gate: Sau khi sửa file trong `service/`, tự động chạy nhanh unit test của class đó (`./gradlew test --tests "*UnitTest"`). Nếu gãy test, lỗi compiler/assertion được ném thẳng vào mặt model để nó tự fix ngay trong phiên!

Điều cần nhớ: PreToolUse là người gác cổng bảo vệ an toàn (chặn đứng trước khi hư hại xảy ra). PostToolUse là thanh tra chất lượng tự động (kiểm tra ngay sau khi sửa và trả feedback cho model tự sửa lỗi).

3. Cơ chế giao tiếp: Exit Code và Feedback Loop

Harness và Hook script nói chuyện với nhau như thế nào? Rất đơn giản và thanh thoát theo chuẩn POSIX Unix:

Tín hiệuÝ nghĩaHành động của Harness
Exit Code 0 Thành công / Cho phép Harness tiếp tục vòng lặp bình thường. Kết quả tool được trả về cho model.
Exit Code khác 0
(Thường là 1 hoặc 2)		 Thất bại / Chặn đứng - Với PreToolUse: Tool bị hủy bỏ hoàn toàn, không ghi file, không chạy lệnh.
- Với cả hai: Toàn bộ output in ra stderr hoặc stdout của hook sẽ được harness bắt lại và đưa vào context như một thông báo lỗi nghiêm trọng.

Đến đây anh có thể tự hỏi: nếu hook chạy test mà test mất 10 phút thì sao? Điểm mấu chốt là: Hook phải chạy cực nhanh (dưới 5–10 giây). Đừng chạy toàn bộ integration test suite trong hook. Hãy chỉ chạy: linter, syntax check, hoặc unit test của đúng class vừa sửa. Bộ test nặng để dành cho CI/CD pipeline.

Điều cần nhớ: Hook giao tiếp bằng exit code: 0 là đi tiếp, khác 0 là chặn lại. Text in ra stderr sẽ trở thành thông điệp hướng dẫn model tự sửa sai. Giữ hook chạy thật nhanh dưới vài giây.

4. Cấu hình thực tế trên Claude Code và Antigravity

Dù chạy trên harness nào, kiến trúc tốt nhất là: viết logic kiểm tra trong shell script riêng (Git-managed), còn file cấu hình của harness chỉ đóng vai trò khai báo liên kết.

A. Cấu hình trên Antigravity (`.agents/hooks.json`)

Antigravity sử dụng file [hooks.json](file:///Users/luatnq/.gemini/antigravity-cli/builtin/skills/agy-customizations/docs/hooks.md) đặt trong thư mục `.agents/`:

{
  "protect-migration": {
    "PreToolUse": [
      {
        "matcher": "replace_file_content",
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/hooks/guard-migration.sh",
            "timeout": 5
          }
        ]
      }
    ]
  },
  "java-lint-gate": {
    "PostToolUse": [
      {
        "matcher": "replace_file_content",
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/hooks/check-java.sh",
            "timeout": 15
          }
        ]
      }
    ]
  }
}

B. Cấu hình trên Claude Code (`.claude/config.json`)

Claude Code cho phép khai báo hook tương tự trong cấu hình dự án hoặc gắn kèm vào `SKILL.md`:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "command": "./scripts/hooks/guard-migration.sh"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit",
        "command": "./scripts/hooks/check-java.sh"
      }
    ]
  }
}

C. Viết script kiểm tra chuẩn (`guard-migration.sh`)

Script nhận thông tin file từ biến môi trường hoặc tham số và quyết định:

#!/usr/bin/env bash
# scripts/hooks/guard-migration.sh
set -euo pipefail

# Lấy đường dẫn file chuẩn bị sửa (tùy harness truyền qua arg hoặc env)
TARGET_FILE="${1:-${TOOL_INPUT_TARGET_FILE:-}}"

if [[ "$TARGET_FILE" =~ db/migration/V.*\.sql$ ]]; then
  # Kiểm tra xem file này đã có trên git origin/main chưa
  if git ls-tree -r origin/main --name-only 2>/dev/null | grep -q "$TARGET_FILE"; then
    echo "ERROR [GUARDRAIL]: File migration $TARGET_FILE đã merge vào main, CẤM SỬA!" >&2
    echo "Gợi ý: Hãy tạo một file migration mới (V...__ten_migration.sql) để thay đổi schema." >&2
    exit 1  # Chặn đứng tool!
  fi
fi

exit 0  # Hợp lệ, cho phép tiếp tục

Điều cần nhớ: Tách logic kiểm tra ra các script shell trong scripts/hooks/ để dùng chung cho mọi harness và có thể chạy thử trực tiếp trên terminal của developer.

5. Thực hành: Xây dựng Guardrail Script cho repo (~20 phút)

Bài tập hôm nay sẽ giúp anh tự tay viết và kiểm thử một hook chặn an toàn thực tế.

Bước 1 — Viết script bảo vệ file migration (8 phút).
Tạo một script shell nhỏ `scripts/hooks/guard-migration.sh` (hoặc viết vào nháp) kiểm tra quy tắc sau:

  1. Nếu file có chứa đường dẫn `db/migration/` và kết thúc bằng `.sql`.
  2. In ra thông báo lỗi rõ ràng bằng tiếng Việt kèm gợi ý cách giải quyết vào `stderr`.
  3. Trả về `exit 1` nếu vi phạm, `exit 0` nếu là file bình thường.

Bước 2 — Chạy thử nghiệm giả lập (Simulation) (7 phút).
Chạy thử script trực tiếp trên terminal với 2 trường hợp:

# Test trường hợp hợp lệ
./scripts/hooks/guard-migration.sh "src/main/java/com/bank/OrderService.java"
echo "Exit code: $?"  # Phải in ra 0

# Test trường hợp vi phạm
./scripts/hooks/guard-migration.sh "src/main/resources/db/migration/V1__init.sql"
echo "Exit code: $?"  # Phải in ra 1 và thấy thông báo lỗi

Bước 3 — Thiết kế Hook cho team (5 phút).
Trả lời ba câu hỏi thực hành:

  1. Bước 2: Script của anh khi vi phạm có in đúng thông báo lỗi ra stderr và trả về exit code 1 không?
  2. Trong dự án Spring Boot của team anh, ngoài việc chặn sửa migration, anh thấy PreToolUse nên dùng để chặn điều gì nữa (ví dụ: chặn sửa file pom.xml/build.gradle, chặn sửa secrets)?
  3. Nếu một dev đề xuất gắn lệnh `./gradlew test` (toàn bộ 1.000 test case mất 5 phút) vào PostToolUse sau mỗi lần sửa file, anh sẽ giải thích trade-off cho họ thế nào và đưa ra phương án tối ưu hơn ra sao?
Gợi ý (mở sau khi đã suy nghĩ)

Câu 3: Vòng lặp phản hồi của coding agent đòi hỏi tính tương tác cao. Nếu mỗi lượt Edit bắt model chờ 5 phút, phiên làm việc sẽ bị tê liệt hoàn toàn, chi phí timeout tăng vọt và developer mất kiên nhẫn. Phương án tối ưu: PostToolUse chỉ chạy linter/spotless hoặc test-compile (dưới 5 giây); còn suite test đầy đủ chỉ chạy ở bước cuối trước khi commit hoặc giao cho CI/CD pipeline.

6. Kiểm tra cuối bài

Ba câu trắc nghiệm tình huống và hai câu tự diễn đạt.

Sự khác biệt bản chất nhất giữa một quy tắc viết trong AGENTS.md và một quy tắc cài đặt qua Hook là gì?

  • AGENTS.md là chỉ dẫn ngữ cảnh còn Hook là cưỡng chế tất định của harness
  • AGENTS.md chỉ áp dụng cho kiểm thử còn Hook dùng cho toàn bộ dự án
  • Hook làm tăng chi phí token nhiều hơn hẳn so với việc ghi vào AGENTS.md
  • Hook chỉ chạy được ở máy chủ còn AGENTS.md áp dụng cho mọi máy trạm

AGENTS.md là context hướng dẫn mềm, model có thể quên hoặc bỏ sót khi ngữ cảnh quá tải. Hook là code thực thi cứng do chính harness chạy độc lập với model, đảm bảo tính tất định 100%.

Để ngăn chặn agent tự ý chỉnh sửa các file migration database nhạy cảm (db/migration/*.sql), điểm neo lifecycle nào là phù hợp nhất?

  • PreToolUse gắn với matcher của tool sửa file để chặn đứng trước khi ghi đĩa
  • PostToolUse để kiểm tra lại lịch sử thay đổi sau khi file đã lưu lại
  • Stop để gửi cảnh báo đến kênh slack của toàn team sau phiên làm việc
  • PreInvocation để nhắc nhở model không được chạm vào thư mục nhạy cảm dự án

PreToolUse can thiệp ngay trước khi tool thực thi, cho phép harness hủy bỏ thao tác ghi đĩa trước khi bất kỳ hư hại nào xảy ra. PostToolUse thì file đã bị sửa mất rồi.

Khi một script hook kiểm tra biên dịch (PostToolUse) phát hiện lỗi và trả về exit code khác 0, điều gì xảy ra tiếp theo trong vòng lặp của agent?

  • Harness đưa thông báo lỗi vào context để model tự nhận biết và sửa lại mã
  • Phiên làm việc ngắt kết nối ngay lập tức và toàn bộ tiến trình dừng lại
  • Model tự động hoàn tác toàn bộ thay đổi vừa thực hiện trên cây thư mục
  • Harness tự động kích hoạt lệnh git commit nhằm lưu trạng thái lỗi của dự án

Khi PostToolUse fail, harness thu thập stderr của script và đưa vào context như một phản hồi hệ thống ở lượt tiếp theo, giúp model tự sửa code mà không cần con người can thiệp.

Tự diễn đạt 1: Giải thích cho một thành viên trong team cơ chế hoạt động của một "Lint Gate" qua PostToolUse bằng thuật ngữ backend.

PostToolUse hoạt động như một Post-Handle Interceptor: sau khi agent gọi tool sửa file mã nguồn xong, harness lập tức kích hoạt linter script (như Spotless/Checkstyle). Nếu có lỗi vi phạm cú pháp hoặc format, script in lỗi ra stderr và exit 1. Harness biến thông điệp này thành exception ném ngược lại context của agent, buộc agent phải tiến hành lượt sửa thứ hai để khắc phục lỗi ngay tại chỗ.

Tự diễn đạt 2: Nối Bài 8 (Instruction) và Bài 9 (Hooks). Khi nào thì một quy định của team nên dừng ở AGENTS.md, và khi nào bắt buộc phải nâng cấp thành Hook?

Dừng ở AGENTS.md khi quy định mang tính ngữ nghĩa, phong cách thiết kế, hướng dẫn chọn thư viện hoặc cách tiếp cận (thứ model cần hiểu để suy luận). Nâng cấp thành Hook khi quy định là luật sắt về an toàn, tính toàn vẹn dữ liệu, hoặc kiểm tra cú pháp bắt buộc không được phép có ngoại lệ (chặn sửa migration đã merge, chặn commit secret, format code theo chuẩn team).

Tóm lại

  • Instruction vs Hook: Instruction là comment trong code; Hook là database constraint. Luật bất khả xâm phạm phải dùng Hook.
  • Hai điểm neo cốt lõi:
    • PreToolUse: Guardrail bảo vệ an toàn (chặn trước khi chạm đĩa).
    • PostToolUse: Verification gate (chạy test/linter và trả feedback cho model tự sửa).
  • Giao tiếp POSIX: Exit code 0 là hợp lệ; exit khác 0 là chặn lại. Text in ra stderr trở thành chỉ dẫn tự sửa lỗi cho agent.
  • Quy tắc thời gian: Hook phải chạy cực nhanh (dưới vài giây). Test nặng để dành cho bước commit hoặc CI/CD pipeline.
  • Mô hình script tách rời: Viết logic kiểm tra trong scripts/hooks/ để dùng chung cho cả Antigravity lẫn Claude Code.
