Bên trong một coding agent

Claude Code trông như một hệ thống phức tạp. Nhưng bài đọc Week 1 của CS146S cho thấy phần lõi của nó chỉ cần 192 dòng Python. Bài này mở cái lõi đó ra. Sau đó ta xem Claude Code đắp thêm những gì lên trên, và vì sao phải đắp.

Sau bài này anh làm được

Mở transcript của một phiên Claude Code thật và đọc hiểu nó: bước nào agent đang tìm hiểu, bước nào đang sửa, bước nào đang kiểm tra lại, và nó phản ứng ra sao khi tool báo lỗi. Giải thích được vì sao lệnh Edit của Claude Code khó tính như vậy.

0. Khởi động — ôn lại hai ý cũ

Trước khi vào bài mới, ta gợi lại hai điều anh đã học. Cả hai sẽ được dùng ngay trong bài này. Đừng lo nếu không nhớ chắc: cố nhớ lại rồi mới chọn, chính lúc cố nhớ là lúc kiến thức được củng cố.

Câu 1 ôn bài 3 llm-foundation, đúng chỗ anh từng sai ở LR-0004. Câu 2 ôn bài 7.

Trong agent 192 dòng, khi model "gọi" read_file, thứ gì thực sự mở file trên đĩa?

  • Vòng lặp Python của harness
  • Model đọc thẳng ổ đĩa
  • Server OpenAI mở hộ file
  • Tokenizer nạp file vào prompt

Model chỉ viết ra một dòng chữ nói rằng nó muốn đọc file. Người thật sự mở file là hàm read_file_tool chạy trên máy anh. Kết quả được dán ngược vào hội thoại cho model đọc. Ở bản 192 dòng điều này còn lộ rõ hơn ở Claude Code: "tool call" chỉ là một dòng text tool: read_file({...}), và code Python tự tách dòng đó ra.

Agent SDK có option excludeDynamicSections: chuyển phần context đổi theo từng phiên (thư mục làm việc, git, ngày) ra khỏi system prompt, xuống user message đầu tiên. Lợi ích chính là gì?

  • Nhiều phiên chung được prefix cache
  • Model tuân thủ system prompt hơn
  • Giảm tổng số token mỗi request
  • Tránh lộ đường dẫn cho model

Cache khớp theo phần đầu (prefix) của request, theo thứ tự tools → system → messages. Chỉ cần một ký tự trong system prompt khác đi, ví dụ đường dẫn hay ngày, là mọi thứ phía sau mất cache. Dời phần hay đổi xuống dưới thì system prompt giống hệt nhau giữa các phiên, nên các phiên dùng chung được cache. Tổng số token không đổi, model vẫn thấy đường dẫn. (Agent SDK — Modifying system prompts)

1. Model và harness: người nghĩ và người làm

Hãy hình dung một chuyên gia tư vấn qua điện thoại. Ông ấy rất giỏi nhưng không chạm được vào máy của anh. Ông nói: "mở file OrderService.java đọc tôi nghe". Anh mở, đọc lại. Ông nói tiếp: "sửa dòng này thành thế này". Anh sửa, rồi báo lại kết quả. Cứ thế cho tới khi xong việc.

Trong coding agent, model là ông chuyên gia: chỉ nghĩ và nói, tức là sinh ra text. Harness là người ngồi ở bàn phím: làm theo lời model, rồi đọc lại kết quả cho model nghe. Tài liệu chính thức gọi Claude Code đúng bằng tên đó, "agentic harness" (tạm dịch: "bộ khung giúp model hành động như agent").

How Claude Code works. Code 192 dòng: coding_agent_from_scratch.py, kèm video bài giảng.

Phép so sánh này hỏng ở một chỗ. Người thật có thể từ chối một yêu cầu nguy hiểm theo cảm tính. Harness chỉ từ chối được nếu ai đó đã viết sẵn luật để từ chối. Đó là lý do mọi cơ chế an toàn (hỏi quyền, sandbox) đều nằm ở harness.

Trong bản 192 dòng, harness chỉ là hai vòng lặp lồng nhau. Vòng ngoài chờ anh gõ yêu cầu. Vòng trong gửi hội thoại cho model. Nếu model xin dùng tool thì harness chạy tool, dán kết quả vào hội thoại rồi hỏi model tiếp. Nếu model không xin tool nữa thì harness in câu trả lời và quay ra chờ anh.

Nhiều người nghĩ "tool calling" là một năng lực đặc biệt nằm sâu bên trong model. Bản 192 dòng cho thấy điều ngược lại. Nó không dùng tính năng function calling của API. System prompt chỉ liệt kê tên và mô tả các hàm, rồi dặn model: muốn dùng tool thì viết đúng một dòng dạng tool: TOOL_NAME({json}). Code Python tìm dòng đó và tách ra. Nói đơn giản: tool calling chỉ là một quy ước viết text mà hai bên đã thỏa thuận. Function calling của API chỉ làm cho quy ước ấy chặt chẽ hơn.

Điều cần nhớ: model chỉ sinh text; harness làm mọi việc còn lại. Khi agent làm sai, hãy hỏi lỗi nằm ở phía nào: model nghĩ sai, hay harness thiếu một lớp chặn.

2. Bộ tool tối thiểu, và mảnh còn thiếu

Trước khi đọc tiếp, thử đoán: một coding agent cần tối thiểu những việc gì? Hãy nghĩ tới lúc chính anh sửa một bug.

Anh sẽ làm ba việc: tìm hiểu (đọc code, grep), sửa, rồi kiểm tra lại (build, chạy test). Claude Code mô tả vòng lặp của nó đúng như vậy: "gather context, take action, and verify results" (tạm dịch: "thu thập context, hành động, rồi kiểm chứng kết quả"). Giờ đặt hai agent cạnh nhau:

Bản 192 dòng thiếu hẳn bước cuối. Giống một developer sửa code xong rồi push luôn, không build lần nào. Model sẽ báo "xong" chỉ dựa trên niềm tin của nó. Vì vậy bash là tool đáng giá nhất: nó thay câu "tôi nghĩ là đúng" bằng câu "compiler và test nói là đúng".

Nghe thì tưởng agent càng nhiều tool càng mạnh. Thực tế không hẳn. Khi làm SWE-bench, Anthropic chỉ cho model hai tool, bash và edit, mà vẫn đạt 49% SWE-bench Verified với Claude 3.5 Sonnet. Công sức dồn vào việc làm cho từng tool thật chắc. Ví dụ: họ thấy model hay nhầm đường dẫn tương đối sau khi đã cd sang thư mục khác, nên bắt tool chỉ nhận đường dẫn tuyệt đối.

Điều cần nhớ: đủ ba pha tìm hiểu, sửa, kiểm tra quan trọng hơn có nhiều tool. Thiếu pha kiểm tra thì agent chỉ còn biết đoán.

3. Vì sao sửa file bằng "thay chuỗi"

Giả sử cần sửa đúng một dòng trong một file Java 400 dòng. Model phải "nói" cho harness biết thay đổi đó. Có ba cách nói:

  1. Viết lại cả file với dòng đã sửa.
  2. Chỉ số dòng: "dòng 212 đổi thành…".
  3. Trích đoạn cũ và đưa đoạn mới: "đoạn này… đổi thành đoạn này…". Cách này gọi là str_replace. Nó giống một comment trong code review: dán đúng mấy dòng cần sửa, kèm bản sửa.

Cách 1 dễ hiểu nhất nhưng rất tốn. Model phải viết lại cả 400 dòng, mà output token đắt gấp 5 lần input (bài 1). Hình dưới vẽ đúng tỉ lệ:

Cách 2 thì rẻ. Nhưng model rất kém khi làm việc với số dòng. Nhóm Aider đo được rằng bỏ số dòng đi là một trong những thay đổi giúp ích nhiều nhất. Họ viết thẳng: "GPT is terrible at working with source code line numbers" (tạm dịch: "GPT làm việc với số dòng trong source code rất tệ"). Anh cũng từng gặp chuyện tương tự: một patch ghi theo số dòng sẽ trượt ngay khi ai đó chèn thêm một dòng ở phía trên.

Aider — Unified diffs; Anthropic — Text editor tool. OpenAI dùng định dạng riêng là apply_patch, nhưng cũng không dùng số dòng mà neo bằng 3 dòng context (GPT-4.1 prompting guide).

Cách 3 vừa rẻ vừa bền. Nó xác định chỗ cần sửa bằng chính nội dung code, không cần số dòng. Anthropic kết luận họ đạt "highest reliability with string replacement" (tạm dịch: "sửa bằng thay chuỗi cho độ tin cậy cao nhất").

Ba điều kiện của Edit, nhìn bằng mắt người làm database

Thay chuỗi cũng có cách hỏng riêng. Anh sẽ thấy chúng quen thuộc nếu nghĩ Edit giống một câu UPDATE … WHERE …. Chuỗi cũ (old_string) đóng vai trò mệnh đề WHERE. Claude Code đặt ba điều kiện, mỗi điều kiện chặn một cách hỏng:

Hãy để ý hàng cuối. Một câu UPDATE không có khóa duy nhất sẽ âm thầm sửa sai row. Bản 192 dòng làm đúng điều đó với code.

Còn một điểm tinh tế. Khi một điều kiện bị vi phạm, harness không tự đoán thay model. Nó trả lỗi về, và model tự sửa cách gọi ở lượt sau. Nghĩa là thông báo lỗi của tool cũng là một phần của vòng phản hồi. Thông báo càng chỉ rõ cách sửa thì agent càng tự gỡ được. Mẫu lỗi Anthropic đề xuất là "Found 3 matches… Please provide more context to make a unique match." (tạm dịch: "Tìm thấy 3 chỗ khớp… Hãy thêm context để chỉ khớp đúng một chỗ.")

Điều cần nhớ: Edit = UPDATE có optimistic locking và bắt buộc trúng đúng một row. Mỗi lần vi phạm, lỗi được trả về để model tự sửa, chứ harness không đoán hộ.

4. Thực hành trên máy thật (~15 phút)

Phần này là chỗ kiến thức biến thành kỹ năng. Đừng mở gợi ý sớm: phải tự vật lộn một chút thì mới nhớ lâu.

4a. Đọc trace của một phiên Claude Code

Claude Code lưu mỗi phiên thành một file JSONL trong ~/.claude/projects/<đường-dẫn-repo>/. Mỗi dòng là một message: model nói gì, gọi tool nào, tool trả về gì. Hãy chọn một phiên có sửa code trong repo công việc (không phải phiên học bài này), rồi chạy:

# 1. Chọn phiên: liệt kê project, rồi lấy phiên mới nhất của repo công việc
ls ~/.claude/projects/
F=$(ls -t ~/.claude/projects/<thư-mục-repo>/*.jsonl | head -1)

# 2. Đếm tool theo loại
jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="tool_use") | .name' "$F" | sort | uniq -c | sort -rn

# 3. Xem trình tự tool call (tên + đối số chính)
jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="tool_use")
  | .name + "  " + ((.input.file_path // .input.command // .input.pattern // "") | tostring | .[0:70] | gsub("\n";" "))' "$F" | head -60

# 4. Các tool_result bị lỗi
jq -r 'select(.type=="user") | .message.content[]? | select(.type=="tool_result" and .is_error==true)
  | (.content | tostring | .[0:160])' "$F"

Viết ra câu trả lời cho bốn câu hỏi, rồi mới mở phần gợi ý:

  1. Xếp các tool call vào ba nhóm: tìm hiểu, sửa, kiểm tra. Mỗi nhóm chiếm bao nhiêu? Lệnh Bash nào là kiểm tra (build, test), lệnh nào là tìm hiểu (cat, rg, git log)?
  2. Trước mỗi lần Edit, agent có đọc file đó chưa (bằng Read, hoặc cat/sed -n)?
  3. Chọn một tool_result bị lỗi. Ở lần gọi tool ngay sau, model đổi cách làm hay lặp lại y hệt?
  4. Trước khi báo xong, phiên đó có bước kiểm tra nào không? Nếu không, anh có tin kết quả không?
Gợi ý đọc kết quả (mở sau khi đã tự trả lời)

Câu 1. Một phiên khỏe thường tìm hiểu nhiều hơn sửa khá rõ. Nếu sửa chiếm phần lớn mà gần như không có kiểm tra, agent đang "sửa mò". Bash làm được nhiều việc, nên phải nhìn vào lệnh cụ thể mới biết nó thuộc nhóm nào.

Câu 2. Harness bắt buộc điều này, nên gần như luôn là có. Để ý thêm: cat/sed -n/grep trên một file (không pipe) cũng được tính là đã đọc.

Câu 3. Đây là câu đáng giá nhất. Lỗi có thông báo rõ (ví dụ old_string không khớp) thường được sửa ngay ở lượt sau. Lỗi mơ hồ (timeout, lỗi không rõ nguyên nhân) hay khiến model lặp lại y hệt. Chất lượng thông báo lỗi quyết định agent có tự gỡ được hay không. Bài 5 (thiết kế tool) sẽ quay lại điểm này.

Câu 4. Nếu phiên không có bước kiểm tra, đó là tín hiệu nên thêm một hook chạy test sau mỗi lần Edit (bài 9), hoặc một dòng trong CLAUDE.md yêu cầu kiểm tra trước khi báo xong (bài 8).

4b. Bắt lỗi bản 192 dòng

Giờ anh đóng vai reviewer. Mở coding_agent_from_scratch.py, đọc hai hàm run_coding_agent_loop và extract_tool_invocations (khoảng 60 dòng). Tìm ít nhất 4 cách agent này sẽ hỏng khi chạy trên một repo Java thật, mỗi cách viết một câu. Viết xong rồi mới mở đáp án.

Đáp án: 5 lỗ và lớp bảo vệ tương ứng trong Claude Code
  1. Vòng trong không có giới hạn. Model cứ gọi tool mãi thì chương trình chạy mãi và đốt token mãi, giống một vòng retry không có max attempts. Harness production có giới hạn số lượt, budget và nút ngắt.
  2. Tool call sai format bị bỏ qua mà không báo gì. extract_tool_invocations bắt mọi exception rồi continue. Nếu model viết JSON bằng nháy đơn, danh sách tool call rỗng, và harness tưởng đó là câu trả lời cuối. Dùng function calling của API sẽ loại bỏ hẳn loại lỗi này.
  3. Tên tool lạ làm sập cả chương trình. TOOL_REGISTRY[name] ném KeyError, thay vì trả lỗi về cho model tự sửa.
  4. Edit không bắt đọc trước và không kiểm tra tính duy nhất, lại luôn thay chỗ đầu tiên. Ví dụ: sửa return null; trong một class có năm chỗ như vậy.
  5. Không có bash, nên không kiểm tra được. Không compile, không chạy test. Cũng không có quyền hay sandbox: edit_file với old_str rỗng ghi đè bất kỳ file nào mà không hỏi ai.

Lỗ thứ 6, nếu anh thấy: hội thoại chỉ dài thêm mãi, không có bước tóm tắt (compaction). Trên repo lớn, nó sẽ sớm chạm giới hạn context window (bài 7 llm-foundation).

Tìm được 3–4 lỗ ở lần đầu là tốt rồi. Lỗ nào anh bỏ sót chính là thứ đáng nhớ nhất của bài này.

5. Kiểm tra cuối bài

Bốn câu, mỗi câu ứng với một phần của bài. Chọn theo suy luận, đừng chọn theo cảm giác quen mắt.

Edit báo lỗi "Found 3 matches of the string" (tìm thấy 3 chỗ khớp với chuỗi), trong khi anh chỉ muốn sửa một chỗ. Agent nên làm gì tiếp?

  • Thêm dòng xung quanh cho duy nhất
  • Ghi đè lại toàn bộ file mới
  • Cứ sửa cả ba chỗ một lượt
  • Dùng số dòng để chỉ vị trí

Giống như thêm điều kiện vào WHERE cho tới khi chỉ trúng một row: kéo dài old_string thêm vài dòng xung quanh cho tới khi nó chỉ khớp đúng chỗ cần sửa. Ghi đè cả file tốn khoảng 67 lần output token (Hình 2). replace_all chỉ dùng khi thật sự muốn sửa mọi chỗ. Còn số dòng thì model xử lý kém (Aider).

Vì sao agent 192 dòng dễ báo "xong" trong khi code vẫn còn lỗi compile?

  • Không có tool chạy lệnh để verify
  • Model GPT kém hơn Claude về code
  • Giao thức tool dạng text thiếu chuẩn
  • System prompt quá ngắn và chung chung

Không có bash thì không compile, không chạy test được, nên vòng lặp thiếu hẳn bước kiểm tra. Đổi model hay viết prompt dài hơn cũng không bù được, vì model không có cách nào nhìn thấy kết quả thật.

Model trả về tool: edit_file({'path': 'A.java', ...}), tức là JSON dùng nháy đơn. Agent 192 dòng sẽ làm gì?

  • Coi đó là câu trả lời cuối
  • Báo lỗi format để model tự sửa
  • Crash ngay vì không parse được JSON
  • Tự sửa nháy đơn rồi chạy tiếp

raw_decode ném exception, bị except: continue nuốt mất, nên danh sách tool call rỗng. Vòng trong hiểu là model không gọi tool nữa: in response ra rồi thoát. File không được sửa, còn người dùng thấy một dòng "tool: ..." và tưởng đã xong. Lỗi im lặng là loại lỗi tệ nhất trong một harness, vì không ai biết để sửa.

Claude Code bắt buộc Read trước Edit. Điều kiện này chủ yếu chặn failure nào?

  • Sửa theo nội dung đoán hoặc cũ
  • Tốn quá nhiều output token khi sửa
  • Hai agent cùng lúc ghi một file
  • Model không biết file có tồn tại

Không đọc file mà vẫn viết ra được old_string nghĩa là model đang dựa vào trí nhớ hoặc phỏng đoán, tức là hallucination ở dạng code (bài 2 llm-foundation). Giống optimistic locking: bắt đọc trước để old_string lấy từ nội dung thật, mới nhất, đang nằm trong context.

Tóm lại

  • Model nghĩ, harness làm. Model chỉ sinh text, mọi thao tác thật và mọi cơ chế an toàn nằm ở harness.
  • Ba pha: tìm hiểu, sửa, kiểm tra. Thiếu pha kiểm tra thì agent chỉ còn đoán; bash là tool đáng giá nhất.
  • Edit = UPDATE an toàn. Đọc trước, khớp chính xác, trúng đúng một chỗ. Sai thì trả lỗi rõ ràng để model tự sửa.

Bài 2 sẽ mở phần còn lại của harness: system prompt, nơi người ta "dạy" model cách dùng các tool này.
