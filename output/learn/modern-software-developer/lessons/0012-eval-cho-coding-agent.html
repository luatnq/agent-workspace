Eval cho coding agent: đo "có tốt hơn không"

Ở bài trước, ta đã audit codebase để đạt chuẩn Agent-Ready: viết AGENTS.md, thiết lập lệnh format tự động, gắn hook kiểm tra biên dịch. Nhưng làm thế nào anh chứng minh được với bản thân và ban giám đốc rằng agent thực sự làm việc tốt hơn, ít lỗi hơn và tiết kiệm tiền hơn trước? Trong kỹ nghệ phần mềm chuyên nghiệp, cảm giác chủ quan ("tôi thấy nó thông minh hơn") không có giá trị. Ta kết thúc Module 5 bằng công cụ sắc bén nhất của một kỹ sư trưởng: Evaluation (Eval) cho Coding Agent.

Sau bài này anh làm được

Phân biệt rạch ròi 3 tầng kiểm thử của agent: Unit test tool, Tool-level eval, và Agent-level eval. Thiết lập một bộ Internal Eval Set gồm 3–5 bài toán thực tế với cơ chế F2P (Fail-to-Pass) và P2P (Pass-to-Pass). Đo lường định lượng hiệu quả của instruction file và hook bằng A/B testing: so sánh tỷ lệ Pass Rate, số turns, thời gian chạy và chi phí token.

0. Khởi động

Một câu ôn bài 11 (củng cố tiêu chí Agent-Ready), và một câu đoán trước. Đáp án câu đoán nằm ở mục 1.

Bài 11 anh đã đạt 4/4 điểm. Câu ôn này củng cố đòn bẩy kỹ thuật quan trọng nhất trong vòng lặp của agent.

Ở bài 11, đâu là yếu tố kỹ thuật đem lại giá trị cao nhất cho vòng lặp phát triển của coding agent?

  • Có lệnh chạy kiểm thử đơn vị cục bộ nhanh chóng và công cụ định dạng tự động
  • Có tài liệu hướng dẫn nghiệp vụ dài hàng trăm trang lưu trữ trên hệ thống nội bộ
  • Có số lượng các lớp đối tượng kế thừa phức tạp trải dài qua nhiều tầng thư mục
  • Có cấu hình môi trường máy chủ phức tạp đòi hỏi phải kích hoạt thủ công bằng tay

Coding agent vận hành theo vòng lặp ReAct (Thought -> Action -> Observation). Việc có lệnh chạy unit test cục bộ siêu nhanh (<15s) và linter tự động sửa format cung cấp phản hồi tất định tức thì, giúp agent tự sửa sai mà không làm đứt gãy mạch suy luận.

Đoán trước: Nếu anh dùng một mô hình LLM khác (LLM-as-a-judge) để đọc đoạn git diff của agent và chấm điểm "code này có đúng không", so với việc chạy bộ unit test tự động (mvn test) xem có pass không, phương pháp nào là Evaluation Oracle chuẩn mực trong kỹ nghệ phần mềm? Viết ra rồi mới mở.

Chính là bộ unit test tự động! LLM-as-a-judge rất dễ bị ảo giác hoặc dễ dãi bỏ qua lỗi logic ngầm. Trong lập trình, "code pass toàn bộ assertions kiểm thử" là sự thật khách quan nhị phân (0 hoặc 1) duy nhất đáng tin cậy.

1. Vì sao Coding Agent Eval khác biệt 180 độ so với Chatbot Eval?

Trong các khóa học LLM truyền thống (như Bài 6 của `llm-foundation`), đánh giá mô hình thường xoay quanh bài toán Text Generation (RAG, tóm tắt, hội thoại):

  • Dùng độ đo tương đồng từ vựng: BLEU, ROUGE, BERTScore.
  • Dùng mô hình ngôn ngữ khác chấm điểm: LLM-as-a-judge (ví dụ: "Hãy chấm điểm câu trả lời này từ 1 đến 5 sao").

Nhưng đối với Autonomous Coding Agent, phương pháp đó hoàn toàn vô dụng!

Trong phát triển phần mềm, một đoạn code dù được LLM khen "rất sáng tạo, đúng chuẩn clean code" nhưng thiếu một dấu chấm phẩy hoặc sai tên biến thì vẫn là 0 điểm (build fail).
Bản chất của Software Eval

Lập trình là một miền bài toán tất định (deterministic domain). Nguồn chân lý tối thượng (Ground Truth / Evaluation Oracle) của chúng ta không phải là lời khen của một AI khác, mà là:
1. Compiler: Code có biên dịch thành công hay không?
2. Test Suite: Code có vượt qua toàn bộ các assert kiểm thử chức năng và hồi quy hay không?

2. Ba tầng kiểm thử trong Agentic Engineering

Để đánh giá một hệ sinh thái agent, ta chia làm 3 tầng độc lập, tương ứng với tháp kiểm thử truyền thống (Unit $\to$ Integration $\to$ E2E):

                      ┌────────────────────────────────────────┐
                      │        3. Agent-level Eval (E2E)       │  ◄── Giải quyết ticket Jira thật
                      │   (Multi-turn ReAct, Pass Rate, Tokens) │      (Đo lường hôm nay học)
                      └───────────────────┬────────────────────┘
                                          │
                                          ▼
                      ┌────────────────────────────────────────┐
                      │         2. Tool-level Eval             │  ◄── Model có chọn đúng tool không?
                      │   (Single-turn: Trigger Rate, Args)    │      (Đã học ở Bài 5)
                      └───────────────────┬────────────────────┘
                                          │
                                          ▼
                      ┌────────────────────────────────────────┐
                      │         1. Tool Unit Test              │  ◄── Code của tool có chạy đúng không?
                      │   (JUnit, Mockito, Pytest, Schema)     │      (Kiểm thử phần mềm truyền thống)
                      └────────────────────────────────────────┘
  • Tầng 1: Tool Unit Test: Đảm bảo mã nguồn của tool chạy ổn định. Ví dụ: Tool `grep_search` không văng lỗi NullPointer khi regex sai cú pháp; tool MCP trả về schema JSON hợp lệ.
  • Tầng 2: Tool-level Eval: Kiểm tra khả năng hiểu ý định người dùng của model ở một lượt chat (Single turn). Khi người dùng hỏi: "Tìm các class xử lý giao dịch quá hạn", model có biết gọi tool `grep_search` hay lại tự tiện bịa câu trả lời?
  • Tầng 3: Agent-level Eval (E2E): Đây là đỉnh cao của đánh giá: giao cho agent một bài toán hoàn chỉnh (ví dụ: một issue bug thật), cấp cho agent quyền chạy bash/edit file trong vòng lặp ReAct đa lượt, và kiểm tra xem agent có tự hoàn thành và pass test hay không.

3. Giải phẫu một Task trong Bộ Eval Nội Bộ (Internal Eval Set)

Trên thế giới có benchmark công khai nổi tiếng là **SWE-bench** (gồm hàng nghìn issues từ các repo Python mã nguồn mở). Tuy nhiên, đối với một ngân hàng hay doanh nghiệp sử dụng Java/Spring Boot, SWE-bench không giúp ích nhiều vì:

  1. Khác biệt về ngôn ngữ và công nghệ: SWE-bench chủ yếu là Python, trong khi doanh nghiệp dùng Java, Oracle, Kafka.
  2. Nguy cơ rò rỉ dữ liệu (Data Leakage): Các issue trên GitHub công khai có thể đã nằm trong tập dữ liệu pre-training của mô hình.
  3. Không phản ánh các thư viện nội bộ và quy ước nghiệp vụ độc quyền.

Vì vậy, giải pháp chuẩn mực của một Tech Lead là xây dựng một Internal Domain-Specific Eval Set tinh gọn (gồm 3–5 tasks cốt lõi). Mỗi task bao gồm 4 yếu tố kỹ thuật chuẩn mực:

Đây chính là tiêu chuẩn mà các công ty hàng đầu (Anthropic, Cognition/Devin) dùng để benchmark harness nội bộ.
Thành phầnÝ nghĩa kỹ thuậtVí dụ trong dự án Spring Boot
Task ID & Problem Statement Mô tả lỗi hoặc yêu cầu tính năng từ Jira issue gốc. Không được mách nước tên file hay cách sửa. BUG-102: Phí chuyển tiền ngoại tệ bị làm tròn xuống thay vì làm tròn lên khi số tiền nhỏ hơn 1 USD.
Base Commit (Git SHA) Commit trên nhánh git mà tại đó bug đang tồn tại. Agent sẽ bắt đầu làm việc từ commit này. git checkout 8f4a1c2 (trạng thái mã nguồn trước khi bug được fix).
Fail-to-Pass Test (F2P) Bài kiểm thử chứng minh: Bài test kiểm tra đúng ca lỗi bị báo cáo. Ở Base Commit, bài test này phải FAIL; sau khi agent sửa xong, nó phải PASS. FxTransferServiceTest.shouldRoundUpFeeWhenAmountIsFractional()
Pass-to-Pass Tests (P2P) Bài kiểm thử hồi quy: Toàn bộ các bài test cũ của hệ thống. Phải tiếp tục PASS sau khi agent sửa code (chứng minh agent không phá hỏng cái cũ). Toàn bộ 45 bài test khác trong FxTransferServiceTest.

4. Bộ chỉ số đo lường cốt lõi (Core Metrics)

Khi chạy benchmark tự động qua hàng loạt tasks, ta thu thập bảng số liệu sau:

Chỉ sốCách đoTại sao quan trọng với Tech Lead?
Pass Rate (%) $\frac{\text{Số task F2P chuyển sang PASS}}{\text{Tổng số task}} \times 100\%$ Chỉ số sống còn đo độ chính xác và khả năng giải quyết vấn đề của agent.
Turns to Solve Số lượt lặp lại vòng ReAct (Thought $\to$ Tool Call) Đo tính định hướng: agent đi thẳng vào file cần sửa hay loay hoay mở 30 files lung tung?
Token Consumption Tổng Input Tokens + Output Tokens Quyết định chi phí tiền điện toán ($). Khi có AGENTS.md chuẩn, lượng token thường giảm 40–60%.
Wall-clock Runtime Thời gian thực thi từ start đến finish (giây) Đo độ trễ trải nghiệm của kỹ sư: agent hoàn thành trong 2 phút hay bắt người dùng đợi 20 phút?
Tool Error Rate (%) $\frac{\text{Số lần tool call bị lỗi}}{\text{Tổng số lượt gọi tool}} \times 100\%$ Chỉ số phản ánh chất lượng tài liệu repo: tool error cao nghĩa là agent đang gõ sai lệnh bash hoặc gõ sai đường dẫn file.

5. Kịch bản A/B Test: Chứng minh giá trị của `AGENTS.md` & `Hooks`

Hãy xem một thử nghiệm thực tế (Experiment) chạy trên một bộ 5 tasks kiểm thử nội bộ:

┌──────────────────────────────────────────────┐       ┌──────────────────────────────────────────────┐
│        Baseline (Repo chưa tối ưu)           │       │        Treatment (Repo Agent-Ready)          │
├──────────────────────────────────────────────┤       ├──────────────────────────────────────────────┤
│ • Không có AGENTS.md                         │       │ • Có AGENTS.md chuẩn 80 dòng                 │
│ • Không có Hook kiểm tra biên dịch           │       │ • Có PostToolUse Hook kiểm tra biên dịch     │
│ • Agent phải tự mò mẫm lệnh build            │       │ • Có lệnh chạy fast unit test subset         │
├──────────────────────────────────────────────┤       ├──────────────────────────────────────────────┤
│ ❌ Pass Rate: 20% (1/5 tasks giải quyết xong)│  ==>  │ ✅ Pass Rate: 80% (4/5 tasks giải quyết xong)│
│ 📉 Turns trung bình: 26 lượt gọi tool        │       │ 📈 Turns trung bình: 8 lượt gọi tool         │
│ 💸 Tokens trung bình: 92.000 tokens / task   │       │ 💰 Tokens trung bình: 24.000 tokens / task   │
│ ⏱️ Thời gian trung bình: 14 phút / task      │       │ ⚡ Thời gian trung bình: 2,5 phút / task     │
│ 💥 Tool Error Rate: 34% (gõ sai lệnh bash)   │       │ 🛡️ Tool Error Rate: 3%                       │
└──────────────────────────────────────────────┘       └──────────────────────────────────────────────┘

Kết luận định lượng: Nhờ có AGENTS.md và Hook, chi phí token giảm 74%, thời gian chờ giảm 82%, và tỷ lệ giải quyết thành công tăng gấp 4 lần! Đây là bằng chứng số liệu không thể chối cãi để anh trình bày trong các buổi báo cáo quản lý.

6. Kiểm tra hiểu biết cuối bài

Tiêu chuẩn đánh giá (Evaluation Oracle) tin cậy và chuẩn mực nhất đối với một coding agent là gì?

  • Các bài kiểm thử tự động độc lập chạy pass hoàn toàn mà không có lỗi phát sinh
  • Lời nhận xét đánh giá cảm tính của một mô hình ngôn ngữ lớn khác trong hệ thống
  • Độ dài của đoạn văn bản giải thích mã nguồn do agent sinh ra sau mỗi lượt chạy
  • Số lượng các dòng chú thích được chèn thêm vào bên trong các tệp tin mã nguồn này

Trong kỹ nghệ phần mềm, code đúng hay sai là một giá trị nhị phân tất định. Không có thước đo nào đáng tin cậy hơn việc bộ unit/integration test tự động vượt qua 100% assertions. Sử dụng LLM-as-a-judge cho code rất dễ bị ảo giác và bỏ lọt lỗi logic ngầm.

Khi đánh giá hiệu quả của coding agent, tại sao chỉ số Token Cost và Số lượt Turn lại quan trọng ngang ngửa Pass Rate?

  • Phản ánh trực tiếp chi phí tài chính thực tế cùng độ trễ phản hồi của hệ thống
  • Cho biết máy chủ cơ sở dữ liệu có bị ngắt kết nối mạng bất ngờ hay không
  • Đảm bảo rằng toàn bộ các bài kiểm thử tự động đã được xóa bỏ hoàn toàn sạch
  • Ngăn chặn mô hình ngôn ngữ tự ý sửa đổi các quy tắc bảo mật của hệ thống

Hai agent cùng pass được một bài test, nhưng agent A chỉ tốn 5 turns và 10k token (xong trong 1 phút, tốn 0.05$), còn agent B tốn 30 turns và 150k token (xong trong 15 phút, tốn 1.20$). Trong môi trường doanh nghiệp quy mô lớn, sự chênh lệch về chi phí và độ trễ là bài toán sống còn.

Vì sao các doanh nghiệp ngân hàng không nên phụ thuộc hoàn toàn vào các benchmark công khai như SWE-bench?

  • Benchmark công khai không phản ánh đúng thư viện nội bộ và các quy ước nghiệp vụ riêng
  • Các bài kiểm tra công khai luôn có độ phức tạp quá thấp so với các dự án
  • Mô hình ngôn ngữ bị cấm truy cập vào mạng internet để tải về các bộ dữ liệu
  • Chi phí để thực thi các bài kiểm thử công khai là quá đắt đỏ cho doanh nghiệp

SWE-bench chủ yếu gồm các dự án mã nguồn mở Python phổ biến, có nguy cơ rò rỉ dữ liệu (data leakage) và không chứa đựng các công nghệ (Java/Spring, Oracle), thư viện nội bộ cũng như quy ước khắt khe về an toàn bảo mật của ngành ngân hàng.

Tự diễn đạt 1: Giải thích cơ chế F2P (Fail-to-Pass) và P2P (Pass-to-Pass) bằng một sự cố bug thực tế trong dự án Spring Boot mà anh từng xử lý.

Gợi ý đối chiếu: Khi người dùng báo cáo lỗi NullPointerException trong hàm tính thưởng cuối năm: (1) Anh viết một unit test mô phỏng đúng payload gây lỗi, chạy test thấy FAIL đỏ lòm $\to$ đó là F2P; (2) Anh giao cho agent sửa code trong Service cho tới khi bài test đó chuyển sang PASS xanh; (3) Anh chạy lại toàn bộ test suite cũ gồm 200 bài test tính lương khác và thấy tất cả vẫn PASS $\to$ đó là P2P (không bị hồi quy lỗi).

Tự diễn đạt 2: Nếu một thành viên trong team đề xuất: "Cần gì chạy test, cứ dùng Claude Sonnet 4.6 làm judge đọc diff rồi chấm điểm từ 1 đến 10 là biết agent viết code tốt hay không", anh sẽ phản biện ra sao?

Gợi ý đối chiếu: Phân tích 3 rủi ro chí mạng: (1) LLM-as-a-judge không thể phát hiện lỗi biên dịch hoặc lỗi type mismatch ngầm; (2) Model judge rất dễ bị đánh lừa bởi code viết văn hoa, đặt tên biến đẹp nhưng logic xử lý biên (edge cases) sai hoàn toàn; (3) Chi phí gọi LLM judge vừa đắt đỏ vừa không có tính tất định, trong khi chạy `./gradlew test` hoàn toàn miễn phí, chạy trong 5 giây và đảm bảo tính đúng đắn toán học 100%.

7. Thực hành: Phác thảo 1 bài Eval Task cho repo của anh

Hãy tự thiết kế một bài toán kiểm thử nội bộ đầu tiên:

  1. Chọn một bug trong quá khứ: Nhớ lại một bug nhỏ (đã từng fix thành công trong quá khứ trên repo công việc hoặc repo cá nhân).
  2. Xác định 4 thành phần của Task:
    • Task ID & Problem Statement: Viết lại mô tả lỗi ngắn gọn (2–3 câu) y như khi người dùng mở issue.
    • Base Commit: Tìm commit git trước khi bug được fix.
    • F2P Test: Chỉ ra class test và method test kiểm tra ca lỗi đó.
    • Oracle Command: Câu lệnh bash để chạy kiểm thử xác minh (ví dụ: ./gradlew test --tests *BugFixTest).
  3. Thực hiện kiểm tra tính năng lưu log trắc nghiệm: Trả lời các câu trắc nghiệm ở trên, F5 kiểm tra, và bấm nút "📋 Sao chép báo cáo kết quả gửi Agent" để dán kết quả vào chat cùng thảo luận!

Tóm tắt cốt lõi

  • Test suite là Oracle tối thượng: Đánh giá coding agent dựa trên việc code có chạy được và pass test hay không, không dựa vào LLM-as-a-judge cảm tính.
  • F2P và P2P: Sửa đúng lỗi được giao (Fail-to-Pass) và không làm hỏng chức năng cũ (Pass-to-Pass).
  • Đo lường đa chiều: Pass rate quan trọng, nhưng Token cost và số lượt Turns quyết định tính khả thi kinh tế trong doanh nghiệp.
