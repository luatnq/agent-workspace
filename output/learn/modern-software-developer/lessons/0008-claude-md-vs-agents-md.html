CLAUDE.md vs AGENTS.md: cái gì đặt ở đâu

Khi làm việc một mình, quăng mọi thứ vào CLAUDE.md là xong. Nhưng khi đưa coding agent vào team—nơi người dùng Claude Code, người dùng Cursor, người dùng Antigravity—file instruction nhanh chóng biến thành bãi rác: trùng lặp, mâu thuẫn và phá vỡ prompt cache. Bài này giúp anh thiết kế kiến trúc instruction file chuẩn công nghiệp: phân định ranh giới, bảo vệ cache prefix và chắt lọc quy ước thực sự có giá trị.

Sau bài này anh làm được

Thiết lập mô hình Single Source of Truth giữa AGENTS.md (dùng chung cho cả team) và các file riêng của harness (CLAUDE.md, GEMINI.md). Giải thích vì sao tóm tắt kiến trúc repo dài dòng là phản tác dụng dựa trên nghiên cứu thực nghiệm. Tối ưu cấu trúc file để bảo vệ Prompt Caching, và viết một bản AGENTS.md chuẩn dưới 150 dòng cho repo Spring Boot công việc.

0. Khởi động

Một câu ôn bài 7, và một câu đoán trước. Đáp án câu đoán nằm ở mục 2.

Bài 7 anh đã đúng 4/4 trắc nghiệm. Câu ôn này kiểm tra lại nguyên lý cốt lõi trước khi sang tầng instruction file.

Ở bài 7, vì sao kiến trúc bộ nhớ Two-tier (Index nạp sẵn, Detail nạp lười) lại vượt trội hơn việc nhồi toàn bộ thông tin cá nhân vào context ở đầu phiên?

  • Tiết kiệm chi phí token và tránh làm loãng khả năng chú ý của model
  • Tự động giải quyết triệt để mọi mâu thuẫn ký ức không cần can thiệp
  • Cho phép model tự động cập nhật mã nguồn mà không cần xin phép người
  • Bảo vệ dữ liệu hoàn toàn an toàn trước mọi nguy cơ bị prompt injection

Nhồi nhét mọi thứ vào context gây tốn tiền (Context Tax) và dẫn đến hiện tượng "Lost in the Middle". Với instruction file cũng hoàn toàn tương tự: một file AGENTS.md dài 1.000 dòng sẽ bị tính tiền ở mọi lượt chat và làm cùn khả năng suy luận của model.

Đoán trước: trong một bài báo thực nghiệm đo lường trên hàng trăm task SWE-bench, loại nội dung nào trong file AGENTS.md làm tăng chi phí token trên 20% nhưng gần như không giúp ích gì cho tỉ lệ hoàn thành task của agent? Viết ra rồi mới mở.

Giữ câu trả lời của anh. Mục 2 sẽ phân tích kết quả nghiên cứu từ paper "Evaluating AGENTS.md".

1. Bối cảnh: từ file cá nhân đến quy ước của cả team

Trước hết, hãy nhìn vào sự tiến hóa của instruction file:

  • Năm 2024, Claude Code giới thiệu CLAUDE.md: một file markdown đặt ở root repo, được harness tự động đọc và đính kèm vào lượt prompt của user.
  • Sau đó, mỗi công cụ AI lại đẻ ra một file riêng: Cursor có .cursorrules, Copilot có .github/copilot-instructions.md, Antigravity có GEMINI.md, Windsurf có .windsurfrules.
  • Hệ quả trong team kỹ thuật: Rule Drift (Trôi dạt quy tắc). Khi một lệnh build thay đổi hoặc team đổi từ Java 17 sang Java 21, người sửa file này nhưng quên sửa file kia. Agent của thành viên này chạy một kiểu, agent của thành viên khác chạy kiểu khác.

Để giải quyết bài toán phân mảnh này, cộng đồng và các hãng (OpenAI Codex, Antigravity, Amp, Cursor) đã chuẩn hóa về một file chung: AGENTS.md. Đây là chuẩn mở, đặt tại root repository, đóng vai trò hợp đồng giao tiếp giữa codebase và bất kỳ coding agent nào bước vào làm việc.

OpenAI Codex, Codex CLI system prompt. Hệ thống chính thức quy định: AGENTS.md là nguồn chân lý duy nhất trong repo.

Với dân backend, kiến trúc này tương tự như Spring Configuration: AGENTS.md là application.yml gốc (chứa toàn bộ quy ước chung bất biến của hệ thống); còn CLAUDE.md hay GEMINI.md giống như profile-specific config (application-claude.yml) chỉ chứa phần mapping tool/subagent riêng của harness đó.

Điều cần nhớ: Đừng viết lại quy tắc chung vào từng file riêng của harness. Đặt toàn bộ chân lý của repo vào AGENTS.md, và dùng các file harness (như CLAUDE.md) làm adapter mỏng trỏ về nó.

2. Bằng chứng thực nghiệm: bài học từ "Evaluating AGENTS.md" (2026)

Rất nhiều kỹ sư khi viết instruction file thường cố gắng "nhồi nhét" toàn bộ tài liệu kiến trúc hệ thống, sơ đồ quan hệ database và mô tả từng thư mục vào AGENTS.md. Họ tưởng rằng cung cấp càng nhiều thông tin thì agent càng thông minh. Đây là một ngộ nhận chết người.

Trong bài báo khoa học "Evaluating AGENTS.md" (Gloaguen et al., 2026), các tác giả đã chạy thử nghiệm toàn diện trên các benchmark lập trình thực tế (SWE-bench) và đưa ra những số liệu định lượng gây giật mình:

Gloaguen et al., "Evaluating AGENTS.md", 2026. Một trong những nghiên cứu định lượng hiếm hoi đo lường tác động thật sự của context files lên hiệu năng coding agent.
"Repository overviews and architectural summaries do not improve agent task completion rates, while increasing context token consumption by more than 20%."
Tạm dịch: "Phần tổng quan kho mã và tóm tắt kiến trúc không hề cải thiện tỉ lệ hoàn thành nhiệm vụ của agent, trong khi làm tăng lượng token tiêu thụ trong ngữ cảnh hơn 20%."

Vì sao lại có nghịch lý này?

  1. Model có tool để tự khám phá: Coding agent đã có sẵn các tool mạnh mẽ: ls, find, grep, view_file. Khi cần biết file nào nằm ở đâu, agent tự chạy lệnh chỉ tốn vài chục token. Nhồi một bản đồ 500 dòng vào AGENTS.md buộc model phải đọc lại bản đồ đó ở mọi lượt chat, kể cả khi nó chỉ sửa một câu typo.
  2. Khả năng tuân thủ suy giảm khi file quá dài: Khi file vượt quá 150–200 dòng, các chỉ dẫn quan trọng (như lệnh chạy test trước khi commit) bị chìm vào giữa văn bản (hiện tượng Lost in the Middle). Model bắt đầu "chọn bừa" chỉ dẫn để tuân theo.

Vậy cái gì thật sự có giá trị trong AGENTS.md? Bài báo chỉ ra:

  • Những quy ước khác thường (Non-standard / Counter-intuitive Conventions): Thứ mà model không thể tự đoán từ kiến thức pre-training. Ví dụ: "Trong repo này, chúng tôi không dùng @Transactional của Spring mà dùng custom wrapper TxHelper.run()"; hoặc "Mọi ID trả về cho client phải là Hashids, không dùng raw Long".
  • Lệnh build và test chính xác: Giúp agent vào việc ngay mà không tốn 3–4 lượt thử sai với gradle test hay mvn test.
  • Ranh giới cấm chạm (Forbidden boundaries): Những thư mục cấm sửa (như db/migration/ đã merge, schema protobuf dùng chung).

Điều cần nhớ: Đừng biến AGENTS.md thành sách giáo khoa hay bản đồ repo. Chỉ ghi: lệnh chạy, quy ước khác thường không thể tự đoán, và ranh giới cấm vi phạm. Giữ file dưới 150 dòng.

3. Prompt Caching: đừng làm vỡ chiếc bình pha lê

Đến đây anh có thể tự hỏi: nếu AGENTS.md được nạp vào mọi phiên, nó ảnh hưởng thế nào đến túi tiền và độ trễ của hệ thống?

Hãy nhớ lại bài học về Prompt Caching ở khóa llm-foundation. Các model hàng đầu (Claude 3.5/3.7, Gemini 1.5/2.0) sử dụng cơ chế Prefix Caching:

Anthropic Prompt Caching và Gemini Context Caching: đọc từ cache rẻ hơn 90% so với token thông thường và giảm 80% độ trễ TTFT.

Phép so sánh backend hoàn hảo ở đây là Docker Layer Caching. Khi anh build một Docker image:

FROM openjdk:21-slim
COPY pom.xml .
RUN mvn dependency:go-offline  # Layer này rất ổn định, được cache!
COPY src/ ./src/              # Layer này hay đổi

Nếu anh đặt một dòng lệnh sinh ngày giờ ngẫu nhiên (RUN date > /build-time.txt) lên trước lệnh dependency:go-offline, toàn bộ layer cache phía sau sẽ bị vỡ hoàn toàn (cache invalidation). Mỗi lần build anh phải tải lại toàn bộ file jar từ Maven Central!

Với LLM Prompt Cache cũng y hệt như vậy. Prompt được cache từ trên xuống dưới (Prefix Match):

Nguyên tắc vàng để bảo vệ Cache:

  • AGENTS.md phải là nội dung tĩnh. Tuyệt đối không nhúng script chạy dynamic (như `date`, kết quả `git status`, hay username biến động) vào file instruction.
  • Không sửa AGENTS.md cho các mục tiêu vụn vặt theo ngày. Việc ngắn hạn để ở prompt hoặc memory.
  • Khi chia nhỏ file, phần tĩnh nhất luôn nạp trước, phần hay biến động nạp sau.

Điều cần nhớ: AGENTS.md nằm ở vị trí đầu của context prefix. Giữ nó tĩnh và ổn định để hưởng 90% giảm giá từ Prompt Caching. Đưa dữ liệu động vào đây là tự đốt tiền của team.

Giờ đây anh đã nắm trọn vẹn 5 tầng tùy biến của một coding agent hiện đại. Hãy dùng bảng ma trận này làm kim chỉ nam mỗi khi cần thêm một chỉ dẫn vào codebase:

Bước 2 — Viết AGENTS.md cho repo Spring Boot công việc (15 phút).
Hãy chọn một repo thực tế mà anh đang lead hoặc bảo trì (dịch vụ thanh toán, core banking, microservice). Soạn thảo một file nháp AGENTS.md cho repo đó tuân thủ cấu trúc 4 phần chuẩn mực sau (lưu vào file nháp hoặc ghi chú của anh):

# {Tên Repo / Service} — Agent Guidelines

## 1. Build & Test Commands (Phải chạy được ngay)
- Build: `./gradlew clean compileJava` (hoặc `mvn clean compile`)
- Test nhanh (unit test): `./gradlew test --tests "*UnitTest"`
- Test toàn bộ: `./gradlew check`
- Linter / Format: `./gradlew spotlessApply`

## 2. Non-standard Conventions (Những thứ model KHÔNG THỂ đoán)
- Không dùng raw `@Transactional` trên controller/listener; chỉ dùng ở Service layer.
- Mọi entity bắt buộc kế thừa `BaseAuditEntity` (tự điền created_by, updated_at).
- Khi gọi HTTP sang service khác, bắt buộc dùng `InternalServiceClient` có sẵn CircuitBreaker, không tự tạo `RestTemplate` hay `WebClient` mới.
- Xử lý tiền tệ: bắt buộc dùng `BigDecimal` với scale 2 và `RoundingMode.HALF_UP`, cấm dùng `double`/`float`.

## 3. Forbidden Boundaries (Ranh giới cấm vi phạm)
- CẤM tự ý sửa các file trong `src/main/resources/db/migration/V*.sql` đã có trên nhánh main.
- CẤM commit secrets, API keys, credentials vào file `application.yml` (dùng biến môi trường).
- Không tự ý thêm dependency mới vào `build.gradle` mà không có yêu cầu rõ ràng.

## 4. Code Modification Rules
- Trước khi báo xong task: bắt buộc chạy `./gradlew spotlessApply && ./gradlew test`.
- Giữ nguyên các comment và docstring hiện có không liên quan đến thay đổi.

Trả lời ba câu hỏi thực hành:

  1. Bước 1: AGENTS.md của `my-agent` hiện có bao nhiêu dòng? Có quy ước nào vi phạm quy tắc "không ghi thông tin biến động" không?
  2. Bước 2: Trong bản AGENTS.md anh vừa viết cho repo công việc, đâu là quy ước khác thường (non-standard convention) quan trọng nhất mà nếu không dặn, agent chắc chắn sẽ làm sai theo thói quen mặc định?
  3. Nếu một dev trong team dùng Cursor và muốn tạo file .cursorrules, anh sẽ hướng dẫn họ viết nội dung file đó như thế nào để không bị trôi dạt quy tắc so với AGENTS.md?
Gợi ý (mở sau khi đã làm)

Câu 2: Trong các dự án Spring Boot ngân hàng/doanh nghiệp, lỗi hay gặp nhất của agent là: tự ý dùng `@Autowired` field injection thay vì constructor injection (Lombok `@RequiredArgsConstructor`), tự dùng `System.currentTimeMillis()` thay vì `Clock` bean để test được, hoặc tự sinh query SQL không có paging trên bảng hàng triệu record.

6. Kiểm tra cuối bài

Ba câu trắc nghiệm tình huống và hai câu tự diễn đạt.

Nghiên cứu thực nghiệm "Evaluating AGENTS.md" (Gloaguen et al., 2026) chỉ ra rằng nội dung nào sau đây trong context file đem lại ít giá trị nhất cho coding agent?

  • Mô tả tổng quan kiến trúc và tóm tắt cấu trúc toàn bộ repo
  • Quy ước đặt tên cùng cấu trúc thư mục khác thường của dự án
  • Lệnh chạy kiểm thử và quy trình kiểm tra mã nguồn trước khi commit
  • Những cạm bẫy kỹ thuật đặc thù và cách khắc phục lỗi thường gặp

Agent đã có sẵn các tool như ls, grep, find để tự khám phá repo khi cần. Nhồi nhét mô tả kiến trúc dài dòng làm tăng token hơn 20% mà không tăng tỉ lệ giải quyết task, thậm chí làm loãng context.

Về mặt Prompt Caching (Prefix Cache), vì sao việc chèn ngày giờ động hoặc trạng thái git vào AGENTS.md lại là một sai lầm nghiêm trọng?

  • Nội dung biến động làm vô hiệu hóa toàn bộ cache breakpoint phía sau
  • Model sẽ không hiểu được định dạng thời gian và dừng phiên làm việc
  • Gây ra lỗi biên dịch mã nguồn khi agent thực thi build dự án
  • Làm cho dung lượng file vượt quá giới hạn tối đa năm trăm dòng

Prompt cache hoạt động theo nguyên tắc Prefix Match từ trên xuống dưới (giống Docker layer cache). Một thông tin biến động ở đầu context làm vỡ toàn bộ cache của các block hội thoại và kết quả tool phía sau, mất sạch 90% ưu đãi chi phí.

Trong một repo microservices lớn, team nên tổ chức AGENTS.md theo mô hình nào để tối ưu context và tránh xung đột quy tắc giữa các service?

  • AGENTS.md chung ở root cho toàn repo và các file con ở từng service
  • Gom toàn bộ mọi quy tắc chi tiết vào duy nhất một root AGENTS.md
  • Mỗi service có file độc lập hoàn toàn không chia sẻ quy tắc chung
  • Chuyển toàn bộ quy ước vào các biến môi trường thay vì file markdown

Mô hình phân cấp (Hierarchical Discovery): file root chứa quy ước chung toàn repo; từng service có file con chứa quy ước đặc thù và chỉ được nạp khi agent làm việc bên trong thư mục của service đó.

Tự diễn đạt 1: Giải thích cho một thành viên mới trong team vì sao họ không được tự tiện paste tài liệu README dài 2.000 dòng vào AGENTS.md. Dùng từ ngữ kỹ thuật về context và chi phí.

AGENTS.md được harness tự động nhồi vào context ở mọi lượt gọi API của mọi thành viên. Nhồi 2.000 dòng tài liệu (~5.000 token) khiến chi phí mỗi lượt prompt tăng vọt (Context Tax) và làm loãng sự chú ý của model (Lost in the Middle), khiến nó dễ bỏ qua các luật test/build quan trọng. Hơn nữa, agent hoàn toàn có thể tự đọc README bằng tool khi cần, nên việc nhồi sẵn là vừa lãng phí vừa phản tác dụng.

Tự diễn đạt 2: Nối Bài 6 (Skill), Bài 7 (Memory) và Bài 8 (AGENTS.md). Khi nào một mẩu thông tin nên nằm ở AGENTS.md, khi nào nên là Skill, khi nào là Memory?

Nằm ở AGENTS.md khi nó là sự thật bất biến áp dụng cho toàn bộ dự án và cả team (lệnh build, quy ước code khác thường, ranh giới cấm). Nằm ở Skill khi nó là quy trình nhiều bước chỉ cần thỉnh thoảng (cần nạp lười để tiết kiệm context). Nằm ở Memory khi nó là sở thích cá nhân hoặc bài học kinh nghiệm thay đổi theo thời gian của riêng một người dùng.

Tóm lại

  • Single Source of Truth: AGENTS.md ở root là hợp đồng chung cho cả team và mọi AI agent. Các file riêng của harness (CLAUDE.md, GEMINI.md) chỉ là adapter mỏng.
  • Nghiên cứu "Evaluating AGENTS.md": Tóm tắt kiến trúc repo dài dòng tốn thêm >20% token mà không tăng hiệu quả. Hãy tập trung vào non-standard conventions, lệnh build/test và ranh giới cấm.
  • Bảo vệ Prompt Caching: AGENTS.md phải là nội dung tĩnh tuyệt đối. Không chèn ngày giờ động, git branch hay biến động làm vỡ prefix cache.
  • Kích thước lý tưởng: Dưới 150 dòng. Càng ngắn gọn, súc tích thì tỉ lệ tuân thủ càng cao.
  • Phân cấp (Hierarchical): Dùng root AGENTS.md cho quy ước toàn dự án, và các file con trong thư mục service cho các quy ước cục bộ.

Bài 9 ta sẽ bước sang một vũ khí cực mạnh để thực thi kỷ luật kỹ thuật mà không phụ thuộc vào trí nhớ của model: Hooks: lint gate, test gate, guardrail. Ta sẽ cấu hình hook tự động chạy test và linter sau mỗi lần agent Edit mã nguồn.
