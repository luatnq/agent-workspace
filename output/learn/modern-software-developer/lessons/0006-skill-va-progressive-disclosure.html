Skill: đóng gói quy trình, nạp khi cần

Bài 5 trao cho agent năng lực: một tool gọi được. Bài này trao cho nó cách làm: một quy trình, một checklist, vài script. Anh đã viết 9 skill trong my-agent. Hôm nay ta đo xem chúng tốn bao nhiêu context, model có thật sự gọi chúng không, và skill nào đang "vô hình".

Sau bài này anh làm được

Giải thích ba tầng nạp của skill và chi phí của từng tầng. Chọn đúng chỗ cho một mẩu chỉ dẫn: CLAUDE.md, skill, hook hay MCP tool. Audit bộ skill của my-agent bằng số đo thật, và chạy một trigger eval an toàn để biết description có làm việc hay không.

0. Khởi động

Một câu ôn bài 5, và một câu đoán trước. Đáp án câu đoán nằm ở mục 3.

Bài 4 và bài 5 chưa có kết quả, nên câu ôn chọn ý quan trọng nhất của bài 5 mà mục 3 hôm nay sẽ dùng lại: thông tin model cần phải nằm ở chỗ model đã đọc sẵn.

Tool tra tiến độ học có tham số topic_slug, chỉ có 3 giá trị và hiếm khi đổi. Ở bài 5, thiết kế nào giúp model gọi đúng ngay lần đầu với ít lần gọi nhất?

  • Đưa slug vào schema dạng enum, kèm tên khóa trong description
  • Thêm tool list_topics và dặn model luôn gọi tool đó trước
  • Giữ string tự do, message lỗi liệt kê slug hợp lệ
  • Đổi tham số thành topic, bỏ phần mô tả cho gọn

Bản v3 ở bài 5: 7 lần gọi cho 6 phiên, 0 lỗi. Bản thêm list_topics hết lỗi nhưng tốn 13 lần gọi vì luôn phải khám phá trước. Bản dựa vào message lỗi tốn 12 lần gọi, 4 lỗi. Thông tin đặt sẵn trong description và schema là thứ model đọc "miễn phí". Hôm nay, description của skill đóng đúng vai đó.

Đoán trước: tôi gửi 9 câu cho Claude Code trong my-agent, mỗi câu nhắm một skill của anh (remember, research, review-java, brainstorm, po, report, teach, skill-creator) và một câu không cần skill nào. Skill nào bị bỏ qua nhiều nhất, và vì sao? Viết ra rồi mới mở.

Giữ câu trả lời của anh. Mục 3 có kết quả thật.

1. Skill là gì: một bộ tài liệu onboarding được nạp lười

Trước hết là một ví dụ anh đã có sẵn. Skill review-java của anh gồm một file SKILL.md 114 dòng và 13 file khác: checklist transaction, concurrency, Oracle SQL… Khi anh nói "review đoạn code này", agent đọc SKILL.md, thấy đoạn code có @Transactional, rồi mới mở checklist transaction. Checklist Oracle thì không mở.

Anthropic định nghĩa skill đúng như vậy: "organized folders of instructions, scripts, and resources" (tạm dịch: "thư mục được sắp xếp, chứa chỉ dẫn, script và tài nguyên"). Họ ví nó với "putting together an onboarding guide for a new hire" (tạm dịch: "soạn tài liệu onboarding cho một nhân viên mới").

Barry Zhang, Keith Lazuka, Mahesh Murag, "Equipping agents for the real world with Agent Skills", Anthropic, 2025-10-16. Ngày 2025-12-18, Agent Skills được công bố thành chuẩn mở.

Với dân Spring, có một phép so sánh sát hơn: lazy loading của JPA. Entity Order được nạp ngay, còn order.getItems() chỉ là proxy, chạm vào mới query. Skill cũng vậy: tên và description được nạp ngay, thân skill chỉ nạp khi cần.

Phép so sánh hỏng ở hai chỗ, và cả hai đều quan trọng:

  • Ai quyết định "chạm vào"? Với JPA là code của anh, tất định. Với skill là model, và nó chỉ dựa vào description. Description dở thì skill không bao giờ được nạp (mục 3).
  • Không có evict. Khi đã nạp, thân skill "enters the conversation as a single message and stays there across later turns" (tạm dịch: "đi vào hội thoại thành một message và nằm đó qua các lượt sau"). Claude Code không đọc lại file. Sau compaction, mỗi skill chỉ được gắn lại 5.000 token đầu, và tất cả cùng chia ngân sách 25.000 token.
Claude Code — Skills, mục "Skill content lifecycle". Hệ quả: chỉ dẫn quan trọng nhất phải nằm ở đầu SKILL.md.

Điều cần nhớ: skill là một thư mục chỉ dẫn + script + tài liệu, nạp lười theo quyết định của model. Description là thứ duy nhất model thấy trước khi quyết định. Đã nạp thì skill nằm lại trong context tới khi compaction.

2. Ba tầng nạp, và context của anh đang tiêu vào đâu

Cơ chế này có tên là progressive disclosure, tức là "lộ dần": chỉ đưa vào context phần chi tiết mà việc hiện tại cần. Chuẩn mở Agent Skills chia ba tầng:

Đến đây anh có thể tự hỏi: tầng 1 "luôn nằm trong context" thì tốn bao nhiêu thật? Tôi chạy claude -p "/context" trong my-agent hôm nay để xem:

Ngân sách cho tầng 1 có giới hạn cứng, và anh nên biết ba con số:

  • Mỗi description (cộng when_to_use) bị cắt ở 1.536 ký tự trong listing.
  • Cả listing có ngân sách bằng 1% context window của model. Vượt ngân sách thì Claude Code bỏ description của các skill ít được gọi nhất trước, chỉ giữ lại tên. Mất description thì mất từ khóa để khớp.
  • Thân SKILL.md nên dưới 500 dòng. Tài liệu tham chiếu chỉ nên sâu một tầng tính từ SKILL.md, vì file bị trỏ lồng nhau có thể chỉ được đọc lướt bằng head -100.
Claude Code — Skills, mục "Skill descriptions are cut short". Skill authoring best practices, mục "Avoid deeply nested references". Lệnh /doctor cho ước lượng chi phí listing; /skill-doctor tìm skill không dùng.

Điều cần nhớ: description của mọi skill luôn nằm trong context, nhưng rẻ: khoảng 90 skill tốn 7,8k token trên máy anh. Thân skill chỉ tốn khi được gọi, còn script thì chỉ tốn phần output. Muốn đặt một quy trình dài vào agent, skill rẻ hơn CLAUDE.md.

3. Description quyết định skill có được gọi hay không

Bài 5 kết luận rằng description của tool là giao diện mà model đọc. Với skill còn gắt hơn: description là thứ duy nhất model có để quyết định nạp. Best practices của Anthropic nói rõ: description phải nói skill làm gì và khi nào dùng, viết ở ngôi thứ ba, và chứa từ khóa người dùng hay nói.

Giờ quay lại câu đoán ở mục 0. Tôi gửi 9 câu hỏi, mỗi câu 2 lần, cho Claude Code chạy trong my-agent. Mỗi phiên chỉ còn một built-in tool là Skill, và ta chỉ đo một việc: lượt đầu, model có gọi đúng skill không. (Về sau tôi mới phát hiện phiên vẫn còn tool MCP; xem khung bên dưới.)

Có hai chuyện đáng học ở đây.

(1) research bị bỏ qua dù khớp nghĩa. Description có cụm "so sánh lựa chọn kỹ thuật", và câu hỏi đúng là so sánh. Nhưng model thấy mình tự trả lời được, nên không gọi. Đây là hiện tượng đã được ghi nhận. Chính skill skill-creator trong repo của anh viết: "currently Claude has a tendency to 'undertrigger' skills -- to not use them when they'd be useful. To combat this, please make the skill descriptions a little bit 'pushy'" (tạm dịch: "hiện Claude có xu hướng gọi skill ít hơn mức nên gọi, tức là bỏ qua cả khi skill có ích. Để chống lại, hãy viết description hơi 'nài nỉ' một chút"). Để ý ba skill được gọi đều đặn (brainstorm, po, review-java) đều có description dài kèm câu kiểu "kể cả khi tôi chỉ nói…". research thì không có.

(2) teach vô hình theo thiết kế. SKILL.md của nó có disable-model-invocation: true. Cờ này đưa skill ra khỏi listing: model không biết nó tồn tại, chỉ anh gõ /teach mới chạy. Chính phiên này cũng vậy: anh gõ "hãy tiếp tục tạo lesson", tôi không thấy teach trong danh sách skill, nên phải tự mở file đọc. Đó là một trade-off hợp lý (một skill nặng 230 dòng, tạo file, không nên tự bật), nhưng anh nên chọn nó một cách có chủ đích.

Nhiều người nghĩ viết skill xong là agent sẽ dùng. Thật ra skill chưa được đo trigger thì chưa biết có chạy hay không, giống tool chưa qua eval ở bài 5.

Điều cần nhớ: description là điều kiện kích hoạt duy nhất của skill. Model có xu hướng bỏ qua skill khi nó tự tin trả lời được, nên description phải nêu tình huống cụ thể, kể cả cách nói tắt. disable-model-invocation làm skill vô hình với model; dùng khi muốn chỉ người gọi.

Chuyện xảy ra khi tôi chạy eval này

Lần chạy đầu tiên, tôi dùng claude -p … --allowedTools "Skill" và tưởng thế là phiên chỉ còn tool Skill. Sai. Máy anh để defaultMode: "auto", và --allowedTools chỉ duyệt trước các tool đó, không gỡ tool khác. Câu "nhớ giúp tôi là tôi thích Gradle" đã chạy skill remember và ghi thật vào memory/, hai lần. Tôi đã xóa file đó và khôi phục MEMORY.md.

Lần hai, tôi dùng --tools "Skill". Built-in tool biến mất, nhưng tool MCP của plugin OMC vẫn còn, trong đó có python_repl, tức là chạy code tùy ý. Model dùng nó để đọc thư mục (may là chỉ đọc). Chỉ đến --tools "Skill" --strict-mcp-config, event init mới báo đúng "tools":["Skill"].

Bài học: harness để chạy eval cũng cần sandbox, và phải kiểm tra danh sách tool thật trong event init, không đoán theo tên cờ. Ta sẽ quay lại ở bài 9 (hook, permission) và bài 15 (threat model).

4. Đặt chỉ dẫn vào đâu: CLAUDE.md, skill, hook hay tool

Giờ anh có bốn chỗ để đưa tri thức vào agent. Câu hỏi để chọn không phải "cái nào mạnh hơn" mà là: khi nào nó cần có mặt, và có được phép bị bỏ qua không.

Bước tất định, dễ sai nếu model tự viết (validate, parse, format)Script trong skill"code is deterministic" (tạm dịch: "code thì tất định"), và script không tốn context.

Trong một skill, best practices còn chia độ tự do theo độ "mong manh" của việc. Hình ảnh của họ: "Narrow bridge with cliffs on both sides" (tạm dịch: "cây cầu hẹp, hai bên là vực") thì đưa lệnh chính xác, kiểu "chạy đúng script này, không thêm cờ". "Open field with no hazards" (tạm dịch: "cánh đồng trống, không chướng ngại") thì chỉ cho hướng và để model tự chọn. Migration database là cây cầu. Code review là cánh đồng.

Điều cần nhớ: sự thật luôn cần → CLAUDE.md; quy trình thỉnh thoảng cần → skill; luật bắt buộc → hook; năng lực bên ngoài → MCP tool; bước tất định → script. Việc càng mong manh, chỉ dẫn càng chặt.

Đo 2026-10-13 bằng wc -l và awk trên .claude/skills/*/SKILL.md. Chuẩn mở chỉ định nghĩa 6 trường: name, description, license, compatibility, metadata, allowed-tools. argument-hint và disable-model-invocation là trường riêng của Claude Code. Antigravity xử lý chúng thế nào thì tôi chưa kiểm chứng.

Bước 1 — Tự đo context (2 phút). Trong my-agent, chạy claude -p "/context". Ghi lại hai dòng Skills và Memory files. Hai số đó có khớp với Hình 2 không?

Bước 2 — Chấm từng skill (8 phút). Dùng checklist trong cheat sheet: description có cả "làm gì" lẫn "khi nào"; thân dưới 500 dòng; tài liệu tham chiếu sâu một tầng; phần "cây cầu hẹp" đã thành script chưa. Ghi lại số skill đạt đủ cả bốn.

Bước 3 — Ra ba quyết định.

  1. teach: giữ disable-model-invocation: true, hay bỏ cờ và viết description đầy đủ? Cân nhắc: lần nào anh nói "học tiếp" mà không gõ /teach thì agent sẽ không biết đến skill này.
  2. skill-creator bản project và anthropic-skills:skill-creator bản đồng bộ từ claude.ai cùng có mặt trong listing. Giữ cả hai, hay tắt một bản bằng skillOverrides?
  3. research: viết lại description để nó được gọi khi anh cần tài liệu chính thức. Nhưng đừng để nó nuốt mọi câu hỏi kỹ thuật.

Bước 4 — Đo lại trigger của research. Chạy trước và sau khi sửa description. Bắt buộc dùng đúng các cờ dưới đây: chúng để lại cho phiên đúng một tool Skill, không có MCP, nên không ghi được gì.

cd ~/workspace/my-agent
for q in "So sánh Kafka và RabbitMQ cho hệ thống thanh toán, cái nào hợp hơn?" \
         "Tìm hiểu giúp tôi Virtual Threads của Java 21 có dùng được với Spring Boot 3 không"; do
  for r in 1 2; do
    claude -p "$q" --tools "Skill" --strict-mcp-config --max-turns 1 \
      --output-format stream-json --verbose 2>/dev/null |
    jq -r 'select(.type=="system" and .subtype=="init") | "tools=" + (.tools|join(","))
         , (select(.type=="assistant") | .message.content[]? | select(.type=="tool_use") | "skill=" + .input.skill)'
  done
done

Mỗi lần chạy phải in ra tools=Skill. Nếu thấy tool khác, dừng lại và báo tôi. error_max_turns là bình thường: ta chỉ cần biết lượt đầu có gọi Skill không.

Trả lời bốn câu:

  1. Bước 1: Skills và Memory files bao nhiêu token? Cái nào lớn hơn, và anh định làm gì với cái lớn hơn?
  2. Bước 2: bao nhiêu/9 skill đạt cả bốn tiêu chí? Lỗi hay gặp nhất là gì?
  3. Bước 3: ba quyết định của anh, mỗi cái một dòng lý do.
  4. Bước 4: research được gọi x/4 trước khi sửa và y/4 sau khi sửa. Câu "Viết hàm đảo chuỗi" có bị kéo vào research không? (Thử một lần.)
Gợi ý (mở sau khi đã làm)

Câu 1. Lúc tôi đo, Memory files là 11,1k, lớn hơn Skills (7,8k). Phần lớn đến từ ~/.claude/CLAUDE.md của OMC, dài khoảng 290 dòng (đã ghi ở bài 2). Đây là ứng viên đầu tiên: phần nào đọc như quy trình thì chuyển thành skill.

Câu 3. Không có đáp án đúng duy nhất. Với teach, một lối giữa: giữ cờ, nhưng thêm vào AGENTS.md một dòng "học tiếp / tạo lesson → dùng /teach". Dòng đó là sự thật luôn cần, nên đặt ở CLAUDE.md là đúng chỗ. Với research, hãy viết tình huống chứ đừng chỉ viết chủ đề, ví dụ "khi tôi cần nguồn chính thức, so sánh có trích dẫn, hoặc nói 'tìm hiểu giúp', 'nghiên cứu'…", và nói rõ khi nào không dùng.

Câu 4. Nếu y tăng mà câu đảo chuỗi cũng bị kéo vào, description đã quá "nài nỉ". Trigger eval luôn cần cả câu dương lẫn câu âm, giống test có cả positive case và negative case.

6. Kiểm tra cuối bài

Ba câu tình huống, hai câu tự diễn đạt.

Team có quy định "không bao giờ sửa file trong db/migration/ đã merge". Anh đã viết nó vào skill review-java, nhưng agent vẫn thỉnh thoảng sửa. Nên làm gì?

  • Chuyển quy định sang hook chặn Edit vào thư mục migration
  • Viết quy định bằng chữ in hoa ở đầu file SKILL.md
  • Chép quy định sang CLAUDE.md để nó luôn nằm trong context
  • Tách quy định ra một file reference riêng nằm trong skill

Luật phải đúng mọi lần thì đặt ở hook: harness chạy nó trước mỗi Edit, không phụ thuộc model có nạp hay nhớ skill hay không. Skill chỉ được nạp khi model thấy cần, và CLAUDE.md vẫn chỉ là context, model có thể bỏ qua. Viết hoa không đổi được bản chất đó.

Skill release có thân 900 dòng: checklist chung, quy trình cho 4 loại service, và bảng mã lỗi. Thường mỗi lần chỉ dùng cho một loại service. Tổ chức lại thế nào?

  • SKILL.md giữ checklist chung, mỗi loại service có một file riêng
  • Giữ nguyên một file vì model đọc file dài vẫn tốt
  • Chuyển toàn bộ nội dung sang CLAUDE.md cho thật chắc chắn
  • Chia bốn file nối nhau, file sau trỏ từ file trước

Đây là mẫu "domain-specific organization": thân dưới 500 dòng, mỗi domain một file, trỏ thẳng từ SKILL.md (sâu một tầng). Chuỗi file nối nhau làm model có thể chỉ đọc lướt. Chuyển vào CLAUDE.md thì trả 900 dòng ở mọi phiên.

Anh muốn đo xem skill mới có được gọi đúng lúc không, bằng claude -p trên repo thật, máy để defaultMode: "auto". Cờ nào giữ phiên an toàn?

  • Dùng --tools "Skill" cùng --strict-mcp-config, rồi kiểm tra lại event init
  • --allowedTools "Skill", vì cờ đó chỉ cho phép đúng tool Skill
  • --tools "Skill", vì cờ đó gỡ hết mọi tool còn lại
  • --max-turns 1, vì một lượt thì chưa kịp ghi file nào

Đúng như chuyện ở mục 3. --allowedTools chỉ duyệt trước, không gỡ tool khác. --tools gỡ built-in nhưng để lại tool MCP. --max-turns 1 vẫn cho model gọi một tool ghi file ngay ở lượt đầu. Phải dùng cả hai cờ và đọc danh sách tool thật trong init.

Tự diễn đạt 1: giải thích cho một dev trong team, trong 3 câu, vì sao một quy trình 300 dòng nên là skill chứ không nên nằm trong CLAUDE.md. Dùng chữ "progressive disclosure" đúng nghĩa.

CLAUDE.md được nạp toàn bộ vào mọi phiên, nên 300 dòng đó bị trả tiền kể cả khi phiên không liên quan, và còn chen vào sự chú ý của model. Skill theo progressive disclosure: lúc đầu chỉ có tên và description (khoảng 100 token) nằm trong context, thân chỉ được nạp khi model thấy việc hiện tại khớp, còn tài liệu và script phụ chỉ được mở hoặc chạy khi chỉ dẫn bảo cần. Cái giá phải trả: skill phụ thuộc vào việc description có kích hoạt được hay không, nên phải đo trigger.

Tự diễn đạt 2: nối bài 5 với bài 6 trong 2 câu. Description của tool và description của skill giống và khác nhau ở đâu?

Giống: cả hai là giao diện mà model đọc để quyết định, nên phải nói làm gì, khi nào dùng, bằng từ khóa người dùng hay nói, và phải được đo bằng eval chứ không đoán. Khác: description của tool quyết định model gọi tool thế nào (đã biết tool tồn tại, schema đi kèm), còn description của skill quyết định model có nạp quy trình hay không. Model hay bỏ qua skill khi tự tin, nên description của skill cần "nài nỉ" hơn.

Tóm lại

  • Skill = tài liệu onboarding nạp lười: thư mục gồm SKILL.md, tài liệu tham chiếu, script. Model quyết định nạp dựa trên description.
  • Ba tầng: metadata luôn nạp (~100 token/skill, cắt ở 1.536 ký tự, cả listing ≤ 1% context), thân khi gọi (< 500 dòng), tài nguyên khi cần (script chỉ tốn output).
  • Trên máy anh: listing ~90 skill tốn 7,8k token, ít hơn memory files (11,1k).
  • Trigger phải đo: research 0/2 vì model tự tin tự trả lời; teach vô hình vì disable-model-invocation. Eval cần cả câu dương lẫn câu âm.
  • Chọn chỗ đặt: sự thật → CLAUDE.md; quy trình → skill; luật bắt buộc → hook; năng lực ngoài → MCP tool; bước tất định → script.
  • Eval harness cũng cần sandbox: --tools … --strict-mcp-config, rồi đọc event init.

Bài 7 vẫn ở Module 3: agent memory. Thư mục memory/ của my-agent (vừa bị eval của tôi ghi nhầm) là một hệ memory dài hạn tự chế. Ta sẽ đối chiếu nó với lý thuyết: short-term và long-term, episodic và semantic, và chuyện "quên".
