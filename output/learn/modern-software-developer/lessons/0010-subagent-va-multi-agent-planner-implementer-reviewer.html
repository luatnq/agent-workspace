Subagent & Multi-agent: planner / implementer / reviewer

Ở các bài trước, ta đã trang bị cho agent công cụ (MCP/Tool), kỹ năng nạp lười (Skills), bộ nhớ dài hạn (Memory), và chốt chặn cưỡng chế (Hooks). Nhưng khi đối mặt với một codebase quy mô hàng trăm nghìn dòng mã, một tác tử đơn lẻ ("God Agent") nhanh chóng bị nghẽn: context phình to, chi phí bùng nổ, và mô hình bắt đầu đãng trí. Hôm nay ta kết thúc Module 4 bằng kỹ thuật kiến trúc quan trọng nhất để mở rộng quy mô: Subagent & Multi-agent.

Sau bài này anh làm được

Giải thích bản chất của Subagent dưới góc độ cô lập ngữ cảnh (Context Isolation) và cơ chế thu gom rác token (Garbage Collection). Thiết kế 3 mô hình đa tác tử kinh điển: Orchestrator-Workers, Assembly Line (Pipeline), và Evaluator-Optimizer. Phân tích tỉnh táo trade-off giữa giải pháp Native Harness (Claude Code / Antigravity) và các framework ngoài như LangGraph, CrewAI, AutoGen.

0. Khởi động

Một câu ôn bài 9 (củng cố cơ chế feedback loop), và một câu đoán trước. Đáp án câu đoán nằm ở mục 1.

Câu ôn này trực tiếp khắc sâu bản chất của vòng lặp ReAct: PostToolUse là cảm biến phản hồi (sensor), không phải máy chém ngắt tiến trình.

Ở bài 9, khi một script kiểm tra biên dịch (PostToolUse hook) phát hiện lỗi và trả về exit code khác 0, cơ chế xử lý chuẩn mực của harness là gì?

  • Harness thu thập stderr đưa vào context để model tự nhận biết lỗi và sửa lại mã
  • Harness lập tức ngắt phiên làm việc và dừng toàn bộ tiến trình hệ thống đang chạy
  • Harness tự động hoàn tác toàn bộ các thay đổi vừa thực hiện trên cây thư mục
  • Harness tự động tạo commit git nhằm lưu giữ lại trạng thái lỗi vừa phát sinh này

Khi PostToolUse fail, harness bắt toàn bộ stderr của script và đưa vào context như một quan sát hệ thống (Observation) ở lượt kế tiếp. Nhờ đó, model tự đọc được lỗi biên dịch/linter và chủ động gọi thêm một lượt Tool Edit nữa để tự sửa lỗi (Autonomous Self-Healing) mà không cần con người can thiệp.

Đoán trước: Nếu một subagent chuyên khảo sát mã nguồn phải đọc 20 file (tiêu tốn 40.000 token trong quá trình tìm kiếm) rồi tóm tắt lại kết quả thành 500 token, thì context window của agent chính sẽ tăng thêm bao nhiêu token? Viết ra rồi mới mở.

Chính xác là chỉ tăng thêm khoảng 500 token (cộng thêm vài chục token metadata gọi tool). 40.000 token trung gian đọc file đã hoàn toàn biến mất! Mục 1 sẽ giải phẫu cơ chế kỳ diệu này.

1. Vấn đề Context Isolation: Vì sao "God Agent" luôn thất bại?

Hãy hình dung một tác vụ thực tế trong dự án Spring Boot ngân hàng: "Kiểm tra xem hệ thống tính phí giao dịch ngoại tệ (FX Fee) đang được gọi ở những service nào, và sửa lại công thức làm tròn số thập phân."

Nếu để một agent duy nhất giải quyết toàn bộ trong một luồng (thread) hội thoại:

  1. Agent dùng lệnh tìm kiếm, liệt kê 35 files liên quan đến module thanh toán và tỷ giá.
  2. Agent lần lượt mở đọc 15 files để hiểu luồng gọi nghiệp vụ. Mỗi file Java khoảng 300–500 dòng $\implies$ context nạp thêm ~45.000 tokens.
  3. Agent bắt đầu sửa 2 file mã nguồn.
  4. Agent chạy test, gặp lỗi, đọc log kiểm thử $\implies$ context tiếp tục phình lên 70.000 tokens.

Hậu quả kiến trúc của mô hình "God Agent" này là gì?

Anthropic gọi đây là Context Pollution hay Context Tax: anh đang trả tiền cho những token đã hoàn thành nhiệm vụ lịch sử nhưng vẫn nằm lỳ trong bộ nhớ.
  • Hao phí tài chính lũy tiến: Nhắc lại kiến trúc LLM: mỗi turn mới, harness phải gửi toàn bộ lịch sử cho model. Khi context đạt 70k tokens, mỗi suy nghĩ, mỗi lượt gọi tool nhỏ nhặt tiếp theo của agent đều tiêu tốn chi phí input của 70k tokens!
  • Hiện tượng Lost in the Middle & Giảm tập trung: Khi context chứa đầy hàng nghìn dòng code tham khảo cũ, model bắt đầu đãng trí: bỏ sót quy ước trong AGENTS.md, quên mất yêu cầu gốc của user, hoặc sinh code nhầm lẫn giữa các phiên bản service cũ và mới.
  • Độ trễ tăng vọt (High TTFT): Thời gian xử lý prompt hàng chục nghìn tokens trước khi sinh ra ký tự đầu tiên tăng từ vài trăm mili-giây lên 5–10 giây.
So sánh Backend

Một "God Agent" giống như một Monolithic Process duy nhất gánh vác mọi việc: khi một luồng tải dữ liệu báo cáo khổng lồ vào RAM, toàn bộ bộ nhớ Heap bị phình trướng, kích hoạt Full GC liên tục và làm nghẽn luôn các luồng xử lý giao dịch thanh toán lõi.
Subagent chính là mô hình Microservice hoặc Worker Process (Fork): ta tách tác vụ đọc dữ liệu nặng nề sang một tiến trình riêng biệt với vùng nhớ Heap độc lập. Khi worker làm xong, nó trả về DTO kết quả nhỏ gọn rồi tự giải phóng vùng nhớ của mình!

2. Ba mô hình Multi-agent chuẩn mực (Patterns)

Thay vì để một agent ôm đồm, kỹ nghệ agent hiện đại tổ chức công việc theo 3 mẫu hình kiến trúc:

Mô hình 1: Orchestrator-Workers (Hub & Spoke)

Đây là mô hình phổ biến và thực dụng nhất trong các coding harness hiện đại (như Claude Code và Antigravity):

                  ┌──────────────────────────────┐
                  │    User / Task Briefing      │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                  ┌──────────────────────────────┐
                  │   Orchestrator Main Agent    │ ◄── Ngữ cảnh tinh gọn (~5k tokens)
                  │ (Giữ mục tiêu, phân chia việc)│
                  └───┬──────────────┬───────────┘
                      │              │
      Ủy thác nhiệm vụ│              │Ủy thác kiểm tra
      (Context Fork)  ▼              ▼ (Context Fork)
  ┌───────────────────────┐      ┌───────────────────────┐
  │   Research Subagent   │      │   Reviewer Subagent   │
  │ (Đọc 30 files mã nguồn│      │ (So sánh git diff,    │
  │  Tốn 50k tokens rác)  │      │  chạy test độc lập)   │
  └───────────┬───────────┘      └───────────┬───────────┘
              │                              │
              └──────────────┬───────────────┘
                             ▼
              Chỉ trả về Bản tóm tắt kết quả (~500 tokens)
              Toàn bộ 50k tokens đọc file bị Garbage Collect!

Cơ chế Context Fork: Main agent gọi subagent thông qua một prompt nhiệm vụ đóng gói gọn gàng. Subagent chạy trên một nhánh context hoàn toàn mới. Khi subagent hoàn thành, nó chỉ trả về kết luận (summary). Toàn bộ dấu vết đọc hàng chục files bị vứt bỏ, bảo vệ context của main agent luôn tinh khôi.

Mô hình 2: Assembly Line (Sequential Pipeline / Handoff)

Áp dụng cho các tính năng mới cần quy trình chặt chẽ (RePPIT / Spec-driven):

  • Chặng 1: Planner Agent (Chỉ đọc) $\to$ Khảo sát yêu cầu, sinh ra file Spec Markdown trên đĩa.
  • Chặng 2: Implementer Agent (Quyền ghi) $\to$ Đọc file Spec, viết code, sửa test.
  • Chặng 3: Reviewer Agent (Chỉ đọc) $\to$ So sánh git diff với Spec ban đầu, chạy linter, xuất báo cáo review.

Nguyên tắc vàng về Handoff: Trong mô hình pipeline, các agent bàn giao công việc cho nhau thông qua Handoff Artifacts (file spec, file diff, test report trên ổ đĩa), TUYỆT ĐỐI KHÔNG bàn giao bằng cách ném nguyên chuỗi lịch sử chat tự do qua lại! Truyền chat tự do làm rò rỉ rác ngữ cảnh và gây méo mó yêu cầu.

Mô hình 3: Evaluator-Optimizer (Critic Loop)

Mô hình cộng tác giữa Người làm (Implementer) và Người chấm (Evaluator/Critic):

  1. Implementer đề xuất giải pháp mã nguồn.
  2. Evaluator đối chiếu với tiêu chuẩn bảo mật hoặc benchmark hiệu năng, đưa ra phản biện.
  3. Implementer tiếp thu và sửa đổi.

Ràng buộc sống còn: Vòng lặp này bắt buộc phải có Circuit Breaker (ngưỡng dừng cứng: Max 2–3 iterations). Nếu không, hai agent sẽ rơi vào bẫy "tranh cãi vô tận" (Ping-pong trap).

3. Cơ chế Harness: Claude Code vs Antigravity

Mỗi harness có cơ chế hiện thực hóa subagent khác nhau ở tầng runtime:

Hạng mục Claude Code Antigravity
Khởi tạo Subagent Khai báo qua frontmatter context: fork trong custom slash command hoặc subagent definition tại .claude/agents/*.md. Gọi tool define_subagent (định nghĩa động) và invoke_subagent (kích hoạt chạy ngầm).
Phân quyền Tool (Scoping) Khai báo danh sách allowed-tools (ví dụ: chỉ cho phép ReadNotebook, Grep, cấm Edit). Cấu hình cờ enable_write_tools: false để tạo agent chỉ đọc (read-only research agent).
Không gian làm việc (Workspace) Chạy chung trên working directory hiện tại. Hỗ trợ 3 chế độ workspace cực mạnh:
- inherit: dùng chung thư mục.
- branch: tự động tạo git worktree/branch riêng, bảo vệ tuyệt đối không bị đè file.
- share: chia sẻ repo underlying.
Mô hình thực thi Đồng bộ: Main agent đợi subagent chạy xong và nhận kết quả text. Bất đồng bộ (Reactive Wakeup): Main agent có thể kích hoạt nhiều subagent chạy nền cùng lúc và tiếp tục việc khác; harness tự đánh thức khi subagent nhắn tin về.

4. So sánh Framework: Native Harness vs LangGraph vs CrewAI vs AutoGen

Hiện nay trên thị trường có nhiều framework quảng bá rầm rộ về "Multi-agent". Một senior engineer cần phân biệt rõ ranh giới kiến trúc và mục đích sử dụng:

Framework Mô hình tư duy cốt lõi Ưu điểm nổi bật Nhược điểm & Rủi ro
Harness-Native
(Claude Code, Antigravity)		 Công cụ lập trình (Developer-centric), bám sát IDE, shell và filesystem. Tốc độ cao, chi phí token tối ưu, kiểm soát context chặt chẽ, không sinh boilerplate thừa. Giới hạn trong môi trường coding agent; không thiết kế để dựng ứng dụng web agent độc lập cho end-user.
LangGraph
(LangChain ecosystem)		 State Machine / Directed Graph: các agent là Node, luồng điều hướng là Edge có điều kiện. Cực mạnh cho quy trình doanh nghiệp có rẽ nhánh phức tạp, hỗ trợ lưu checkpoint (time-travel debugging), human-in-the-loop. Độ phức tạp (learning curve) cao, nhiều code boilerplate, dễ bị over-engineering cho các tác vụ lập trình thông thường.
CrewAI Role-playing: mô phỏng nhân sự (Bạn là Senior Java Architect, Bạn là QA Tester). Cực kỳ dễ demo, viết code định nghĩa agent trực quan, giao việc theo chức danh quen thuộc. Cháy token: Prompt bị nhồi nhét quá nhiều câu văn mô tả tính cách/vai trò; các agent dễ sa đà vào việc "đóng kịch" thay vì giải quyết task kỹ thuật.
AutoGen
(Microsoft)		 Conversational Group Chat: các agent trò chuyện, phản biện tự do qua tin nhắn. Linh hoạt trong nghiên cứu mô phỏng tương tác xã hội giữa các mô hình ngôn ngữ. Khó kiểm soát nhất: Rất dễ rơi vào bẫy hội thoại vòng quanh (Chatter loop), thiếu tính tất định cần có của phần mềm production.
Lời khuyên thực chiến

Đối với công việc kỹ thuật hàng ngày (coding, refactor, debug, review): Ưu tiên tuyệt đối Native Subagents của Harness (hoặc script phân rã đơn giản). Đừng vội vã đưa LangGraph hay CrewAI vào khi bài toán chỉ là đọc hiểu và sửa đổi codebase. Đơn giản là tối thượng!

5. Bốn bẫy kiến trúc (Pitfalls) của Multi-agent

Khi bước vào thế giới đa tác tử, các lỗi sau đây là nguyên nhân hàng đầu khiến dự án agent thất bại:

Bẫy 1: Ping-pong / Banter Trap (Tranh luận vô tận)

Khi Implementer và Reviewer được cấu hình phản biện lẫn nhau mà không có tiêu chí định lượng: Reviewer bắt bẻ tên biến $\to$ Implementer sửa $\to$ Reviewer bảo chưa ưng ý $\to$ Implementer giải thích. Sau 10 turns, cạn sạch ngân sách token mà code vẫn chưa chạy.

Khắc phục: Luôn cài đặt Max Iterations $\le$ 3. Mọi tiêu chí về format, style, biên dịch phải giao cho Hook/Linter tất định kiểm tra, cấm để hai agent tranh luận văn xuôi về formatting!

Bẫy 2: Context Starvation (Đãng trí khi bàn giao)

Gọi subagent với câu lệnh cộc lốc: "Kiểm tra lỗi NullPointerException trong PaymentService giúp tôi". Subagent chạy trên một context fork trống trơn, không hề biết branch hiện tại là gì, test case nào đang fail, hay quy ước trong AGENTS.md ra sao $\implies$ Subagent hallucinate hoặc trả lời chung chung như ChatGPT.

Khắc phục: Lời gọi subagent phải là một Self-contained Briefing: cung cấp đường dẫn file chính xác, error log cụ thể, và mục tiêu đầu ra rõ ràng.

Bẫy 3: Workspace Collision (Xung đột ghi đè mã nguồn)

Nếu hai subagent cùng chạy song song và cùng sửa đổi mã nguồn trên cùng một thư mục làm việc, chúng sẽ ghi đè đè lên nhau, gây ra trạng thái race condition tồi tệ hơn cả multithreading không đồng bộ.

Khắc phục: Áp dụng nguyên tắc Single Writer: chỉ một agent có quyền ghi mã nguồn tại một thời điểm; hoặc sử dụng chế độ cách ly branch (git worktree) của Antigravity để mỗi agent thao tác trên một branch riêng biệt rồi merge lại qua pull request.

Bẫy 4: Over-engineering (Dao mổ trâu giết gà)

Một lỗi typo chính tả trong file README hoặc sửa 1 dòng query SQL đơn giản mà kích hoạt quy trình 3 subagents (Planner $\to$ Coder $\to$ Reviewer) $\implies$ tốn gấp 5 lần tiền và 10 lần thời gian vô ích.

Quy tắc vàng: Chỉ chia subagent khi lượng đọc vượt quá 20.000 tokens hoặc khi cần cô lập quyền truy cập (ví dụ: cần một agent chỉ được đọc chứ không được sửa code).

6. Kiểm tra hiểu biết cuối bài

Lợi ích kiến trúc quan trọng nhất khi tách một tác vụ khám phá mã nguồn lớn cho một Subagent độc lập thực hiện là gì?

  • Ngăn chặn việc rò rỉ hàng chục nghìn token rác vào ngữ cảnh làm việc của agent chính
  • Giúp cho model có thể tăng tốc độ sinh văn bản lên gấp nhiều lần so với trước
  • Cho phép vượt qua mọi giới hạn an toàn của hệ điều hành trên máy chủ phát triển
  • Tự động giải quyết các lỗi cú pháp mà không cần gọi thêm bất kỳ công cụ nào

Subagent hoạt động trong một context fork độc lập. Hàng chục nghìn token phát sinh từ việc mở đọc hàng loạt file mã nguồn chỉ tồn tại tạm thời; khi kết thúc, subagent chỉ trả về bản tóm tắt ngắn cho main agent, giúp context chính luôn tinh gọn và tránh hiện tượng Lost in the Middle.

Trong mô hình Planner - Implementer - Reviewer, phương thức bàn giao (handoff) giữa các agent nào được coi là chuẩn mực và an toàn nhất?

  • Bàn giao thông qua các file tài liệu đặc tả cùng bản vá mã nguồn ghi trên đĩa
  • Bàn giao bằng cách nhồi toàn bộ lịch sử hội thoại dài dòng qua lại giữa các agent
  • Bàn giao thông qua việc dùng chung một vùng nhớ chia sẻ toàn cục giữa các luồng chạy
  • Bàn giao bằng cách truyền nối tiếp các biến môi trường ngầm định trong suốt phiên làm việc

Bàn giao chuẩn mực trong kỹ nghệ agent luôn dựa trên Handoff Artifacts (file spec markdown, bản vá git diff, file test report trên ổ đĩa). Việc truyền nguyên lịch sử chat tự do qua lại sẽ làm ô nhiễm ngữ cảnh và gây méo mó yêu cầu kỹ thuật.

Hiện tượng bẫy tương tác "Ping-pong / Banter Trap" trong hệ thống multi-agent thường dẫn đến hậu quả nguy hiểm nào sau đây?

  • Hai tác tử tranh luận và khen ngợi nhau qua lại vô tận gây cháy ngân sách token
  • Mô hình ngôn ngữ bị sập nguồn máy chủ do xung đột luồng xử lý của hệ thống
  • Cơ sở dữ liệu tự động kích hoạt tính năng khóa toàn bộ các bảng ghi dữ liệu
  • Trình duyệt web từ chối hiển thị tài liệu do vi phạm các chính sách bảo mật mạng

Ping-pong trap xảy ra khi các agent phản biện lẫn nhau bằng văn xuôi mà không có chốt chặn cứng hoặc tiêu chí định lượng, dẫn đến việc khen ngợi hoặc tranh cãi vòng quanh làm cạn kiệt ngân sách token. Giải pháp là đặt Max Iterations và dùng Hook/Linter tất định để đánh giá.

Tự diễn đạt 1: Giải thích cơ chế "Garbage Collection" của context khi dùng Subagent bằng góc nhìn quản lý bộ nhớ heap/stack trong Java.

Gợi ý đối chiếu: Khi main agent tự làm mọi việc, các biến trung gian khổng lồ (nội dung 30 files) được lưu vào phạm vi toàn cục (Global Context Heap) và không bao giờ được giải phóng. Khi gọi Subagent, tác vụ tương tự như mở một Stack Frame mới hoặc gọi một Thread riêng biệt: mọi dữ liệu đọc file được cấp phát trên Stack Frame của Subagent. Khi Subagent return giá trị tóm tắt, Stack Frame bị hủy hoàn toàn, giải phóng sạch sẽ bộ nhớ.

Tự diễn đạt 2: Nếu một junior engineer trong team đề xuất tích hợp CrewAI để chia 5 agent (Frontend Dev, Backend Dev, Tester, DevOps, Project Manager) cùng chat với nhau để viết một tính năng nhỏ, anh sẽ phân tích trade-off và phản biện thế nào?

Gợi ý đối chiếu: Phân tích 3 điểm yếu: (1) Token overhead khổng lồ từ các đoạn prompt mô tả tính cách/role của 5 agent; (2) Nguy cơ Ping-pong và mất tập trung cao độ khi 5 agent trò chuyện tự do; (3) Chi phí và độ trễ cao không tương xứng với giá trị của một tính năng nhỏ. Đề xuất: Dùng một agent duy nhất kèm RePPIT spec, hoặc tối đa là một cặp Planner/Implementer với handoff bằng file spec markdown.

7. Thực hành: Kiểm chứng Context Isolation trên máy

Hãy trải nghiệm thực tế cơ chế cô lập của Subagent ngay trên workspace này:

  1. Quan sát Subagent có sẵn: Mở file hướng dẫn hệ thống của Antigravity (`AGENTS.md` / `GEMINI.md`) để xem danh sách các subagent được cấp quyền:
    • research: Subagent chỉ đọc (read-only), dùng để khảo sát codebase hoặc tìm kiếm tài liệu mà không làm bẩn context chính.
    • self: Subagent có đầy đủ quyền đọc/ghi/chạy lệnh.
  2. Thử nghiệm trong suy nghĩ: Khi cần tìm kiếm một mẫu code Java trong toàn bộ dự án lớn:
    • Nếu tự chạy grep_search rồi view_file 10 lần trong thread chính: context của anh tăng ngay 20.000 tokens.
    • Nếu ủy thác: "Hãy gọi subagent research tìm cho tôi tất cả các class kế thừa từ BaseService và tóm tắt danh sách": subagent tự đọc 10 files đó ở phòng riêng, rồi chỉ trả về 1 danh sách 5 gạch đầu dòng. Main thread chỉ tốn ~100 tokens!
  3. Kiểm tra tính năng lưu log trắc nghiệm mới: Hãy thử trả lời bộ câu hỏi trắc nghiệm ở trên, F5 lại trang để thấy kết quả được phục hồi nguyên vẹn, sau đó bấm nút "📋 Sao chép báo cáo kết quả gửi Agent" ở Bảng tổng kết bên dưới để dán vào chat!

Tóm tắt cốt lõi

  • Context Isolation là lý do số 1: Subagent không phải để "làm màu" đa nhân cách, mà là giải pháp kỹ thuật để cô lập ngữ cảnh và thu gom rác token sau các tác vụ đọc nặng nề.
  • Handoff bằng Artifact: Không truyền chat tự do qua lại giữa các agent. Bàn giao thông qua file Spec, Git diff, hoặc Test report trên đĩa.
  • Đơn giản là sức mạnh: Ưu tiên subagent native của harness. Đừng lạm dụng các framework role-playing phức tạp khi chưa thật sự cần thiết.
