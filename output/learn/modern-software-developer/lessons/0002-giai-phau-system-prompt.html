Giải phẫu system prompt của coding agent

Bài 1 mở phần "tay chân" của agent: vòng lặp và bộ tool. Nhưng còn một câu hỏi bỏ ngỏ: làm sao model biết khi nào nên dùng tool nào, khi nào nên dừng, việc gì không được làm? Câu trả lời nằm trong system prompt. Hôm nay ta đọc một system prompt production thật, từng đoạn một.

Sau bài này anh làm được

Nhìn vào một dòng trong system prompt hay CLAUDE.md và nói được nó đang chặn lỗi gì. Biết luật nào nên viết vào CLAUDE.md, luật nào phải chuyển thành hook. Và tìm ra chỗ mâu thuẫn trong chính các file instruction trên máy anh.

0. Khởi động — hỏi lại hai câu bài trước

Ở bài 1, anh sai hai câu, và cả hai cùng xoay quanh một chuyện: lỗi đi đâu trong harness. Sai ở chỗ này là bình thường, vì đây là phần tinh tế nhất của bài. Hôm nay ta hỏi lại, nhưng đứng ở vị trí khác: lần này anh là người viết tool.

Ôn giãn cách cho LR-0001. Đổi góc nhìn (từ người dùng agent sang người viết harness) để não phải nhớ lại ý, chứ không nhớ mặt chữ của đáp án cũ.

Anh đang viết tool edit_file cho một agent nội bộ. Model gửi old_string khớp tới 4 chỗ trong file. Tool nên làm gì?

  • Trả lỗi kèm số chỗ khớp và cách sửa
  • Tự sửa chỗ đầu tiên rồi báo thành công
  • Tự sửa cả bốn chỗ để tránh bỏ sót
  • Trả về chuỗi Error ngắn gọn không chi tiết

Tool không được đoán hộ model: đoán sai là sửa nhầm code mà không ai biết. Nhưng chỉ trả mỗi chữ "Error" cũng không đủ, vì model không biết mình sai ở đâu và thường lặp lại y hệt. Thông báo tốt cho biết sai gì (4 chỗ khớp) và sửa thế nào (thêm dòng xung quanh). Nhờ vậy lượt sau model kéo dài old_string, giống như thêm điều kiện vào WHERE cho tới khi trúng đúng một row.

Tự diễn đạt: vì sao except: continue trong code parse tool call còn tệ hơn để chương trình crash? Viết ra 2 câu, rồi mới mở.

Crash thì ồn ào: ai cũng thấy, và ai cũng biết phải sửa. Nuốt lỗi thì im lặng: harness tưởng model không gọi tool nữa, nên coi response là câu trả lời cuối. File không được sửa, còn người dùng thấy dòng "tool: ..." và tưởng việc đã xong. Cách đúng là thứ ba: trả lỗi parse về cho model dưới dạng một tool_result báo lỗi, để lượt sau nó viết lại cho đúng format.

So với câu của anh: có đủ hai ý (1) "im lặng → tưởng đã xong" và (2) "cách đúng là trả lỗi về cho model" không? Thiếu ý nào thì báo tôi.

1. System prompt nằm ở đâu trong một request?

Trước hết, nhắc lại một điều từ bài 1 của llm-foundation: model không nhớ gì giữa các lần gọi. Mỗi lượt, harness gửi lại toàn bộ mọi thứ model cần biết. Vậy "mọi thứ" đó gồm những gì?

Hãy nghĩ tới ngày đầu đi làm của một kỹ sư mới. Họ nhận ba thứ: sổ tay công ty (quy định chung, áp dụng cho mọi dự án), README của team (cách build, quy ước code của dự án này), và ticket (việc cụ thể hôm nay). Một request của coding agent cũng có đúng ba lớp đó, cộng thêm danh sách công cụ:

Chi tiết ở lớp màu cam rất quan trọng. Tài liệu Claude Code nói rõ: "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself" (tạm dịch: "nội dung CLAUDE.md được gửi dưới dạng một user message nằm sau system prompt, chứ không phải một phần của system prompt"). Codex CLI cũng để AGENTS.md ngoài phần prompt cố định: nội dung file được gửi "with the developer message" (tạm dịch: "kèm theo developer message"), tức một message riêng của phía harness.

Claude Code — How Claude remembers your project; Agent SDK — Modifying system prompts.

Phép so sánh "sổ tay nhân viên" hỏng ở một chỗ. Người mới đọc sổ tay một lần rồi nhớ. Model thì đọc lại toàn bộ ở mỗi lượt, và mỗi dòng đều tốn token, đều chiếm chỗ trong context. Vì vậy mỗi dòng phải đáng tiền.

Điều cần nhớ: system prompt do harness viết; CLAUDE.md do anh viết và đi vào như một user message. Cả hai đều là lời dặn, không phải cấu hình bắt buộc. Mục 4 sẽ cho thấy điều này quan trọng thế nào.

2. Đọc system prompt của Codex CLI

Claude Code không công bố system prompt của nó. Các system prompt mà Anthropic công bố chỉ là của app claude.ai. Nhưng Codex CLI của OpenAI là mã nguồn mở, nên ta đọc được nguyên văn: file prompt.md dài 275 dòng. Tên sản phẩm khác nhau, nhưng các coding agent giải cùng một bài toán, nên cấu trúc prompt rất giống nhau.

openai/codex — prompt.md (bản sửa gần nhất 2026-06-23). Phần git safety lấy từ gpt_5_codex_prompt.md cùng repo.

Trước khi đọc tiếp, thử đoán: nếu anh phải viết system prompt cho một coding agent, anh sẽ viết những mục gì?

Giờ so với bản thật. Có một cách đọc giúp mọi thứ sáng ra: hầu hết các dòng trong prompt là một vết sẹo. Mỗi dòng tồn tại vì model từng làm sai đúng việc đó. Giống như runbook của team anh: dòng "nhớ drain node trước khi reboot" có mặt vì đã có một lần quên. Vì vậy, với mỗi đoạn dưới đây, hãy hỏi: dòng này đang chặn lỗi gì?

Hãy dừng lại ở dòng "Cách dùng tool". Prompt bảo model đừng đọc lại file sau khi sửa, vì tool sẽ báo lỗi nếu sửa không được. Dòng này chỉ an toàn khi harness thật sự báo lỗi. Đặt nó vào agent 192 dòng ở bài 1, nơi lỗi bị nuốt im lặng, thì model sẽ tự tin bước tiếp trên một file chưa hề được sửa. Nói cách khác: prompt và harness phải khớp nhau. Một lời dặn trong prompt luôn dựa trên một giả định về cách harness hành xử.

Phần còn lại của prompt (khoảng một nửa) nói về cách giao tiếp: gửi một câu ngắn trước mỗi nhóm tool call, báo tiến độ, format câu trả lời cuối. Nó không làm agent code giỏi hơn, nhưng giúp người dùng theo kịp và tin tưởng agent.

Điều cần nhớ: đọc system prompt như đọc runbook. Mỗi dòng là một lỗi đã từng xảy ra. Khi anh viết CLAUDE.md, hãy viết theo cùng cách: bắt đầu từ lỗi thật, rồi mới viết luật.

3. ReAct: vì sao agent xen kẽ "nghĩ" và "làm"

Nhìn lại vòng lặp ở bài 1: model nghĩ một chút, gọi tool, đọc kết quả, nghĩ tiếp. Mẫu này có tên: ReAct (Reasoning + Acting, tức "suy luận + hành động"), đề xuất năm 2022.

Yao et al. — "ReAct: Synergizing Reasoning and Acting in Language Models", ICLR 2023. roadmap.sh xếp ReAct và planner–executor vào nhóm kiến trúc agent.

Trước ReAct, có hai cách tách rời. Một là cho model nghĩ từng bước (chain-of-thought) nhưng không được kiểm tra gì với thế giới bên ngoài. Hai là cho model làm nhưng không nghĩ. ReAct ghép hai thứ lại, và mỗi bên bù cho bên kia. Bài báo viết: suy luận giúp model "induce, track, and update action plans" (tạm dịch: "đề ra, theo dõi và cập nhật kế hoạch hành động"), còn hành động giúp nó "gather additional information" (tạm dịch: "thu thập thêm thông tin") từ bên ngoài.

Điểm đáng giá nhất với anh: ReAct "overcomes issues of hallucination and error propagation prevalent in chain-of-thought reasoning" (tạm dịch: "khắc phục vấn đề hallucination và lỗi dây chuyền vốn phổ biến khi chỉ suy luận chuỗi"). Nói đơn giản: nếu chỉ nghĩ, một giả định sai ở bước 2 sẽ kéo sai hết các bước sau. Có hành động xen vào, model được "va chạm với thực tế": nó nghĩ file có hàm findById, chạy rg thì thấy không có, và sửa lại suy nghĩ ngay. Đây cũng là lý do bash quý như bài 1 đã nói.

Vậy kế hoạch (plan tool) từ đâu ra? roadmap.sh gọi mẫu này là planner–executor: một bên lập kế hoạch, một bên thực hiện. Coding agent hiện nay dùng phiên bản nhẹ: cùng một model vừa lập kế hoạch, vừa thực hiện, và cập nhật kế hoạch trong lúc làm. Ba lựa chọn này có trade-off rõ:

Cách làmHợp vớiRủi ro
ReAct thuần, không planViệc nhỏ, một hai bướcViệc dài dễ lạc hướng, quên việc đã hứa
ReAct + plan tool (Codex, Claude Code)Việc nhiều bước trong một phiênPlan rườm rà cho việc đơn giản, nên prompt phải dặn khi nào không dùng
Planner và executor tách riêng (thường là hai agent)Việc lớn, cần người duyệt plan trước khi làmPlan lập ra trước khi thấy code thật, dễ sai; tốn thêm lượt gọi

Dòng thứ ba sẽ quay lại ở bài 3 (quy trình RePPIT: Research, Propose, Plan, Implement, Test) và bài 10 (subagent planner / implementer / reviewer).

Điều cần nhớ: coding agent là ReAct: nghĩ, làm, quan sát, lặp lại. Hành động giữ cho suy luận không trôi xa khỏi thực tế. Plan chỉ là lớp mỏng bên ngoài để không lạc trong việc dài.

4. Lời dặn không phải là luật

Nhiều người nghĩ viết NEVER bằng chữ hoa trong CLAUDE.md là đủ để cấm hẳn một việc. Tài liệu Claude Code nói ngược lại: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." (tạm dịch: "Claude coi các file này là context, không phải cấu hình bắt buộc. Muốn chặn một hành động bất kể Claude quyết định thế nào, hãy dùng PreToolUse hook.")

Còn khi hai file dặn hai điều trái nhau? Codex giải quyết bằng một luật ưu tiên viết ngay trong system prompt: file nằm sâu hơn thắng. Claude Code thì khác. Mọi file CLAUDE.md được nối vào context, không file nào đè file nào, và "if two rules contradict each other, Claude may pick one arbitrarily" (tạm dịch: "nếu hai luật mâu thuẫn, Claude có thể chọn bừa một trong hai"). Tài liệu còn khuyên mỗi file CLAUDE.md nên dưới 200 dòng, vì file dài làm model tuân thủ kém đi.

Claude Code — How Claude remembers your project, các mục về size, consistency và troubleshooting.

Với dân backend, có thể hình dung thế này. CLAUDE.md giống comment trong code: người đọc nên theo, nhưng không có gì ép buộc. Hook giống constraint trong database: vi phạm là bị từ chối, bất kể ai viết câu lệnh. Việc gì mà làm sai sẽ gây hậu quả không đảo ngược được, thì đừng chỉ viết comment.

Điều cần nhớ: CLAUDE.md để định hướng, hook để chặn. Hai file mâu thuẫn thì Claude Code không có luật phân xử, nên việc giữ các file nhất quán là trách nhiệm của anh.

5. Thực hành: audit các file instruction trên máy anh (~15 phút)

Khi anh mở Claude Code trong my-agent, model nhận cùng lúc: ~/.claude/CLAUDE.md (file global), my-agent/CLAUDE.md và các file nó import (context/profile.md, context/conventions.md, memory/MEMORY.md). Anh sẽ đọc chúng bằng con mắt của người viết system prompt.

cd ~/workspace/my-agent
wc -l ~/.claude/CLAUDE.md CLAUDE.md context/*.md memory/MEMORY.md
  1. Đối chiếu với 8 mục của Codex. Mục nào đã có trong các file của anh? Mục nào thiếu hẳn (ví dụ: an toàn git, cách kiểm tra)?
  2. Tìm ít nhất 2 chỗ mâu thuẫn giữa file global và file project. Với mỗi chỗ: nếu theo luật của Codex thì bên nào thắng? Với Claude Code thì chuyện gì xảy ra?
  3. Tìm một luật đang viết như lời dặn nhưng đáng ra phải là hook. Gợi ý: luật nào mà nếu model lỡ vi phạm thì hậu quả khó đảo ngược?
  4. Viết thêm một luật theo kiểu "vết sẹo": một lỗi thật mà agent từng gây ra cho anh, rồi mới đến luật chặn nó. Chưa cần sửa file, chỉ cần viết ra.
Gợi ý (mở sau khi đã tự làm)

Câu 1. Cách kiểm tra có trong context/conventions.md ("Code thay đổi phải được test/verify trước khi báo hoàn thành"). An toàn git có một phần ("Không commit/push khi tôi chưa yêu cầu"), nhưng thiếu luật kiểu "không revert thay đổi mình không làm".

Câu 2. Một chỗ mâu thuẫn rõ: file global bảo "route implementation to executor" (tạm dịch: "giao việc implement cho executor"), còn bảng trong my-agent/CLAUDE.md bảo viết code thì giao cho senior-software-engineer. Theo luật Codex, file project nằm sâu hơn nên thắng. Với Claude Code, model có thể chọn bừa. Chỗ thứ hai nằm ở ngưỡng "việc nhỏ làm trực tiếp": hai file mô tả ngưỡng này theo hai cách khác nhau. Ngoài ra, file global dài khoảng 288 dòng, vượt mức khuyến nghị 200 dòng.

Câu 3. "Không commit/push khi tôi chưa yêu cầu" là ứng viên tốt: push nhầm lên remote thì khó rút lại. Bài 9 (hooks) sẽ biến nó thành một hook thật.

Câu 4. Không có đáp án chuẩn. Luật tốt thì cụ thể và kiểm tra được: "chạy ./mvnw -q test -pl <module> trước khi báo xong" tốt hơn "nhớ test cẩn thận".

6. Kiểm tra cuối bài

Bốn câu. Câu thứ ba nối bài này với phần anh sai ở bài 1, nên hãy đọc kỹ.

File global bảo giao code cho executor, CLAUDE.md của project bảo giao cho senior-software-engineer. Theo tài liệu Claude Code, chuyện gì xảy ra?

  • Model có thể theo bất kỳ bên nào
  • File project luôn thắng vì được đọc sau
  • File global luôn thắng vì phạm vi rộng
  • Claude Code báo lỗi xung đột lúc mở

Claude Code nối mọi file CLAUDE.md vào context, không file nào đè file nào, và nói rõ khi hai luật mâu thuẫn thì Claude "may pick one arbitrarily" (có thể chọn bừa một bên). File project đúng là được đọc sau, nhưng tài liệu không hứa nó thắng. Codex thì khác: luật ưu tiên được viết ngay trong system prompt.

  • Nhắc lại luật ở mọi user message
  • Thêm ví dụ sai vào system prompt

Mọi lựa chọn còn lại đều là lời dặn: model đọc và thường làm theo, nhưng không có gì bảo đảm. Hook chạy trong harness, trước khi lệnh được thực thi, nên chặn được bất kể model quyết định gì. Giống constraint trong database so với comment trong code.

Prompt Codex dặn: đừng đọc lại file sau khi apply_patch, vì nếu sửa không được thì tool sẽ báo lỗi. Lời dặn này chỉ an toàn khi nào?

  • Tool luôn báo lỗi khi sửa thất bại
  • Model đủ thông minh để tự nhớ file
  • File sửa nhỏ hơn giới hạn context window
  • Người dùng tự review diff sau mỗi lượt

Lời dặn trong prompt dựa trên một giả định về harness: sửa hỏng thì chắc chắn có lỗi trả về. Nếu harness nuốt lỗi như agent 192 dòng, model sẽ tự tin bước tiếp trên một file chưa hề được sửa. Prompt và harness phải khớp nhau, và lỗi phải luôn đi ngược về model.

Vì sao xen kẽ hành động với suy luận (ReAct) giảm hallucination so với chỉ suy luận từng bước?

  • Quan sát thật sửa lại suy luận sai
  • Model được suy nghĩ lâu hơn mỗi bước
  • Prompt ngắn hơn nên ít bị nhiễu hơn
  • Tool tự sửa câu trả lời của model

Chỉ suy luận thì một giả định sai ở bước đầu kéo sai tất cả các bước sau (lỗi dây chuyền). Mỗi lần gọi tool, model nhận về một quan sát thật từ bên ngoài, ví dụ rg báo hàm không tồn tại, và nó sửa lại suy nghĩ trước khi đi tiếp. Tool không sửa gì hộ model; nó chỉ cung cấp sự thật.

Tóm lại

  • Một request có bốn lớp: tool definitions, system prompt (harness viết), CLAUDE.md (anh viết, gửi dưới dạng user message), hội thoại.
  • Đọc prompt như đọc runbook: mỗi dòng chặn một lỗi đã từng xảy ra. Prompt và harness phải khớp nhau.
  • Coding agent là ReAct (nghĩ, làm, quan sát), cộng một plan mỏng cho việc dài.
  • Lời dặn không phải luật: muốn chặn chắc chắn thì dùng hook; các file CLAUDE.md mâu thuẫn thì model có thể chọn bừa.
