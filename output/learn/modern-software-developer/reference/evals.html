Coding Agent Evaluation & Benchmarks

Phương pháp đo lường định lượng và thiết lập hệ thống benchmark tự động để kiểm chứng hiệu năng, chi phí token và tính đúng đắn của Coding Agent trong môi trường doanh nghiệp.

1. Ba tầng kiểm thử trong Agentic Engineering

Tầng kiểm thửĐối tượng kiểm traMục đích cốt lõiCông cụ & Phương pháp
1. Tool Unit Test Code backend của tool/MCP server Đảm bảo hàm thực thi không bị văng exception bất ngờ, trả về JSON/text đúng schema kỹ thuật. JUnit, Mockito, Pytest, Client(server) in-memory test.
2. Tool-level Eval Khả năng chọn tool của Model (Single turn) Đo lường model có kích hoạt đúng tool (Trigger) và truyền đúng tham số (Arguments) khi nhận prompt nhập nhằng. Eval prompts dataset, Confusion Matrix, Trigger Rate (đã học ở Bài 5).
3. Agent-level Eval (E2E) Toàn bộ chuỗi hành động ReAct (Multi-turn) Đo lường agent có tự giải quyết được ticket/bug thật trong codebase, chạy test pass và không gây regression hay không. SWE-bench harness, Headless CLI runner (claude -p), Dockerized sandbox.

2. Bộ chỉ số đo lường chuẩn (Agent Core Metrics)

Chỉ sốĐơn vị tínhÝ nghĩa kỹ thuậtKỳ vọng cải tiến
Pass Rate / Resolve Rate Tỷ lệ % Tỷ lệ số task agent sửa code khiến toàn bộ unit/integration test pass hoàn toàn. Càng cao càng tốt (>70% cho task vừa và nhỏ).
Turns to Solve Số lượt (turn count) Số lần agent gọi tool và suy nghĩ qua lại trước khi dừng lại báo hoàn thành. Càng ít càng tốt (thể hiện agent đi đúng hướng, không loanh quanh).
Token Consumption Tokens (Input / Output) Tổng số token tiêu thụ trong suốt phiên làm việc. Quyết định trực tiếp hóa đơn tiền điện toán ($). Giảm 30–50% khi có AGENTS.md chuẩn và subagent cô lập context.
Wall-clock Runtime Giây / Phút Thời gian thực tế từ lúc giao task đến khi agent hoàn tất. Càng ngắn càng tốt (<3–5 phút cho một ticket thông thường).
Tool Error Rate Tỷ lệ % Tỷ lệ tool calls bị fail (ví dụ: gõ sai lệnh bash, sai cú pháp str_replace, đường dẫn file không tồn tại). Càng thấp càng tốt (phản ánh chất lượng tài liệu và instruction).

3. Cấu trúc một Task trong Internal Eval Set

Một bài test benchmark chuẩn mực cho coding agent gồm 4 thành phần tất định:

  1. Task ID & Issue Statement: Mô tả lỗi hoặc yêu cầu tính năng thực tế từ Jira/GitHub Issue (không gợi ý cách sửa).
  2. Base Commit (Git SHA): Trạng thái commit của repo trước khi sửa lỗi (nơi bug đang tồn tại).
  3. Verification Oracle (Bài kiểm thử chứng minh):
    • Fail-to-Pass (F2P): Bài test kiểm tra hành vi bị lỗi. Ở Base Commit bài test này phải FAIL; sau khi agent sửa xong bài test này phải PASS.
    • Pass-to-Pass (P2P): Toàn bộ các bài test cũ của hệ thống. Phải tiếp tục PASS để chứng minh agent không phá hỏng tính năng cũ (No Regression).
  4. Environment Container: Docker container hoặc workspace cô lập với đầy đủ database, JDK, và dependencies sẵn sàng.

4. So sánh: SWE-bench công khai vs Internal Eval nội bộ

Tiêu chíSWE-bench (Lite / Verified)Internal Domain-specific Eval
Nguồn dữ liệu Repo mã nguồn mở Python phổ biến (Django, SymPy, Flask, requests...) Repo nghiệp vụ thực tế của công ty (Java/Spring Boot, Oracle, Kafka)
Rủi ro Data Leakage Cao (Code và PR giải quyết có sẵn trên GitHub, model có thể đã "học vẹt" trong pre-training) Bằng 0 (Mã nguồn độc quyền, private repo, model chưa từng thấy trước đây)
Mức độ sát thực Thấp đối với môi trường doanh nghiệp (thiếu các ràng buộc về audit, security, banking conventions) 100% sát thực (Đo lường chính xác hiệu quả làm việc hàng ngày của kỹ sư)
Chi phí thực thi Rất đắt đỏ (SWE-bench full có 2.294 bài test, chạy mất hàng nghìn USD) Rất rẻ (Bộ eval nội bộ tinh gọn chỉ gồm 5–10 tasks cốt lõi, chạy trong 15 phút)
